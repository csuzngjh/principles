## 0. 一句话方案

**先让用户"看得懂、敢决定"，再让界面"读得快、看着稳"，最后才打磨细节。**

不重做视觉风格——现有暖纸底 + 藏青 + 墨色的体系是对的（评审：设计系统 70 分）。真正要动的是三件事：**语言层（把工程语言挡在界面外）、注意力层（同类信息只说一次）、决策层（把审批页从"材料展示"改成"做决定的页面"）**。

分 3 个阶段，共 10 个批次。第一阶段做完，用户不会再说"这不是给我用的"；第二阶段做完，界面第一眼会从"工程工具"变成"产品"；第三阶段做完，才算打磨完成。

## 3. 设计体系怎么定

### 3.1 字号阶梯（5 级 + 1 个受限标签）

**规则**：正文最小 14px；说明文字最小 12px；11px 仅允许用于"非内容性眉标"（一段区块上方的大写说明），**不得用于按钮、正文、任何用户必须读的文字**。

| 令牌 | 字号/行高 | 用途 | 禁止 |
| --- | --- | --- | --- |
| `text-display` | 28 / 36 | 页面唯一 H1 | 一页出现两个 |
| `text-title` | 20 / 28 | 区块标题 H2、卡片组标题 | 用于正文 |
| `text-subtitle` | 16 / 24 | 卡片标题 H3、小标题、审批正文 | 用于徽章 |
| `text-body` | 14 / 22 | 默认正文、按钮（默认尺寸） | 低于 14 |
| `text-reading` | 16 / 26 | 审批/原则长文阅读区 | 用于表格 |
| `text-caption` | 12 / 18 | 时间、来源、计数、辅助说明 | 承载关键结论 |
| `text-eyebrow` | 11 / 16，字距 0.08em，等宽大写 | 仅"TOOLS""原则审查"这类页面级眉标 | 按钮/正文/必读信息 |

**在代码里落地的位置**：[globals.css](../../packages/pd-console/src/ui/styles/globals.css#L8-L75) 的 `@theme` 内新增 `--text-*`（Tailwind v4 文本令牌，含 `--text-*--line-height`）。**只新增语义名，不覆盖 Tailwind 内置 `text-sm/xs`**，避免全站意外缩放。

```css
@theme {
  --text-display: 28px;   --text-display--line-height: 36px;
  --text-title: 20px;     --text-title--line-height: 28px;
  --text-subtitle: 16px;  --text-subtitle--line-height: 24px;
  --text-body: 14px;      --text-body--line-height: 22px;
  --text-reading: 16px;   --text-reading--line-height: 26px;
  --text-caption: 12px;   --text-caption--line-height: 18px;
  --text-eyebrow: 11px;   --text-eyebrow--line-height: 16px;
}
```

**执行顺序**（这一步决定成本高低）：

1. 先改 4 个共享组件——区块标题、按钮、徽章、卡片标题。这一层改完，全站约一半的 11px 会自动消失。
2. 再按"用户停留最久"的顺序替换页面内联字号：治理焦点 → 原则审查 → 审批详情 → 设置 → 其余。
3. 每改一个页面，同时调 `min-h`、`truncate`、`gap`，否则 11px→14px 会造成文字溢出和卡片高度跳动（这是本次最主要的回归风险）。

### 3.2 间距刻度

只允许 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64` 八个数（Tailwind 默认刻度），**禁止 `13px`、`14px`、`18px`、`22px` 这类手写值**（当前 `px-[14px]` 已出现在按钮里）。

| 场景 | 桌面 | 窄屏（≤768） |
| --- | --- | --- |
| 页面左右留白 | 32 | 16 |
| 区块之间 | 32 | 24 |
| 卡片内边距 | 20 | 16 |
| 列表行高 | 40 | 44（触控） |
| 控件最小热区 | 32×32 | 44×44 |
| 纯文字链接最小热区 | 24×24（用 padding 补） | 44×44 |

### 3.3 圆角、边框、阴影

保留现有 3/4/8/12 四级，但**补齐规则**：

- 徽章/标签：**3px**（现在实际是 2px，与令牌不符，统一到 3px）。
- 按钮/输入框：**4px**。
- 卡片/面板：**8px**。
- 弹层/抽屉：**12px**。
- 卡片一律用 1px 边框，不用阴影；阴影只用于浮层（弹窗、下拉）。深色模式阴影为 `none`（现有做法正确，保持）。

### 3.4 色彩语义与告警分级

**核心规则：红色不是"注意"，红色是"停"。**

| 级别 | 何时用 | 视觉表达 | 禁止 |
| --- | --- | --- | --- |
| **信息** | 说明、来源、时间 | `ink-3` 文字，无底色 | 使用语义色 |
| **提示** | 需要知道但不影响操作（如"资料部分未读取"） | 藏青左边框 + `gov/5` 底 + `ink` 文字 | 用红色 |
| **注意** | 会影响当前决定，但系统仍可用（如"材料不足，暂不可批准"） | 琥珀左边框 + `amber/10` 底 + `ink` 文字，图标琥珀 | 用琥珀做 12px 以下正文（实测 4.2:1，不达标） |
| **阻断/危险** | 不可逆操作、当前流程无法继续、服务不可用 | `danger/10` 底 + 深红文字 + 明确后果 | 用于"未知""缺失""未配置"这类中性状态 |

**红色白名单（只有这 4 类可以出现红色）**：
1. 破坏性或不可逆操作（暂停全部规则、归档、删除）；
2. 阻断级错误（服务不可用、数据读取失败导致无法继续）；
3. 失败状态（任务失败、更新失败），且必须同时给出原因与下一步；
4. 表单校验错误。

**其他约束**：
- 单页琥珀提示最多 1 条；单页红色提示最多 1 条，且必须可关闭或可修复。
- "缺数据/未配置/未登录"一律用**中性或藏青**，不用红、不用琥珀。
- 深色模式沿用现有令牌（实测达标），本轮只新增"琥珀仅限 ≥14px 正文"的限制。

### 3.5 图标与动效

- 图标：统一线性风格、1.5px 描边、16/20 两种尺寸，与文字基线对齐；不使用 emoji 作为结构化元素（B-9 的 emoji 来自演示数据，但界面应对 emoji 做纯文本化处理或统一图标）。
- 动效：只保留两类——页面淡入（4px 位移，≤180ms）和状态反馈（按钮 press 0.98、≤150ms）。**新增动效需回答"它帮用户理解了哪一步"**，否则不加。
- 骨架屏：与最终内容同尺寸，避免加载完成时跳动。
- `prefers-reduced-motion` 已支持，保持。

### 3.6 怎么避免以后再走形（三道闸）

| 闸 | 机制 | 拦截什么 | 成本 |
| --- | --- | --- | --- |
| **静态检查** | 新增 `packages/pd-console/scripts/check-ui-tokens.mjs`：扫描 `src/ui` 中 `text-[Npx]`（N<12 且不在白名单文件）、`px-[14px]` 类手写值 | 字号/间距回潮 | S |
| **文案检查** | 新增 `scripts/check-console-i18n.mjs`：校验代码中 `t("字面量")` 的键在 `zh-CN.json` **和** `en.json` 都存在，且两文件键集合一致 | B-1 这类键名写错、双语漏翻 | S |
| **视觉基线** | 用 `packages/pd-console/tests/` 下新增 Playwright 视觉用例，固定 4 档视口 × 浅/深色 × 关键页面，截图对比 | 布局与字号被悄悄改回去 | M |

三道闸建议接入 `verify:merge` 的前置检查（属于治理变更，需 Owner 同意，见 §10.4）。

**另外**：仓库已有 `/design-system` 页面（路由存在，见 [App.tsx](../../packages/pd-console/src/ui/App.tsx#L249)）。把它升级为"活规范"：字号阶梯、间距、色彩语义、状态级别、空/错/慢模板都在这里各放一个真实示例。**改一次规则，必改这一页**——它是对抗"规范写在文档里、代码里各写一遍"的唯一低成本办法。

## 4. "人话层"怎么建

### 4.1 分层：数据层不改，只加一层"翻译"

```
数据/接口（原始枚举、错误码、路径）   ← 不动
        ↓
统一翻译层（UI 层唯一入口）           ← 本方案新增的唯一能力
        ↓
页面组件（只拿人话，不接触原始值）
```

**复用已有能力，不新建抽象**：[enum-labels.ts](../../packages/pd-console/src/ui/utils/enum-labels.ts) 已经实现了"i18n → 本地映射 → 原始值"的三级回退，且有 10 个类别。本方案做三件事：

1. **扩类别**：新增 `decisionStatus`（待您决定/已批准/已拒绝/已暂缓）、`taskOutcome`（已完成/失败/需要您处理）、`debtReason`（长期未生效/未部署/已过期）、`runtimeMode`（正常/部分功能不可用）、`approvalReadiness`（材料齐全/材料不足/版本未锁定/权限未知）。
2. **堵回退漏洞**：现状是"找不到标签就显示原始值"，这正是 `internalization-missing` 泄漏的原因。改为：生产环境返回中性兜底（如"状态待确认"），开发环境 `console.warn` 输出缺失的类别与值；同时补一条单测，断言所有已知枚举都有标签。
3. **新增一个技术文本处理器**：`utils/technical-detail.ts`，提供三个纯函数——
   - `maskPath(p)`：`C:\Users\张三\AppData\...` → `C:\Users\***\AppData\...`；
   - `summarizeCommand(cmd)`：识别 `pd runtime ...` 等命令，返回 `{ summary: "继续处理这条候选", command: 原文 }`；
   - `isTechnicalText(s)`：判断一段文本是否为命令/堆栈/路径/内部编号。

   页面不再自己拼"Run: ..."，只调用 `summarizeCommand`，命令原文放进"技术详情"折叠区。

> 为什么不把这些写进 i18n JSON 就完事？因为 **i18n 负责"翻译句子"，不负责"翻译状态"**。状态是有限枚举，放在有类型的映射表里才能被测试和静态检查；散在 JSON 里只能靠人眼发现。

## 5. 注意力预算的规则化

**结论**：把"克制"写成可检查的数字，否则每次改版都会重新膨胀。

### 5.1 首屏规则（R1）

| 规则 | 数值 | 检查方法 |
| --- | --- | --- |
| R1-1 首屏状态提示条 | ≤1 条（所有"资料待确认/决策锁定/部分不可用"合并为 1 条） | DOM 计数 `[data-status-banner]` |
| R1-2 首屏主按钮 | ≤1 个深色主按钮 | 计算样式计数 |
| R1-3 第一条可操作项位置 | 1440×900 下 top ≤320px；1024×768 下 ≤360px；390 宽下 ≤420px | Playwright `boundingBox()` |
| R1-4 页头解释文案 | ≤2 行（约 90 个汉字），超出折叠 | 文本长度断言 |
| R1-5 每屏视觉焦点 | ≤3 个（主标题、主内容、主操作） | 人工清单 + 截图 |

### 5.2 重复上限（R2）

| 规则 | 数值 |
| --- | --- |
| R2-1 同一结论文案在同一页面出现次数 | **≤1 次**（含标题、说明、空状态） |
| R2-2 同一原因导致的多个条目 | 合并为"共 N 条（原因相同）"，展开后才逐条列出 |
| R2-3 同类徽章出现率 | 超过该页条目数 **30%** 且 N≥5 时，禁止逐项展示，必须升级为页级说明 |
| R2-4 同一信息的呈现层数 | ≤2 层（页级说明 + 条目内差异），不允许"页级说明 + 每条重复 + 每卡徽章"三层同时存在 |

### 5.3 告警分级与红色白名单

见 §3.4。补充两条可检查规则：

- R3-1 每个提示必须带级别属性（`info | notice | attention | danger`），页面不得使用未分级的提示样式。
- R3-2 `danger` 级提示在同一屏最多 1 条；超过 1 条时，多余的降级为 `attention` 并合并。

### 5.4 折叠规则（R4）

- 解释性内容超过 2 行 → 折叠，摘要一行。
- 技术内容（§4.3）→ 一律折叠。
- 折叠控件必须写清楚"展开后能看到什么"（"展开完整规则实现" → "查看技术实现"），不能只写"展开"。

### 5.5 检查方法

1. **自动**：Playwright 用例 `attention.spec.ts`——统计状态条数量、重复文本次数、首条待办位置、红色元素数量。
2. **人工**：每阶段结束做一次"5 秒测试"——只看首屏 5 秒，说出"这页要我干什么"；说不出来即不通过。

## 6. 决策页的信息模板

### 6.1 五段结构（审批详情 / 原则采纳 / 证据判断共用）

| 段 | 必须回答 | 内容来源 | 长度上限 | 缺失时 |
| --- | --- | --- | --- | --- |
| **① 是什么** | 改什么、哪个版本、什么类型 | 标题 + 版本 + 类型 | 80 字 | 禁用批准 |
| **② 为什么现在** | 哪次行为触发的、什么时候、来自哪里 | 事件时间 + 来源 | 2 行 | 显示"来源未记录"，不阻断 |
| **③ 影响谁 / 不处理会怎样** | 影响范围、默认行为、风险等级、可逆性 | 范围内 / 例外 / 风险说明 | 4 行 | 禁用批准 |
| **④ 推荐动作** | 系统建议批准/拒绝/暂缓 + 一句理由 | 现有推荐字段 | 1 句 | 显示"系统无推荐"，不替用户选 |
| **⑤ 决定** | 三个按钮 + 备注 | — | — | 见 §6.2 |

**页面顺序固定为 ①②③④⑤**，不允许把"技术详情""证据链""历史记录"插在③和⑤之间。技术内容全部收进底部"技术详情"折叠或二级页。

### 6.2 就绪度矩阵（信息不全时怎么表现）

| 状态 | 判定条件（保守，只认显式标记） | 主按钮 | 次按钮 | 必须显示 |
| --- | --- | --- | --- | --- |
| **材料齐全** | 风险说明、准则、范围三项都有值 | 跟随推荐（无推荐则"批准"） | 拒绝 / 替换 | 推荐理由一句话 |
| **材料不足** | 任一必填项为"未记录/暂不可读" | **「查看缺什么」→ 跳转到缺失项** | 拒绝 | "缺少：风险说明、行为准则。补齐后可批准。" |
| **版本未锁定** | 审批服务未保证提交版本与阅读版本一致 | **「重新读取」** | 无 | "当前不提供批准/拒绝，避免您批错版本。" |
| **权限未知** | 无法确认审批权限 | 无（只读） | 无 | "暂时无法确认审批权限。" + "去设置" |
| **来源未关联** | 找不到对应原则或可读名称 | **禁用** | 拒绝 | "未找到对应原则，请先核对；材料不足时可以拒绝。" |

**关键取舍**：材料不足时，**主按钮不再是"批准"**。这会让短期处理速度变慢（用户要多一步去补材料），但换来的是"不会批错"。这一点需要 Owner 确认（§10.4）。

### 6.3 底部决策条规格

- 固定吸底，高 **64px**，内容区底部留白 ≥96px（避免最后一行被遮住）。
- 左：进度"第 3 / 18 件"；中：一句推荐（或"系统无推荐"）；右：三个按钮。
- 键盘：`J` 下一件、`K` 上一件、`A` 批准、`R` 拒绝（仅在无输入焦点时生效，且批准/拒绝需再确认）。
- 提交中：按钮进入 loading，禁用重复提交，显示"正在提交…"；结果未知时显示"结果待确认，请重新读取"而不是"成功"。

### 6.4 与现有组件的关系

不新建页面框架。现有 [OwnerWorkbench](../../packages/pd-console/src/ui/pages/focus/OwnerWorkbench.tsx)（双栏）与 [ApprovalSubjectReading](../../packages/pd-console/src/ui/pages/focus/ApprovalSubjectReading.tsx)（材料区）已经承担了大部分结构，本轮是**调整区块顺序 + 增加吸底决策条 + 增加就绪度判定**，不改数据获取方式：

```
OwnerWorkbench（双栏，不变）
├── 左：列表（加排序理由）
└── 右：ApprovalSubjectReading（重排为 ①②③④）
        + 新增 DecisionBar（吸底，⑤）
        + 新增 DecisionReadiness（纯函数，由现有字段推导）
```

`DecisionReadiness` 必须是**纯函数 + 单测**，只读现有字段；不新增后端契约、不新增权限判定（见 §10.1）。

## 7. 空 / 错 / 慢三态的统一模式

**结论**：三种状态共用同一个 `StatePanel` 组件（4 个变体），禁止每页各写一套。

| 变体 | 标题（事实） | 说明（为什么） | 主行动 | 次行动 | 禁止 |
| --- | --- | --- | --- | --- | --- |
| **空** | "还没有需要您处理的事" | "PD 在捕获到行为偏差后会在这里通知您。" | 去接入/去设置（若未接入） | 看示例 | 警示色、0 项告警、"不完整" |
| **首次** | "欢迎，先完成两件事" | "接入工作区 → 打开控制台。" | 开始引导 | 跳过（跳过后落到空状态引导页） | 空白列表 |
| **错·不可达** | "无法连接工作台" | "服务未响应。可能是控制台没有启动。" | 重试 | 查看启动方式（技术详情） | 跳登录页 |
| **错·认证** | "需要访问令牌" | "这次请求被拒绝，需要令牌才能继续。" | 输入令牌 | — | 把网络错误也说成认证 |
| **错·部分不可用** | "部分功能暂不可用" | "核心待办仍可使用；受影响的：原则账本。" | 刷新 | 技术详情 | 说"系统故障" |
| **慢** | "正在检查更新（2/3）" | "正在核对版本与下载源。" | 稍后再试 | 取消 | 只有骨架、无文字 |

### 7.1 文案模板（可直接复用）

```
空：[还没有 X]。 [什么情况下会出现 X]。
     [主行动]
错：[现在发生了什么]。[最可能的原因]。
     [主行动] · [技术详情]
慢：正在 [具体动作]（第 n / m 步）。
     [超过 10 秒的补充：可以离开此页，完成后会通知您]
```

### 7.2 何时不该报警

- 条目数为 0 时，"资料未读取""列表可能不完整"一律不显示（B-2 的根因）。
- 首次进入且工作区为空时，不显示任何琥珀/红色提示。
- 只读状态（权限不足）是**中性信息**，不是错误。
- 历史数据缺失说明（"无法保证历史完整性"）不放在首屏，收进"这个数字代表什么"折叠。

### 7.3 慢的阈值

| 时长 | 表现 |
| --- | --- |
| 0–1 秒 | 无提示（避免闪烁） |
| 1–2 秒 | 局部骨架（与内容同尺寸） |
| >2 秒 | 出现步骤文案 + "稍后再试" |
| >10 秒 | 允许离开，后台继续，完成后通知 |
| 任何时长 | 失败必须有原因 + 下一步 |

## 10. 风险与不做的事

### 10.1 会牵动数据或权限逻辑的改动（必须单独评审）

| 改动 | 为什么敏感 | 防护 |
| --- | --- | --- |
| B-2 空状态报警 | 修改的是"何时显示警示"的判定，容易把真实警示也关掉 | 只改 `workItems.length===0` 且无错误的分支；补"有错误 + 0 项"的测试 |
| B-3 积压状态矛盾 | 涉及队列状态的语义归属 | 先确认"积压"的定义来源，再统一文案；不改状态计算 |
| B-6 原则详情矛盾 | 涉及"治理身份是否建立/数据是否读取"的判定 | 由数据层给出单一结论；UI 不做二次推断；必须加回归测试 |
| 材料不足时禁用"批准" | 会改变用户可执行的操作集合 | 只认显式"未记录/不可读"标记，不推断；保留"拒绝"可用；Owner 确认 |

**这些改动不新增后端契约、不新增权限判定、不改数据库**。若发现必须改数据层，单独开缺陷修复项，不并入视觉改版。

### 10.2 本轮不做

- 不改视觉风格（配色、字体家族、蓝图网格、暖纸底）。
- 不引入新组件库、不重写路由、不改信息架构的页面数量。
- 不做产品功能新增（例如"自动排序算法"上线、新的审批类型）。
- 不动安装器与已安装运行时目录（`~/.pd/runtime/`、`~/.openclaw/extensions/`），这是仓库硬规则。
- 不做英文界面的完整重排（只保证新增文案双语同步）。
- 不删除 `/design-system`，而是把它变成活规范。
- 不做 320/360 极窄屏专项适配（本轮验收到 390）。

### 10.3 回归风险与防护

| 风险 | 触发原因 | 防护 |
| --- | --- | --- |
| 字号放大导致布局溢出 | 11px→14px 后卡片高度与文字宽度变化 | 每页同时调 `min-h`/`truncate`/`gap`；四档视口截图对比 |
| 全局替换误伤 | 直接批量替换 697 处字号 | 先组件层、再页面逐个；每批只改一个维度（字号或文案，不同时改布局） |
| 深色模式失衡 | 新增琥珀/红色用法 | 每次改完重跑对比度脚本；深色截图必看 |
| 双语漏翻 | 只改 `zh-CN.json` | `check-console-i18n.mjs` 校验两文件键集合一致 |
| i18n 键名再写错 | 手写 `t("...")` | 同上脚本；B-1 修复时补一条用例 |
| 决策页禁用按钮误伤 | 就绪度判定过严 | 只认显式缺失标记；"齐全"路径必须有正向用例 |
| 视觉基线噪音 | 截图受字体/DPR 影响 | 固定容器与字体加载完成后再截；只比对关键区域 |

### 10.4 需要 Owner 拍板的取舍

1. **材料不足时是否禁用"批准"？**
   - 禁用：更安全，但处理变慢，且用户可能不理解"为什么不能批"。
   - 不禁用但降级为描边按钮 + 顶部说明：更顺畅，但仍可能误批。
   - 建议：**禁用，并把"查看缺什么"做成主按钮**。

2. **推荐动作为"拒绝"时，是否让"拒绝"成为深色主按钮？**
   - 是：视觉与建议一致，决策正确率高；但用户可能觉得"被引导"。
   - 否：保持"批准"为主按钮，但违背"界面不替用户做决定"。
   - 建议：**跟随推荐**，并在按钮上方写明推荐理由，让用户看到"为什么"。

3. **全站人称统一为"您"——已由 Owner 于 2026-11-11 拍板。**
   - 决定：**全站中文文案统一用"您"**，同时清掉现存的"你/您"混用。
   - 理由：Owner 明确要求；"您"在治理类界面更符合场景语气。
   - 执行影响：术语表（§4.2）与验收标准（§9.1）中原本写"你"的地方一律按"您"执行。

4. **Examiner / 更新 / 失败任务是否收进"高级"入口？**
   - 收进：首屏更安静，但功能可发现性下降。
   - 不收：保持现状，噪音继续。
   - 建议：**保留在导航，但降为"技术"分组**，并在这三页首屏各加一句人话结论。

5. **是否把字号/i18n 守卫接入 `verify:merge`？**
   - 接入：能长期防回潮，但会增加合并门禁的失败面。
   - 建议：**先以包级脚本存在（`npm run check:console-ui`），稳定 2 个阶段后再进门禁**。

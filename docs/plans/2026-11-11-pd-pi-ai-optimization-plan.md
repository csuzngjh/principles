## Owner 原则的落地方式

| 原则 | 对本方案的约束 |
| --- | --- |
| 代理全在后端运行，不与 Owner 对话 | 流式输出从方案中**彻底移除**：不做、不排期、不留接口。L2 现有的 `streamSimple` 只作为 pi 官方智能体循环的内部传输方式保留（删掉它等于重写 pi 的循环，违反第 3 条） |
| 稳定 > 高效 > 经济 | 阶段顺序即优先级；"高效"阶段的项必须不与"稳定"冲突 |
| 能复用 pi-ai 就复用 | 判定表里每条先问"pi 有没有现成入口"；只有证明不够用才写"自建"，并给出最小范围 |
| 不为将来预建抽象 | 所有自建都落在已有文件内，不新增模块、不新增接口层 |

# 二、分阶段实施细则

> 每个阶段独立可交付、独立可验证、独立可回滚。阶段内条目有依赖的已注明。

## 第一阶段：稳定（对应报告 §4.1 / §4.2 / §4.5 / §4.8 / §3.3）

### S1 让取消真正生效，超时只有一个预算

- **改哪里**：`packages/principles-core/src/runtime/adapter/pi-ai-runtime-adapter.ts`（`cancelRun` 第 1143–1150 行、`startRun` 第 644–681 行、修复调用第 1394–1395 行）。
- **怎么改**：
  1. 适配器实例内持有一个 `AbortController`；外部取消 → `controller.abort()`。
  2. 总超时用 `AbortSignal.any([controller.signal, AbortSignal.timeout(budget)])` 合成一个信号，传给 `completeSimple` 的 `signal`。
  3. 修复调用不再用固定 60 秒，而是"剩余预算"，剩余不足 1 秒则直接放弃修复并返回已得到的结构化错误。
- **失败路径**：abort 后必须映射为 PD 的 `cancelled` 类别，不能被当成 `execution_failed` 再重试一次。
- **改前红 / 改后绿**：用已有的本地 HTTP 桩（`__tests__/pi-ai-runtime-adapter-budget-wire.test.ts` 的 stub 机制）让请求永不返回 → 调 `cancelRun()` → 断言 `startRun` 在 1 秒内以 `cancelled` 结束、且桩只收到 1 次请求。改前该测试超时（红），改后 1 秒内结束（绿）。
- **预期效果**：用户点取消，任务真的停；不再为已放弃的请求付钱。
- **成本 / 风险**：约 30 行。风险低，但会让过去被吞掉的 abort 路径暴露出来（属于修 bug，不是回归）。
- **回滚**：单文件改动，revert 即可。

### S2 传输重试交给 pi-ai，PD 只保留"输出预算下调"

- **改哪里**：`pi-ai-runtime-adapter.ts` 的 `completeWithRetry`（第 1443–1753 行）与调用点（第 1510 行的 `maxRetries: 0`）。
- **怎么改**：
  1. 传输类失败（网络、429、5xx、408）不再由 PD 循环处理：调用时传 `maxRetries: 2`、`maxRetryDelayMs: 30_000`，由 pi-ai 判定与等待。
  2. PD 只保留一种重试：**输出预算被拒**（`MAX_TOKENS_REJECTED_PATTERN`，第 77–78 行）时把 `maxTokens` 下调（减半）再试一次。这是业务语义，pi-ai 不做。
  3. 删掉 PD 的指数退避与"限流翻倍"逻辑（第 1472–1476、1621–1623 行）。
- **失败路径**：`maxRetryDelayMs` 设 30 秒是为了**不改变现有最长等待**；若供应商要求的等待超过 30 秒，pi-ai 会立即失败并带上请求的延迟，PD 把这条原始信息写进证据，不再自作主张。
- **改前红 / 改后绿**：本地桩依次返回 `429`（带 `retry-after: 0`）→ `200`。断言"总请求数 = 2"且第二次紧接第一次。改前 PD 用自己的正则也能通过，但桩返回 `401` 时：改前请求 3 次（红），改后请求 1 次（绿）。两个用例一起加，覆盖"该重试的重试、不该重试的不重试"。
- **预期效果**：密钥/权限/参数错误不再重试；供应商要求的等待被正确执行。
- **成本 / 风险**：约 −80 行（删代码）+ 2 个参数。风险中等：重试节奏由 pi-ai 决定，需要跑一轮真实回归确认。
- **回滚**：恢复 `maxRetries: 0` 与旧循环，改动集中在一个函数内。

### S3 错误分类用状态码，不再猜文本

- **改哪里**：`pi-ai-runtime-adapter.ts` 的 `onResponse` 注入点 + 现有错误归一化函数；`pi-ai-http-transport.ts` 不动。
- **怎么改**：给 `completeSimple` 传 `onResponse`，把 `{status, headers}` 记到本次调用的局部变量（每次尝试覆盖）；错误归一化时优先看状态码：`401/403 → 配置错误`、`400/422 → 请求错误`、`429 → 限流`、`5xx → 上游故障`、`408 → 超时`；没有状态码时才退回现有文本规则。
- **失败路径**：状态码缺失（自定义端点不回传）→ 走旧文本规则，并在遥测里标记 `status_unknown`，不静默降级。
- **改前红 / 改后绿**：桩返回 `401` + 文本 "quota exceeded"（故意误导）→ 断言分类为"配置错误"且不重试。改前会被文本规则误判成限流并重试 3 次（红），改后 1 次且分类正确（绿）。
- **预期效果**：错误类别可信，后续所有"该不该重试/该不该换模型"的判断才有依据。
- **成本 / 风险**：约 20 行。风险低。
- **回滚**：删掉 `onResponse` 注入即可回到纯文本判定。

### S4 上下文先估算，溢出可识别

- **改哪里**：`pi-ai-runtime-adapter.ts` 的输入拼装（第 683–691 行）；`artificer-l2-adapter.ts` 第 428 行的 5 万字符截断。
- **怎么改**：
  1. 发请求前用 `estimateContextTokens`（`@earendil-works/pi-ai/utils/estimate`）估一次，和 `model.contextWindow` 比较；超过 90% 就按固定优先级裁剪输入（先丢重复证据、再丢低置信度条目），并在证据包里记录"丢弃了哪些 id 与原因"。
  2. 失败后用 `isContextOverflow` 判一次，命中则归类为"上下文溢出"，不再当作普通失败重试。
  3. 删掉 Artificer 的 5 万字符魔法数，改用同一套预算。
- **失败路径**：估算低于实际（估不准）→ 仍可能溢出，但此时走第 2 步识别，会明确报"溢出"而不是"未知错误"，可重试一次更激进的裁剪。
- **改前红 / 改后绿**：构造一个明显超过 `contextWindow` 的输入，桩返回 pi-ai 的溢出错误文本 → 断言错误类别是"上下文溢出"且输入被裁剪、证据里记了丢弃 id。改前是 `execution_failed` 且不裁剪（红），改后（绿）。
- **预期效果**：溢出从"莫名失败"变成"可解释、可恢复"。
- **成本 / 风险**：约 40 行（含 #8 的裁剪优先级）。风险：裁剪规则需要产品判断，**这是本阶段唯一需要 Owner 拍板"哪些证据可以丢"的点**。
- **回滚**：把裁剪阈值设为无穷大即等于关闭。

### S5 补上唯一的裸调用

- **改哪里**：`packages/host-runtime/src/adaptive-selection.ts` 第 454–455 行。
- **怎么改**：补 `outputSchemaRef`（复用 `output-schema-registry` 里已有 schema，如需新增只加一个 schema 定义），让它走和其它 runner 一样的三路径保护。
- **改前红 / 改后绿**：断言该调用携带 schemaRef；改前拿不到（红），改后拿到（绿）。同时用一个"模型返回缺字段"的桩验证会触发校验失败而不是静默接受。
- **预期效果**：整条管道没有一处绕过结构校验。
- **成本 / 风险**：约 5 行 + 一个 schema。风险：会把现有不规范输出暴露成失败，需要观察一轮。
- **回滚**：去掉 schemaRef。

## 第二阶段：高效（对应报告 §4.3 / §4.4）

### S6 三条输出路径共享一次"运行预算"

- **改哪里**：`pi-ai-runtime-adapter.ts` 第 770–796 行（路径选择）与三条路径函数。
- **怎么改**：
  1. 在 `startRun` 内创建一个纯局部对象 `{ requestsLeft }`，初始值 3（可配置）。
  2. 三条路径每次发请求前扣 1；扣到 0 就停止并返回当前最好的错误。
  3. 可重试的传输错误由 pi-ai 内部消化（S2 之后），不再额外消耗 PD 的路径预算。**注意口径**：`requestsLeft` 只约束 PD 的三条输出路径，不覆盖 pi-ai 的内建重试——一次路径调用在传输层仍可能产生多次 HTTP 请求。
- **失败路径**：预算耗尽时返回"已尽力"的结构化结果，带 `attempts` 与最后错误，不抛裸异常。
- **改前红 / 改后绿**：桩让工具路径与 JSON 路径都返回不可解析内容 → 断言 **PD 路径调用 ≤ 3**。实际 HTTP 请求数是 `路径调用 × (1 + pi-ai 内建重试次数)`（默认重试 2 次时最坏 9），不要把它写成"总请求数 ≤ 3"。改前最坏 5 次路径调用（红），改后 ≤ 3（绿）。
- **预期效果**：最坏路径调用 5 → 3（−40%）；实际 HTTP 请求取决于传输层重试配置，需单独观测。
- **成本 / 风险**：约 30 行，涉及 5 处签名。风险：属行为变更，需 characterization 测试先锁定现有三路径行为再改。
- **回滚**：把预算设大（如 99）即等于旧行为。

### S7 并发上限（先测后做）

- **改哪里**：`packages/openclaw-plugin/src/service/internalization-auto-consumer-service.ts`（第 21、209 行）。
- **怎么改**：只有在测量显示"积压"或"429 占比上升"时才做。做法是在现有串行循环内加一个并发许可计数，不引入队列库、不新建调度器。
- **先测什么**：① 每轮平均耗时与积压任务数；② 429 占全部失败的比例；③ 同一 provider 的并发峰值。
- **改前红 / 改后绿**：先写一个"测量测试/脚本"统计上述三项；没有数据不动代码。
- **预期效果**：吞吐提升（幅度待测）。
- **成本 / 风险**：约 20 行。风险：并发会放大限流，必须与 S3 的错误分类一起观察。
- **回滚**：并发数设回 1。

## 第三阶段：经济（对应报告 §4.7 / §5）

### S8 成本按阶段归因

# 三、量化目标

| 指标 | 现状 | 目标 | 依据 / 状态 |
| --- | --- | --- | --- |
| 单次逻辑运行的最坏请求数 | 5（1 工具 + 1 JSON + 3 自由文本） | ≤ 3 | S6；第 3 条由 `maxRetries` 默认值 2 推出 |
| 401/403/400 的重试次数 | 最多 3 | 0 | S2 + S3 |
| 429/5xx 的重试次数 | 最多 3（PD 自己） | 2（pi-ai） | `maxRetries: 2` |
| 取消后真正停止的时间 | 不停止（no-op） | ≤ 1 秒 | S1；实测以桩为准，接入真实供应商后复测 |
| 成本可归因的调用比例 | 0% | 100% 成功调用带 `cost.total` | S8 |
| 溢出失败中"发请求前就被识别"的比例 | 0% | ≥ 80%（**待测量**） | S4；估算不是精确分词，先测再定 |
| 缓存命中率 | 不适用（未开启） | **待测量** | S9 |
| 单次诊断成本 | 未测量 | **待测量** | S8 上线后才能给 |
| 任务积压 / 429 占比 | 未测量 | **待测量** | S7 的前置数据 |

# 四、明确不做清单

| 不做的事 | 一句话理由 |
| --- | --- |
| 流式输出、增量 JSON 解析 | Owner 明确：代理不与 Owner 对话，没有消费端；留接口就是预建抽象 |
| 把 L2 的 `streamSimple` 改成 `completeSimple` | 那是 pi 官方智能体循环的内部传输方式，改掉等于重写循环 |
| 迁移到 `createAgentSession` 完整智能体运行时 | 会引入文件工具、会话生命周期与权限边界，PD 不需要 |
| 会话压缩 / 引入 pi-durable | 新子系统 + 新持久化，而 PD 的调用是无状态一次性任务 |
| 多 provider 并行 / 预建 provider 抽象 | 没有第二个 provider 的运行数据，属投机抽象 |
| 自动模型故障转移 | 没有失败率数据，先做 S3 把分类做准再说 |
| 缓存预热（cache warming） | 1.2.0 没有该能力；且 PD 调用间隔以秒计，用不上 |
| 依赖升级到 1.5.1 | 没有单项收益论证；若将来确需某能力，单独立项 |
| 工具参数校验 `validateToolArguments` | PD 不执行模型自选工具，能力没有落点 |

# 五、执行顺序

```
第一阶段（稳定）── S1 ── S2 ── S3 ── S4 ── S5
                     │
第二阶段（高效）      └── S6（依赖 S2/S3 的重试语义已收敛）
                          └── S7（依赖 S7 自己的测量数据）

第三阶段（经济）      S8（可与第一阶段并行：只读字段、零行为改变）
                      S9（依赖 S8 的用量数据）
```

- **必须先后的**：S2 → S3（先让 pi-ai 负责重试，再用状态码分类，否则两套机制打架）；S3 → S6（预算要基于正确的"可重试"判断）；S8 → S9（没有用量数据无法判断缓存是否划算）。
- **可并行的**：S1 与 S5 互不影响；S8 可与整个第一阶段并行（纯读字段）。
- **必须先有测量数据再做**：S7（并发上限）、S9（缓存）。S4 的裁剪阈值也需要一轮真实输入分布才能定，但"识别溢出"本身不需要数据，可以先上。
- **建议的首个交付**：S1 + S5 + S8 合并为一个小批次（三处互不冲突、风险最低），先拿到"取消可用 + 无裸调用 + 成本可见"三个变化；S2/S3 作为第二个批次单独验证重试行为。

# 六、风险与总成本

- **代码总量**：净减少约 30–50 行（S2 删掉的重试逻辑多于新增），新增集中在 S4 的裁剪规则。
- **最大风险**：S2 改变失败时的等待节奏。用 `maxRetryDelayMs: 30_000` 把上限锁在现状，可把风险压到"等待更聪明，而不是等待更久"。
- **需要 Owner 拍板的两处**：① S4 中"哪些证据可以丢"的优先级；② S2 是否接受"删除 PD 自己的重试循环、改用 pi-ai"。

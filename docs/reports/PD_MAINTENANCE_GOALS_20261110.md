# 三个目标的分离：各自的成本、第一步与度量

- 日期：2026-11-10
- 状态：给 Owner 决策的输入。**不排期**，不是计划。
- 关联：`docs/plans/2026-11-10-architecture-complexity-remediation-plan.md`（只覆盖目标 A）

---

## 0. 为什么必须分开

三个目标经常被写成同一句话："降低维护成本，让 AI 更好开发这个项目"。
但它们的最短路径不同、度量不同，甚至互相冲突：

| 目标 | 真正想改善的体验 | 最短路径 | 与其它目标的关系 |
| --- | --- | --- | --- |
| **A 少踩坑** | 出了事能发现、能读懂 | 把静默失败变成可观察失败 | 与 B 基本正交；有时为可观察性**增加**代码量 |
| **B 改得更快** | AI 改一个需求的实际负担 | 缩短"找到该改哪里 / 找到哪些测试" | 会**减少**代码量；但收益取决于改哪个区域 |
| **C 降复杂度** | 结构债本身 | 只还"有复发证据"的债 | 容易变成"重构上瘾"，与 A/B 都可能无关 |

把 C 混进 A 的典型后果：为一个 3 行 bug 发明一套 schema 框架。
把 A 混进 B 的典型后果：为了"改得快"而**删掉**失败信号。

**本文件只描述，不排期。** 要不要另开线，由 Owner 判断。

## 1. 目标 A：少踩坑（事故可发现、失败可读）

**这就是当前计划**（`docs/plans/2026-11-10-architecture-complexity-remediation-plan.md`）。
这里只补"怎么衡量"，不重复计划内容。

### 现在最贵的是什么

不是"有 bug"，而是**bug 只能靠人肉发现**：
- 配置字段被静默丢弃（`systemPrompt`、`splitPipelineTimeoutMs`）；
- 决策列表读失败与"没有待决"同形（`catch { continue; }`）；
- read-model 跳过行不可见（5 个 `continue`）。

### 第一步

已在本计划内：Phase 5A（已完成）→ 2B（可计数可归因）→ 3A（配置字段不再静默）→ 5B（页面渲染 warning）。

### 怎么衡量有没有变好

| 指标 | 今天 | 度量方式 |
| --- | --- | --- |
| **静默失败点数量** | 配置校验 7 处白名单构造点 + 决策列表 1 处 `catch{continue}` + read-model 5 个 `continue` | 人工登记表（本计划的批次表即基表）；每修一处，表里划掉一行 |
| **同一类事故的复发次数** | 1 次（`principles` 曾手工修过同类，profile 又复发） | `docs/process/error-management/records/` 的 occurrence 计数 |
| **失败是否可归因** | 部分：顶层 degraded 已渲染，逐行 warning 未渲染 | 任取一个失败场景，能否在 UI/CLI 上回答"哪一行、为什么" |
| **修复前能否先红** | 5A 已证明可行（8 个测试） | 每个批次必须给出"今天红"的证据 |

**不追求的指标**：测试覆盖率。覆盖率高与"事故可发现"没有因果关系。

## 2. 目标 B：改得更快（AI 改一个需求的实际负担）

### 现在最贵的是什么

按代价排序，**不是**配置读取、**不是** SQL 直连：

1. **定位"哪些测试保护这段代码"**。仓库有 **1,391 个测试文件 / 382,741 非空行**（2026-11-10，`origin/main` 26defe20 实测）。
   改一个 core 文件的现实流程是：`rg` 搜符号 → 猜文件名 → 试跑 → 失败 → 再搜。这一步每次都发生，且没有任何自动化。
2. **字段从后端到 UI 要改 5 个地方**：`pd-config-types.ts` / core validator / console model / `validators.ts`（3,934 total / 3,564 非空行）/ 测试。其中 `validators.ts` 那一步**漏改不报错**（静默丢字段）。
3. **跨包影响面不可预测**：`runtime/index.ts`（2,371 total / 2,147 非空行）是公共 barrel，改导出会触发 PRI-775 冻结护栏。

### 第一步（两个可量化落地项）

**(B1) 测试反查索引**：`npm run test:for -- <源文件路径>` 输出"直接或间接 import 该文件的测试文件"。

- 做法：用 `git ls-files` + 正则解析 import 图（无需 AST、无需新依赖；`tsc` 已有，但不值得为此跑全量编译）。
- 验收：对 10 个已知文件（例如 `OwnerDecisionConsoleModel.ts`）手工核对，反查结果必须包含人工认定的测试集。
- 预估：脚本约 150 行 + 1 个 npm script，**1 人日**。
- 度量：从"改一个 core 文件到跑上第一批相关测试"的命令数，**基线 3–5 → 1**。

**(B2) `validators.ts` 生成化**（探针优先，见字段丢弃方案文档 §7）。

- 先只做 `validateOwnerDecisionsData` 一个函数（`validators.ts:3878-3890`），保持 12 个现有断言不变。
- 预估：探针 **1–2 人日**；若成立，全量收敛 **5–8 人日**（按 3,934 行、约 30 个重建型 validator 估）。
- 度量：文件行数 3,934 → 目标 < 1,200；"后端新增一个响应字段需要改的前端文件数" **2 → 1**（且由编译期兜底）。

### 怎么衡量"改得更快"

不要用主观感受。建议做一次**回放测量**：取最近 3 个真实变更（例如 PRI-1136 改名、PRI-1119 配置映射、本次 5A），记录：
- 打开过的文件数；
- 跑过的测试命令数；
- 第一次 CI 失败的原因（是"实现错"还是"漏跑测试"）。

基线建立后，再看 B1/B2 是否让这三个数字下降。**没有基线就不做 B2 的全量部分。**

### 明确不追求的

- 减少包数量（拆包不会让改一个字段更快）；
- 统一代码风格（与本目标无关）；
- 把测试写得更多（1,391 个文件已经很多了，问题是**找不到**，不是不够）。

## 3. 目标 C：降低复杂度本身（结构债）

判断标准只有一条：**有没有复发证据**。没有证据的"看着乱"，不做。

| 结构债 | 规模（实测） | 是否值得还 | 理由 |
| --- | --- | --- | --- |
| 配置校验：类型与校验器两套真相 | `pd-config-validate.ts` 932 行 / 7 个构造点 | **值得** | 已有 2 个字段丢失 + 1 次同类复发 |
| Console UI validators 逐字段重建 | 3,934 total / 3,564 非空行 | **值得（生成化）** | 与上一行同构，规模大 4 倍；新字段静默丢失 |
| 存储直连（`new SqliteConnection`） | 70 处 / 45 文件；测试直连 SQL 326 条 / 105 文件 | **部分值得**：只在**新增**处收口 | 迁移存量 42 个产线文件无事故证据，风险 > 收益 |
| 公共 barrel `runtime/index.ts` | 2,371 total / 2,147 非空行 | **部分值得** | 已有 PRI-775 护栏兜住；杠杆是"消费者按需导入"，不是拆文件 |
| 双语文案 | — | **不值得** | 这是产品要求，不是复杂度 |
| `.changeset` 流程 | — | **不值得** | 流程成本，不产生结构债 |
| `io-seam-registry` | — | **不值得（单独判断）** | 它是护栏，不是债；只有"为了过关而注册"才是债 |

### 第一步

只做上面两行标"值得"的：配置校验（计划内 3A）+ UI validators 生成化（B2 探针）。
其余标"部分值得"的，只加**新增限制**，不迁移存量。

### 怎么衡量

| 指标 | 基线 | 目标 |
| --- | --- | --- |
| "同一事实的第二份真相"处数 | 配置层 7 个构造点；UI 层约 30 个重建型 validator | 配置层 0；UI 层 0（生成化后只剩 schema） |
| 新增字段的必改点数 | core 4 处 / 前端 2 处 | core 2 处（类型 + schema）/ 前端 1 处 |
| 结构债清单条目数 | 本表 7 行 | 只减不增：任何新增条目必须先有复发证据 |

## 4. 三者之间的关系（一句话版）

- **A** 是"有 bug 时要看得见"——本计划已经覆盖，继续按批次走即可。
- **B** 是"没 bug 时改得动"——唯一有量化杠杆的是**测试反查**与 **validators 生成化**，其余（拆包、拆文件）不产生可测收益。
- **C** 只还"已复发"的债——本表 7 行里只有 2 行够格。

**建议 Owner 的决策方式**：
1. A 继续（已在执行）。
2. B 先只开 B1（1 人日，立刻可度量），B2 等 B1 的回放基线出来再决定。
3. C 不另开线，只跟随 A/B 顺带还那 2 行。

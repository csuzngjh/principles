# PD 典型案例库（Case Studies）

这里收集 Principles Disciple（PD）在真实 Agent 协作中的典型 Pain、Owner 纠错、原则生成、治理决策和后续行为验证，供产品普及、技术交流、文章、演示和用户研究使用。

**核心约定：一个案例不是一条宣传文案，而是一条可追溯的证据链。** 不以测试通过、原则生成、Reviewer 自评或 Prompt 投递来冒充“Agent 已学会”；必须有独立的新任务行为证据，才可宣称行为改善。

## 案例入库标准

1. **真实事件**：标明 Pain 来源是自动发现、手工录入还是其他渠道；区分原始证据和 Owner 陈述。
2. **清楚冲突**：说明任务目标、Agent 实际行动、Owner 的预期及偏差；不编造 Agent 的内心动机或原始对话。
3. **可追溯链路**：尽可能记录 Pain ID、关键提交/PR、诊断、候选、最终原则、审批及激活渠道。
4. **证据分层**：严格区分“生成”“批准”“投递尝试”“真实应用”“行为结果”；缺失即写“未验证”。
5. **可迁移价值**：说明从具体错误抽象出的行为准则，以及适用范围与误伤风险。
6. **公开安全**：不得提交私有轨迹、用户照片、凭据、数据库或未经脱敏的对话；公开前核对相关项目与参与者的信息发布边界。

## 案例状态

- **素材收集**：有问题线索，事实与来源尚待确认。
- **事件已核实**：已核对原始行为或可公开证据；不意味着诊断正确。
- **原则已激活 / 效果待验证**：存在原则审批或激活记录，但没有有效的后续行为对照。
- **行为改善已验证**：有新的独立任务、可复核的行为轨迹及适当对照；同时报告失败与负面影响。
- **公开发布就绪**：已经完成证据、措辞、隐私与演示素材检查。

## 推荐使用方式

每个案例独立放在一个稳定的英文 slug 目录；用 [CASE_TEMPLATE.md](CASE_TEMPLATE.md) 建立新案例。对外传播可以使用有吸引力的标题，但正文的技术事实、数字和效果声明必须与证据一致。可以将阅读版故事、演示脚本和复现实验记录逐步补充到案例目录，避免先堆模板和空目录。

> PD 的产品目标是 Owner 治理的 Agent 行为内化。原则进入 Prompt 并不自动证明 Agent 的未来行为已经改变。

## 第一部分：AI 系统的下一个边界 —— 我们正站在哪里

### 智能载体的迁移轨迹

观察 AI 系统过去几年的演化，会发现一个隐藏规律：

> **智能的载体，正在从"模型内部"不断向"模型外部"迁移。**

迁移轨迹大致是这样的：

```
模型参数 → 工具调用 → 系统提示词 → 上下文工程 → Skill 工程 → Harness 工程 → ?
```

每一次外延，都在扩张"智能产生的物理基底"。早期我们以为智能就在模型权重里；现在我们知道，智能是**模型 + 它能调用的工具 + 它的上下文 + 它的执行框架**共同涌现的产物。

### 下一个边界：三层叠加

我的判断是，下一次跃迁不是单一边界，而是三层同时出现：

1. **多智能体协作层**
   单个 agent 已经摸到天花板。下一次跃升来自 agent 之间的**契约、市场、组织协议**。当多个 agent 需要协调时，问题不再是"模型够不够强"，而是"它们怎么互相信任、怎么分工、怎么仲裁分歧"。

2. **环境协同进化层**
   AI 不再只是适应环境，而开始**重塑环境**。IDE、操作系统、CI 流水线都在被 AI 改写。这是双向反馈的真正开始——环境塑造 AI，AI 反过来塑造环境。

3. **制度嵌入层**
   AI 成为组织规则的一部分，而不只是工具。法务流程、合规检查、绩效评估开始内嵌 AI 决策。这意味着 AI 开始承担**制度性责任**。

更长远（5–10 年），最有趣的边界是**自我演化的 Harness**——agent 不仅修改自己的 prompt 和 skill，还开始修改自己的执行框架本身。

> **PD 已经在做这件事，只是把它压缩在"原则"这一条窄通道里。**

### 应该用什么思维去看

单一学科已经不够了。一个工具箱建议：

| 学科 | 提供的核心概念 | 解释什么 |
|------|--------------|---------|
| **控制论** | 必要多样性定律（Ashby） | 控制器的多样性必须 ≥ 被控对象的多样性。这一句话就解释了为什么上下文窗口决定了 agent 复杂度上限 |
| **生态学** | 生态位、演替、承载力 | 多 agent 系统就是生态系统 |
| **机制设计**（经济学）| 激励兼容、信息揭示 | 当 agent 之间需要协调，谁愿意诚实报告、谁愿意配合 |
| **演化生物学** | 选择压力、适应度地形 | PD 的"原则演化"本质上是**拉马克式**的——后天获得性遗传，比达尔文式快几个数量级 |

但比方法更关键的，是**视角切换**：

> **把 AI 系统当生态系统看，不当程序看。**
>
> 程序的单位是"函数"，生态系统的单位是"反馈回路"。

这次切换是 SD 模型文档悄悄完成的最重要的事，比任何一条 Linear issue 都重要。

## 第二部分：PD 的本质 —— 四个元素 + 一个回路

剥开所有技术层（数据库、CLI、Hook、Plugin、Manifest……），PD 的核心元素有四个：

| 元素 | 角色 | 类比 |
|------|------|------|
| **行为证据（Pain Evidence）** | 输入信号 | 拥有者认为值得改变的反复摩擦、纠正、风险接近或行为偏差 |
| **原则（Principle）** | 可审查政策 | 针对相似未来情境的行为建议或约束 |
| **拥有者（Owner）** | 价值判断与风险责任人 | 决定什么值得内化、以何种强度激活、何时撤回 |
| **行为（Performance）** | 可观察输出 | agent 在后续相似任务中实际怎么做 |

核心回路只有一个：

> **行为证据 → 反思 → 原则提案 → 拥有者审批与通道选择 → 行为修正 → 新证据**

`Pain` 是当前代码中的技术名词，但它不等于“每一次工具错误”。如果一次事件不体现拥有者重视的行为模式，它就不应该自动推动一条新原则。

### 这个回路不是新东西

它是 Donald Schön 在 1983 年提出的**"反思性实践者循环"**（Reflective Practitioner Loop），被搬到了 agent 的运行时。

PD 真正在做的事情，是把**人类心理学层面的反思与审议过程**，工程化到一个可观察、可回滚的系统里。系统可以持续运行，但“什么是更好行为”的决定不能从拥有者手里移走。

### 但是——有形式不等于有功能

一个回路看起来闭合（痛苦进来，原则出去），不代表它真的闭合（原则真的减少了痛苦）。

这是早期叙事的根本性弱点：**假设了闭环，但没有先证明用户能看到行为改变。**
MVP 的第一步不是建立因果指标，而是证明：**拥有者审批的一条原则，能通过可回滚通道在后续可比场景中产生可观察的行为变化。**
Attribution 则是未来在真实使用数据足够时，把“看见变化”进一步升级为“谨慎测量作用”的机制。

### 主要杠杆点（用非技术语言）

按当前阶段排序：

1. **拥有者能理解并控制原则的激活**
   没有人审与回滚，PD 只是另一个不可控自动化系统。这是 PRODUCT_IDENTITY 的产品锚点，不可让位。
2. **agent 能感知到拥有者关心的失败类型**
   行为证据是回路输入端。如果只有"工具调用失败"被感知到，拥有者再勤奋也无法治理她在意但 agent 看不见的失败模式。当前 PD 的痛苦感知层比文档描述窄得多——详见姊妹篇 [`PD_Pain_Signal_Audit.md`](./PD_Pain_Signal_Audit.md)。
3. **从真实证据到可观察行为改变**
   MVP 必须先跑通一条客户能看见、能复现、能否决的链路。
4. **从"软"到"硬"的可控内化**
   对已批准的行为约束，使用 prompt 或 RuleHost 等可回滚通道。
5. **测量长期有效性（Attribution，post-MVP）**
   只有真实客户数据足够后，才值得投资因果归因与自动清理。

### 当前架构想达成的系统行为

**一个二阶控制系统**——不仅控制 agent 行为，还控制"控制本身"是否有效。

野心很大。

### 它可靠吗？

诚实地说：**概念上扎实，工程上脆弱。**

脆弱在三处：

- Attribution 需要稳定的 painId 分类体系，但生产中 painId 会漂移很快。
- PRRR 在小工作区里统计噪声大，容易出现"看起来无效但其实是样本不够"。
- "原则有效性"和"agent 整体能力提升"很难分离——你怎么知道 agent 变好是因为这条原则，还是因为别的？

这就是为什么 ADR-0014 把 v2.0 的 Attribution 路径推迟到 MVP 之后。**技术上对，但商业上得先证明 PD 的基本叙事能让真实用户买单。** 这个判断是对的。

## 第三部分：极简模型 —— 拨云见月

### 一句话定义 PD

> **PD 是一个由拥有者治理的行为政策编译与部署系统。**

它把真实工作中的反复摩擦、明确纠正和风险接近，编译成可以审查的原则提案；由拥有者选择是否部署以及部署到什么行为通道；再在后续任务中观察变化。

“有记忆的恒温器”仍可解释反馈回路，但不能指导产品边界：agent 面对的是开放情境，什么叫“更好行为”也必须由拥有者判断，而不是系统自动认定。

真正的问题是：**被拥有者批准部署的原则，是否在相似的后续情境中改变了行为，而且这种改变是否符合拥有者期待？**

### 最简的图

```text
[行为证据] -> [模式诊断] -> [原则提案] -> [拥有者审批]
                                               |
                              prompt / RuleHost / defer_archive
                                               |
                                               v
                                      [后续可观察行为]

Post-MVP only: 真实数据充分后，再用 Attribution / PRRR 辅助评估长期有效性。
```

**这就是 PD 的全部。**

其他所有 Linear issue、ADR、代码、文档，都是这张图的工程化具现。

### 一个判断标尺

当你怀疑某个新功能是不是必要时，问一句：

> **"它让拥有者治理行为原则的哪一个环节变得更可用、更可观察或更可回滚？"**

不在图上的，多半就是 ADR-0014 警告的"维护者驱动的完整性焦虑"。

## 第四部分：两个核心公式的白话解读

SD 模型文档里那两个公式看起来吓人，其实非常朴素。把数学符号去掉，换成日常画面就清楚了。

### 公式 1：痛苦的演化

```
痛苦(t+1) = 痛苦(t) − 有效率 × 原则数(t) + 探索(t)
```

把它想象成一个**水池**：

- **水池里的水位 = 当前的"痛苦总量"**（agent 现在还在反复犯错的那些事）
- **每个时刻有水流出（减少痛苦）**：因为 agent 已经学到的原则在帮它避开旧坑
- **同时有水流进（增加痛苦）**：因为 agent 又去尝试了新的、更难的事，遇到了新的坑

逐项翻译：

| 符号 | 通俗说法 |
|------|---------|
| 痛苦(t) | 今天 agent 还在踩的坑 |
| 原则数(t) | 今天 agent 已经学到的"做事的道理" |
| 有效率 | 这些道理里，**真正管用的比例**（不是所有原则都有效） |
| 有效率 × 原则数 | 真正在帮 agent 避坑的"有用原则数" |
| 探索(t) | agent 今天去尝试的新挑战带来的新麻烦 |

整个公式说的就是：

> **明天的痛苦 = 今天的痛苦 − 有用原则帮你避免的那部分 + 你尝试新事物带来的新痛苦**

#### 公式 1 的真正洞察：在"有效率"这个乘数

如果你只看"原则数"，会得出"原则越多越好"的错误结论。但乘上有效率之后：

- 假如有效率是 0.2，你哪怕有 100 条原则，实际只有 20 条在帮你
- 如果有效率是 0.8，你只有 30 条原则，实际有 24 条在帮你

> **少而精胜过多而杂。**

这就是 v1.0 没看清、v2.0 拼命想看清的事：**没有对"有效率"的测量，原则数本身没有意义。**

### 公式 2：原则数的演化

```
原则数(t+1) = 原则数(t) + 诊断率 × 痛苦(t) − 归档率 × 无效原则(t)
```

还是水池的画面，但这次水池里装的是**原则**：

- **进水**：今天发生的痛苦越多，诊断引擎越忙，生成的原则就越多。
- **出水**：经过验证发现没用的原则，被自动归档（删除）。

公式说的是：

> **明天的原则库 = 今天的原则库 + 痛苦带来的新原则 − 被证明没用的原则**

#### 公式 2 的真正洞察：两个流量的赛跑

| 情形 | 结果 |
|------|------|
| 诊断速度 > 归档速度 | 原则库不断膨胀 → 上下文压力爆炸 → agent 反而变笨。这就是 B1 阻尼回路在描述的灾难 |
| 归档速度 > 诊断速度 | 原则库萎缩 → agent 失去记忆 → 永远学不会 |
| 两个速度匹配，且淘汰精准度高 | 系统进入良性循环 |

### 两个公式连起来的故事

> **痛苦推动原则增长，原则消减痛苦，无效原则被淘汰。**
>
> 这是一个有自我清洁机制的学习循环。

但有个**隐藏前提**：**"无效原则"得能被识别。**

在 MVP 阶段，谁来识别？首先是拥有者：通过审批、拒绝、回滚和真实使用反馈判断原则是否值得保留。

当系统积累了足够真实数据，PRRR 或其他 attribution 指标才可能辅助这个判断，减少长期人工成本。

所以这两个公式描述的是长期系统风险：原则不能只增不减。但它们不证明 PRRR 是 MVP 前置项，也不授权当前实现自动归因或自动清理。

## 第五部分：PRRR 北极星指标 —— 设计、含义、软肋、替代方案

> **阶段边界**：本部分描述 post-MVP 候选度量方法。当前 MVP 的成功标准是 `demonstrated behavior change`：拥有者能审批一条原则，并在后续相似场景中观察到更符合预期的行为。除非 [post-mvp-conditional-roadmap.md](../plans/post-mvp-conditional-roadmap.md) 的触发条件满足，不得据本节派发 Attribution / PRRR 实施工单。

### 5.1 字面意思

PRRR = Pain Recurrence Reduction Rate = **痛苦复发减少率**

```
PRRR = 1 − ( 原则启用后那段时间，同类痛苦发生的次数
              ──────────────────────────────────────────
                原则启用前那段时间，同类痛苦发生的次数 )
```

### 5.2 一个具体例子

假设 agent 反复犯一个错：每次写完代码忘记跑测试。

- 启用某条原则前的 100 次工具调用里，这种错发生了 10 次。
- 启用某条原则后的 100 次工具调用里，这种错发生了 2 次。

那么 **PRRR = 1 − (2 / 10) = 0.8**，意思是这条原则减少了 80% 的同类痛苦。

### 5.3 PRRR 的取值范围

| PRRR 值 | 含义 |
|---------|------|
| 接近 1 | 原则很有效，几乎杜绝了同类错误 |
| 接近 0 | 原则没什么用，痛苦照旧 |
| 负数 | 原则反而让事情变糟（可能引入了副作用） |

### 5.4 PRRR 代表了什么 —— 三层含义

**第一层（表面）**：一个原则有多大程度上"做到了它声称要做的事"。

**第二层（系统视角）**：把"agent 是否在学习"这件玄学问题，变成了**可以被数字回答的问题**。这是 PD 区别于其他 agent 框架的关键——大多数项目卡在"我们让 agent 有记忆了"，但回答不了"这个记忆有没有真正改变行为"。

**第三层（哲学视角）**：它**重新定义了"学习"**。在 PRRR 框架下：

> **学习 = 行为改变 = 同类失败的减少。**
>
> 不是"知道了什么"，而是"不再犯什么"。

这继承了行为主义心理学的传统，也契合 Dalio 在《原则》里的核心观点：**原则的价值不在于被记住，在于被自动执行。**

### 5.5 为什么这样设计 —— 四个考量

1. **前后比较**：度量的是"原则启用之后"的同类现象变化，而不是仅看原则是否被加载。它提供效果线索，但本身不证明干净因果。
2. **同类比较**：用同一类 painId 在启用前后做对比，减少部分混杂影响；多原则并行、分类漂移和环境变化仍可能破坏归因。
3. **可累加**：每条原则有自己的 PRRR，可以排序、剪枝、推荐。
4. **可证伪**：PRRR < 0 是明确的"系统说错了"信号，触发自动归档。一个无法被证伪的指标在工程上是负担。

### 5.6 PRRR 的软肋 —— 诚实的承认

PRRR 设计得很巧妙，但它有几个内在弱点：

| 软肋 | 含义 |
|------|------|
| **因果分配问题** | 当多条原则同时启用，某个痛苦减少了，到底是谁的功劳？PRRR 把功劳全算给"derivedFromPainIds 匹配的那条"，但实际上可能是另一条相邻原则起了作用。这是经济学里的"归因问题"，没有干净解 |
| **painId 漂移** | PRRR 假设"同类痛苦"是稳定的分类。但实际上 painId 体系本身在演化——昨天叫"forgot_to_run_tests"，今天可能被细分成"forgot_unit_tests"和"forgot_integration_tests"。一旦分类变了，前后窗口就不可比 |
| **小样本噪声** | 在小工作区，100 次工具调用里某类痛苦可能本来就只发生 1–2 次。这种数量级下，PRRR 从 1.0 跳到 -1.0 都可能是纯噪声 |
| **负面外部性看不见** | 一条原则可能在它"声称解决"的 painId 上 PRRR=0.9，但同时让 agent 变得过分谨慎，在另一个 painId 上 PRRR 变成 -0.5。**单条 PRRR 看不到这种侧损** |
| **探索惩罚** | PRRR 偏向于让 agent "保守"——尝试新事物会引入不在 derivedFromPainIds 范围内的新痛苦，这些新痛苦在 PRRR 体系下找不到对应原则负责，可能反而抑制 agent 探索复杂任务。这违反了 R1 飞轮的初衷 |

### 5.7 有没有更好的指标 —— 三层候选

#### 候选 A：复合化的 PRRR（短期改进）

不改 PRRR 的本质，但加几个补丁：

- **Net-PRRR**：这条原则带来的同类痛苦减少 − 它带来的其他类痛苦增加。捕捉副作用。
- **Bayesian-PRRR**：给 PRRR 加上置信区间，小样本时拒绝下定论。
- **Cohort-PRRR**：在多个工作区平均化，减少单一工作区的偏差。

> 低成本、高回报的改进，v2.0 重启时应该考虑。

#### 候选 B：Time-to-Recovery（中期视角）

不看"痛苦减少多少"，而看"**同类痛苦再次发生时，agent 多快恢复**"。

举例：原则启用前，agent 犯了同类错之后平均要 5 个工具调用才能修好；启用后只需要 1 次就纠正。

这个指标比 PRRR 更接近"学习"的本质：

> **学习不是"再也不犯错"，而是"犯错之后修复得更快"。**

它对探索友好，因为允许犯错。

#### 候选 C：Information-Theoretic 北极星（长期视角）

最有野心的一种思路：把 agent 整体看作一个**预测系统**，度量它对未来工具调用结果的**预测准确度**或**意外度（surprise）**的下降。

公式上类似：

```
学习增益 = H(行为 | 上次会话) − H(行为 | 这次会话)
```

H 是信息熵。意思是：经过一段时间的演化，agent 在面对相同情境时的行为变得更确定（信息熵下降），说明它真的"内化"了什么。

**好处**：

- 不依赖 painId 分类是否稳定。
- 自动捕捉所有维度的学习，包括 PRRR 看不见的隐性进步。
- 与多智能体场景天然兼容。

**坏处**：

- 实现复杂度高，需要 trajectory 级建模。
- 不直观，难向非技术利益方解释。

### 5.8 推荐演化路径

| 阶段 | 主指标 | 理由 |
|------|--------|------|
| **MVP 当前** | 拥有者观察的可复现行为变化 | 在没有外部样本时先证明产品闭环可用 |
| **满足重启条件后** | PRRR + Net-PRRR + Bayesian 平滑 | 有真实数据后再谨慎引入长期效果判断 |
| **中期**（产品稳定后）| 引入 Time-to-Recovery 作为补充 | 解决探索惩罚问题，让产品叙事从"agent 不再犯错"升级到"agent 自我修复更快"——后者是更深的护城河 |
| **长期**（行业领先后）| 研究信息论指标 | 当其他厂商还在比谁的 prompt 库大、谁的 memory 长，PD 已经在比"谁的 agent 学习速率更快" |

这就是 v1.0 故事 → v2.0 工程 → v3.0 范式的完整演化路径。

## 第六部分：作为拥有者，你只需要看的四件事

技术细节再多，作为项目拥有者，你只需要持续盯着四个问题：

### Q1：我反复指出的行为偏差，agent 在相似场景中是否改变？

如果没有 → PD 的核心承诺没兑现。

### Q2：我能否看懂、批准、拒绝并撤回一条原则？

如果不能 → PD 不是拥有者治理系统，只是后台自动化。

### Q3：在原则激活后，我是否能看到可比任务中的行为证据？

如果不能 → 现在还不能声称它产生了价值。

### Q4：PD 看见的"痛苦"，覆盖了我真正在意的失败吗？

如果 PD 学到的原则永远围绕"工具调用更安全"，而你真正头疼的是"agent 跑偏目标"或"agent 反复忽略测试"——这是一个**值得追查的信号**：可能是感知层覆盖不到、可能是诊断器把它误归类、也可能是拥有者从未把这类失败录入 manual pain。具体根因需要拥有者结合 [`PD_Pain_Signal_Audit.md`](./PD_Pain_Signal_Audit.md) 的事实图来定位，**不要直接断定是"感知带宽不够"**。

---

> **这四个问题不需要技术能力回答。它们是 MVP 的价值判断锚点。PRRR 是未来可选的量化辅助，而不是当前回答这些问题的前置条件。**

把这四个问题刻在脑子里，胜过读 100 页架构文档。

## 第七部分：感知带宽 —— 一个值得拥有者关注的分析维度

> 这一节是这份伴读本的延伸思考，不是产品路线图。完整的事实图与改进框架在姊妹篇 [`PD_Pain_Signal_Audit.md`](./PD_Pain_Signal_Audit.md)。

### 7.1 一个被低估的事实

LLM 不具备"痛觉神经"。

人类的痛觉是天生的、自动的、无法关闭的——手碰到火立刻收回，不需要专门设计一个"火检测器"。但 LLM / Agent 不同：它必须由外部系统**显式构造**痛觉。**这意味着"agent 能看见什么样的失败"是一个产品设计选择，而不是一个自然事实**。

### 7.2 一个分析视角（不是产品定位）

> ⚠️ 下面这句话是**分析视角**，不是 PD 产品定位。PD 的产品定位见 [`PRODUCT_IDENTITY.md`](../../PRODUCT_IDENTITY.md)：拥有者治理的行为内化系统。

> **痛苦信号的多样性，本质上是 agent 对世界的感知带宽。**
>
> **拥有者能治理的行为领域，受限于 agent 感知层覆盖的痛苦类型。**

这不是"agent 自主感知 → agent 自主进化"。它是说：

- 如果 agent 永远只能感知到工具调用失败，那么**拥有者再勤奋审批，也无法治理她在意的"目标偏离 / 反复返工 / 用户挫败"等领域**——因为这些痛苦从来没有进入诊断器和拥有者的视野。
- 反过来，扩大 agent 的感知层，**不是让 agent 自动学到更多**，而是让**拥有者拥有更完整的素材去做产品判断**。

### 7.3 三种感知 → 三种治理领域（修辞性映射）

> ⚠️ **disclaimer**：下面这个三段映射是**修辞性的**，不是命题论证。"感知到 → 治理到"是必要不充分关系——感知是治理的前置，但拥有者要不要把某类痛苦变成原则、用什么通道部署、何时回滚，仍然是产品判断。

```
agent 只能感知到工具失败                   → 拥有者只能治理工具调用边界
agent 能感知到目标偏离                     → 拥有者**有机会**治理目标对齐方向
agent 能感知到用户反复纠正                 → 拥有者**有机会**治理用户期待对齐
```

"有机会"是关键词。后续是否真的产生可观察的行为变化，仍然取决于伴读本第六部分的四个问题（特别是 Q1 / Q3）。

### 7.4 什么时候应该担心感知带宽

> ⚠️ 这是**诊断思路的候选维度**，不是工程优先级指令。

如果你（拥有者）发现：

- PD 学到的原则月复一月围绕同一个维度（例如总是"工具调用更安全"）
- 你自己心里记的"agent 反复犯但 PD 没学到"的失败类型在增加
- 你做了大量 manual `pd pain record` 但其他通道几乎不产 pain

——那么瓶颈**很可能**在感知层，不在诊断器智能。这时值得把"扩展某一类感知"作为拥有者治理决策的候选项之一，对照 PRODUCT_IDENTITY Decision Gate 的四个问题逐项评估。

### 7.5 一个值得验证的猜想（不是行业断言）

> ⚠️ 我之前在这里写了"AI Agent 行业下一波差异化在 sensing layer，大家都假装解决了"。**这是无证据的同行批评，撤回**。

只留一个**待验证的猜想**：当前 AI Agent 公开讨论中，"agent 该如何感知自己什么不对"这一层关注度低于"模型规模 / prompt / 工具数"。如果这个观察成立，PD 投资感知层可能形成差异化；如果不成立，PD 的差异化仍然在拥有者治理这条主线。两种情况下，下一步动作都应回到 PRODUCT_IDENTITY，**不依赖"行业都不做 sensing"这个外部假设**。

### 7.6 想再深一层？

## 第八部分：系统动力学 × AI 系统 —— 一门正在诞生的交叉学科

### 8.1 主流盲区

AI 工程界的主流仍是"算法思维"——把 AI 当函数：

```
input → model → output
```

这种思维下，**模型变大、prompt 变好、工具变多**就是进步。

但它解释不了：

- 为什么"原则越多 agent 反而越笨"
- 为什么 multi-agent 系统会陷入死锁
- 为什么 agent 会自己跑偏目标

> **这些都是反馈系统问题，不是函数问题。**

### 8.2 系统动力学带来的三个洞察

1. **AI 系统是控制系统，不是算法。**
   分析单位是回路，不是函数。
2. **学习是反馈回路，不是过程。**
   没有效果度量的"学习"只是模式生成。
3. **复杂 AI 系统最大的风险不是恶意，而是失谐（incoherence）。**
   多个回路缺乏阻尼 → 振荡、漂移、最终崩溃。

### 8.3 但纯 SD 也有盲区

SD 学者习惯用方程描述慢变量（人口、库存、资金），而 AI 系统的"变量"本身是**高维语义对象**（一条原则、一段 prompt、一次 trajectory）。

这要求 SD 方法和**符号 / 语义建模**结合——这一步还没人系统化做出来。

### 8.4 一个新学科的雏形：AI Systems Engineering

我会把这个交叉领域命名为 **AI 系统工程学（AI Systems Engineering）**。

它应该是 ML 和 SE 之外的第三门学科：

| 学科 | 研究对象 |
|------|---------|
| Machine Learning | 模型怎么训练 |
| Software Engineering | 代码怎么组织 |
| **AI Systems Engineering** | **多反馈、多 agent、人机混合系统的动力学性质** |

### 8.5 PD 项目的真正历史价值

不在于做了一个工具，而在于它用真实工程实践回答一个理论问题：

> **"agent 能否通过观察自己的失败而变得更好？"**

- v1.0 给了一个浪漫的答案。
- v2.0 加了一个工程师的诚实条件：**"只有当我们能测量'变得更好'的时候。"**

这个诚实条件，是 PD 区别于市面上 99% "memory layer / agent learning" 项目的关键。

> **市面上大部分项目都在卖 v1.0 的故事，没有人愿意接 v2.0 的工程债。**
>
> **这恰恰是 PD 的护城河——前提是 ADR-0014 之后，你还能活到去把 v2.0 兑现的那一天。**

## 结语

> **拨云见月，PD 的本质是：**
>
> **一个由拥有者治理的行为内化循环：从重要行为证据出发，把经审查的原则部署到可回滚通道，并观察下一次行为是否更符合期待。**
>
> 这个循环要真正运转，agent 必须能感知到值得拥有者治理的痛苦。**感知带宽决定的是拥有者的治理视野**——视野多宽，拥有者能治理的领域就多宽。详见 [`PD_Pain_Signal_Audit.md`](./PD_Pain_Signal_Audit.md)。
>
> Attribution 与 PRRR 可以在真实用户数据足够后让这个循环更诚实，但它们不能代替拥有者，也不能阻塞 MVP 的第一次真实验证。
>
> 缺少拥有者，它会变成失控的自动化；缺少可观察行为，它只是原则仓库；缺少足够的感知层覆盖，它就只能治理感知到的那一小片领域。

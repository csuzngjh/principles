## 产品定义锚点

PD 的稳定产品定义以仓库根目录的 PRODUCT_IDENTITY.md 为准：

> PD 是由拥有者治理的行为原则内化系统，不是任务执行引擎、通用记忆层或通用工具修复框架。

这句话是本文所有推理的起点。

PD 不是让 Agent 自动变聪明的魔法系统。
PD 不是把所有经验都塞进 memory 的知识仓库。
PD 不是自动修复工具调用错误的补丁框架。
PD 也不是让 Agent 自己决定自己应该成为什么样的自主进化系统。

PD 真正做的是：

> 从真实工作中的重要行为证据出发，把反复出现的行为偏差压缩成可审查原则；由拥有者判断是否值得内化；再通过可回滚通道影响 Agent 未来行为。

如果只能记住一句话：

> **PD 是一个由拥有者治理的 Agent 行为内化回路。**

# 第一部分：AI 系统的下一个边界 —— 我们正站在哪里

过去几年，AI 系统的演化有一个隐藏规律：

> 智能的载体，正在从“模型内部”不断向“模型外部”迁移。

大致可以这样看：

```text
模型参数
→ 工具调用
→ 系统提示词
→ 上下文工程
→ Skill 工程
→ Harness 工程
→ 组织协议 / 治理机制
```

早期我们以为智能主要存在于模型权重里。
后来我们发现，模型能调用什么工具、拿到什么上下文、遵守什么系统指令、嵌入什么执行框架，都会显著改变它的行为能力。

也就是说，现代 Agent 的智能不是单独由模型产生的，而是由：

```text
模型 + 工具 + 上下文 + Skill + Harness + 治理机制
```

共同涌现出来的。

## 下一个边界：不是更长的 prompt，而是更好的行为治理

当 Agent 只能回答问题时，prompt 很重要。
当 Agent 能修改代码、调用工具、操作文件、影响真实工作流时，仅靠 prompt 就不够了。

问题会从：

> “我怎样让它完成这个任务？”

变成：

> “我怎样让它在反复工作中形成稳定、可控、符合我期待的行为方式？”

这正是 PD 所处的位置。

PD 并不是去替代 IDE、Agent 框架、工具调用层，也不是直接训练一个新模型。PD 站在更窄但更关键的位置上：

> 它试图把拥有者认可的行为原则，逐步内化到 Agent 的未来行为里。

## 谨慎修正：PD 不是自我修改 Harness

更长远看，AI 系统可能会走向“自我演化的 Harness”：Agent 不只是修改自己的 prompt 和 skill，还能修改自己的执行框架。

但当前 PD 不应该被描述为“已经在做自我演化 Harness”。

更准确的说法是：

> PD 在更窄、更安全的通道里，探索 Agent 行为原则的可治理演化。

也就是说，PD 不是让 Agent 自己改造自己，而是让 Agent 从真实工作中提出行为改进线索，再由拥有者决定哪些原则可以进入未来行为。

这条边界非常重要。

一旦把 PD 说成“Agent 自我演化系统”，就会误伤它最核心的产品定位：Owner Governance。

PD 的护城河不在于“自动进化”，而在于：

> 让 Agent 的行为演化始终处在拥有者可理解、可审查、可撤回的治理框架中。

# 第二部分：PD 的本质 —— 不是 memory，而是行为内化

很多人第一次看到 PD，可能会把它归类为以下几种东西：

* Agent memory layer
* prompt 管理工具
* rule system
* workflow engine
* 自动反思框架
* 工具错误修复系统

这些说法都只碰到了 PD 的某个侧面，但都没有抓住核心。

## PD 不是 memory

Memory 关注的是：

> 系统记住了什么。

PD 关注的是：

> 系统记住的东西，是否改变了未来行为。

如果一条原则被保存了，但后续相似任务中 Agent 仍然照旧犯错，那么它只是被存储了，并没有被内化。

所以 PD 的核心价值不在“记忆”，而在“行为改变”。

## PD 不是规则引擎

规则引擎通常关心：

> 当条件 A 出现时，执行动作 B。

但 PD 的原则不是普通规则。

原则更像是面向未来相似场景的行为判断框架：

```text
当面对类似情境时，Agent 应该优先考虑什么？
应该避免什么？
应该先确认什么？
什么情况下必须停下来询问 Owner？
什么改动范围是危险的？
什么证据不足以支持继续执行？
```

原则不是死板命令，而是可审查的行为政策。

## PD 不是任务执行引擎

任务执行引擎关心：

> 如何把一个任务做完。

PD 关心：

> Agent 在做任务的过程中，是否逐渐形成更符合拥有者期待的行为方式。

这两者差别很大。

一个任务完成了，不代表 Agent 学会了。
一个任务失败了，也不代表没有学习价值。
真正有价值的是：这次行为证据能否帮助未来的 Agent 少犯同类偏差，或者更快恢复。

## 更准确的定义

我会把 PD 抽象成：

> **PD 是一个以拥有者价值判断为最高控制源，把 Agent 运行中的重要行为偏差压缩成可审查原则，并通过可回滚行为通道影响未来 Agent 行为的语义控制系统。**

这句话拆开看：

* “拥有者价值判断”：什么是好行为，不能由 Agent 自己最终决定。
* “重要行为偏差”：不是所有错误都值得学习，只有治理上有意义的偏差才值得进入系统。
* “压缩成原则”：PD 不是保存原始日志，而是提炼可迁移的行为建议或约束。
* “可审查”：原则必须让 Owner 看得懂、改得动、否决得了。
* “可回滚”：原则不能成为永久污染源。
* “影响未来行为”：PD 的最终价值出口是行为变化，不是原则数量。

# 第三部分：核心模型 —— 七个对象与一个闭环

剥开数据库、CLI、Hook、Plugin、Manifest、Linear issue、ADR 这些工程细节，PD 可以抽象成七个核心对象。

---

## 1. Environment：任务环境

Environment 是 Agent 面对的外部世界，包括：

* 代码库
* issue
* 文件
* 工具
* 用户意图
* 项目规范
* 权限边界
* 上下文窗口
* 组织流程
* 其他 Agent

任务环境不是静态的。

Agent 越强，任务会越复杂。
任务越复杂，新的 pain 会出现。
新的 pain 出现，不一定说明系统变差，也可能说明 Agent 进入了更高难度的任务域。

所以 PD 不能假设：

> pain 应该单调下降。

更准确的判断是：

> 旧的、重复的、Owner 已经明确不接受的行为偏差，应该逐渐减少；新的探索性 pain 可以存在，但应该被理解、被分类、被治理。

---

## 2. Agent + Harness：被治理对象

PD 治理的不是裸模型，而是整个 Agent 运行系统：

```text
模型
+ system prompt
+ tools
+ skills
+ plugins
+ runtime harness
+ 当前上下文
+ 已激活原则
```

所以 PD 不是在训练一个模型，而是在调节一个 Agent 系统的行为倾向。

这也解释了为什么 PD 的原则不能只写成抽象鸡汤。

一条原则如果不能进入 Agent 的实际运行通道，就不会影响行为。

---

## 3. Pain Evidence：治理型误差信号

Pain 不等于 error。
Pain 不等于每一次工具调用失败。
Pain 不等于所有用户不满意。
Pain 也不等于“系统自动认为不对的事情”。

更准确地说：

> **Pain Evidence 是拥有者认为值得系统学习的行为偏差证据。**

它有几个特点：

1. 它必须来自真实行为，而不是凭空想象。
2. 它最好体现反复出现的模式，而不是孤立偶然事件。
3. 它应该和 Owner 的真实关切有关。
4. 它应该能推动未来行为改变，而不是只用于归档。

比如：

| 事件                 | 是否一定是 Pain | 原因         |
| ------------------ | ---------- | ---------- |
| 工具调用失败一次           | 不一定        | 可能只是外部环境问题 |
| Agent 反复忘记跑测试      | 很可能是       | 体现稳定行为偏差   |
| Agent 修改大范围文件却没先确认 | 很可能是       | 涉及风险边界     |
| 用户反复纠正同一类理解偏差      | 很可能是       | 体现目标对齐问题   |
| Agent 遇到未知问题主动探索失败 | 不一定        | 可能是有价值探索   |

Pain 的价值不在于“记录失败”，而在于给 Owner 提供治理材料。

---

## 4. Principle Candidate：语义压缩结果

原则不是普通规则，也不是普通记忆。

原则是从行为证据中压缩出来的、面向未来相似场景的行为约束、行为偏好或判断优先级。

一条高质量原则，至少应该回答：

```text
它来自什么证据？
它试图改变什么行为？
它适用于什么场景？
它不适用于什么场景？
它应该如何被激活？
它应该进入哪个通道？
它可能有什么副作用？
Owner 是否批准？
未来如何撤回？
```

如果原则没有这些元信息，原则库很容易退化成“高级 prompt 垃圾场”。

## 好原则的六个标准

| 标准  | 解释                       |
| --- | ------------------------ |
| 清楚  | Agent 和 Owner 都能理解       |
| 有边界 | 知道什么时候适用，什么时候不适用         |
| 有证据 | 能追溯到真实 pain 或 trajectory |
| 可执行 | 能改变下一次行为，不只是漂亮口号         |
| 可回滚 | 出现副作用时能撤回或降权             |
| 低冲突 | 不和已有原则产生严重矛盾             |

原则不是越多越好。
原则真正有价值的地方，是在正确场景中以正确强度影响行为。

---

## 5. Owner：价值函数与治理闸门

Owner 不是普通用户，也不是审批机器。

在 PD 模型里，Owner 是系统的价值判断源。

Owner 负责判断：

* 什么 pain 值得学习；
* 哪些行为偏差真的重要；
* 原则表达是否准确；
* 哪些原则可以部署；
* 部署到什么强度；
* 什么副作用不能接受；
* 什么时候应该回滚；
* 哪些边界不能让 Agent 自己决定。

所以 Owner 是 PD 的最高治理层。

这也是 PD 和“Agent 自动进化系统”的分界线：

> Agent 可以提出原则，但不能最终决定什么是更好行为。

没有 Owner，PD 会退化成失控自动化。
Owner 被架空，PD 就不再是 PD。

---

## 6. Deployment Channel：行为执行通道

原则只有进入某个行为通道，才可能影响未来 Agent。

常见通道可以分成几类：

| 通道                        |    强度 | 优点         | 风险             |
| ------------------------- | ----: | ---------- | -------------- |
| prompt hint               |     低 | 灵活、易撤回     | 容易被忽略          |
| skill / instruction       |     中 | 适合任务习惯     | 可能泛化过度         |
| RuleHost / guardrail      |     高 | 行为约束强      | 可能让 Agent 过度保守 |
| workflow / harness change |    很高 | 可改变系统动力学   | 风险最大，需要谨慎      |
| defer / archive           | 无直接影响 | 防止垃圾原则进入系统 | 可能错过有效学习       |

这里的关键问题不是：

> 原则有没有保存？

而是：

> 原则是否在正确场景，以正确强度，进入了正确通道？

一条好原则，如果部署通道错了，也可能造成坏行为。

---

## 7. Observable Behavior：可观察行为

这是 PD 的最终价值出口。

不是原则数量。
不是 pain 数量。
不是 proposal 数量。
不是 PRRR 曲线。
不是漂亮的反思报告。

而是：

> 在后续相似任务中，Agent 是否真的以更符合 Owner 期待的方式行动。

可观察行为变化可以包括：

| 维度                   | 例子          |
| -------------------- | ----------- |
| omission reduction   | 不再忘记跑测试     |
| planning improvement | 动手前先确认边界    |
| recovery speed       | 犯错后更快修正     |
| risk avoidance       | 不再大面积改动     |
| user-alignment       | 更少违背用户真实意图  |
| context discipline   | 更少丢失关键约束    |
| evidence discipline  | 更少凭空假设      |
| change discipline    | 更少无边界扩张修改范围 |

PD 的 MVP 不需要先证明复杂因果归因。
MVP 要先证明：

> Owner 批准的一条原则，能在后续相似任务中产生可复现、可观察、符合期待的行为变化。

---

## 一个闭环

七个对象连起来，就是 PD 的核心闭环：

```text
Environment 中发生任务
→ Agent + Harness 执行
→ 产生 Trajectory
→ Sensing 捕获 Pain Evidence
→ Diagnosis 生成 Principle Candidate
→ Owner 审查、修改、批准或拒绝
→ Principle 进入 Deployment Channel
→ 后续任务中影响 Observable Behavior
→ 新行为再次产生证据
```

再压缩一点：

```text
行为证据
→ 模式诊断
→ 原则提案
→ Owner 治理
→ 可回滚部署
→ 后续行为变化
→ 新证据
```

这就是 PD 的核心。

# 第四部分：三层结构 —— 运行层、反思层、治理层

PD 最好不要只看成一条线性流程，而要看成三层系统。

---

## 第一层：运行层

运行层负责完成任务。

```text
Task → Agent → Action → Result
```

这里关注的是：

* 工具调用是否成功；
* 文件是否正确修改；
* 测试是否执行；
* 用户请求是否完成；
* Agent 是否按照当前上下文行动。

运行层产生事实。

---

## 第二层：反思层

反思层负责从运行事实中提炼行为证据。

```text
Trajectory → Pain Evidence → Diagnosis → Principle Candidate
```

这里关注的是：

* 哪些行为值得学习；
* 是否存在反复模式；
* 偏差背后的行为机制是什么；
* 能否压缩成未来可用的原则；
* 原则是否有明确适用边界。

反思层产生解释。

---

## 第三层：治理层

治理层负责决定什么进入未来行为。

```text
Principle Candidate → Owner Decision → Deployment → Rollback / Archive
```

这里关注的是：

* Owner 是否理解这条原则；
* 是否批准；
* 是否修改；
* 是否拒绝；
* 应该进入什么通道；
* 何时回滚；
* 是否产生副作用。

治理层产生授权。

---

## 三层关系

一句话总结：

> **运行层产生事实，反思层产生解释，治理层产生授权。**

这句话是理解 PD 的关键。

PD 的原则不是“模型觉得对”。
PD 的原则也不是“系统自动总结出来就应该执行”。
PD 的原则应该是：

> 基于事实，由系统解释，经 Owner 授权，进入未来行为。

这就是 Owner-Governed Behavioral Internalization。

# 第五部分：系统动力学重建 —— 从库存模型到语义控制模型

早期用系统动力学看 PD，容易自然得到两个库存变量：

* 痛苦数量；
* 原则数量。

然后得到一个朴素模型：

```text
痛苦增加 → 原则增加
原则生效 → 痛苦减少
无效原则归档 → 原则库减负
```

这个模型有启发意义，但还不够准确。

原因是：

> pain 不是同质库存，principle 也不是同质库存。

一次工具调用失败、一次目标偏离、一次用户纠正、一次危险改动，它们不是同一种 pain。
一条清晰、有边界、可执行的原则，和一条抽象、空泛、难激活的原则，也不是同一种 principle。

所以 PD 不能只问：

> 有多少 pain？有多少原则？

而应该问：

> 什么类型的 pain 被看见了？
> 什么质量的原则被生成了？
> 原则有没有被正确激活？
> Owner 审得动吗？
> 后续行为真的变了吗？

---

## 五个更关键的状态变量

我会用五个变量来重建 PD 的系统模型。

---

## 1. Sensing Coverage：感知覆盖度

表示 PD 能看见哪些类型的行为偏差。

```text
S = {
  tool_failure,
  user_correction,
  goal_drift,
  repeated_rework,
  test_omission,
  permission_error,
  context_loss,
  risky_large_change,
  assumption_without_evidence,
  owner_manual_pain,
  ...
}
```

如果 sensing 太窄，PD 只能治理很窄的行为领域。

如果系统只能看见工具失败，那么它最多只能围绕工具调用生成原则。
如果系统看不见目标偏离，它就很难治理目标对齐。
如果系统看不见用户反复纠正，它就很难治理用户期待偏差。

所以更准确的说法是：

> **感知覆盖度限制了 Owner 可治理行为领域的上限。**

注意，是“限制上限”，不是“决定结果”。

感知到，只是治理的前置条件。
真正能否治理成功，还要看诊断质量、原则质量、Owner 审批、部署通道和后续行为反馈。

---

## 2. Principle Quality：原则质量

原则数量不是核心，原则质量才是核心。

一条原则的质量可以粗略理解为：

```text
Q(p) = clarity × scope_fit × evidence_strength × actionability × reversibility × conflict_safety
```

翻译成人话：

```text
原则质量
= 清晰度
× 场景适配度
× 证据强度
× 可执行性
× 可回滚性
× 冲突安全性
```

如果一条原则很抽象，比如：

> 做事要认真。

它几乎没有行为价值。

如果一条原则变成：

> 当需要修改超过 3 个文件，或改动跨越多个模块时，先向 Owner 汇报改动范围、风险点和验证计划，再执行大面积修改。

它就更可能改变行为。

---

## 3. Activation Precision：激活精度

很多原则系统失败，不是因为没有原则，而是因为原则激活错了。

常见问题包括：

* 该激活时没激活；
* 不该激活时乱激活；
* 一次激活太多原则；
* 原则挤爆上下文；
* 原则和当前任务不匹配；
* 原则被加载了，但 Agent 不知道怎么执行；
* 原则之间互相冲突。

所以，PD 真正优化的不是原则库大小，而是：

```text
A(P_approved, Context)
```

也就是：

> 在当前任务上下文里，正确原则是否以正确强度被激活。

可以把原则影响力粗略理解为：

```text
Principle Impact = Principle Quality × Activation Precision × Channel Strength
```

翻译成人话：

```text
原则影响力
= 原则本身好不好
× 激活得准不准
× 部署通道够不够合适
```

这比“有效率 × 原则数”更接近真实系统。

---

## 4. Owner Attention Budget：拥有者注意力预算

这是 PD 极容易被低估的变量。

Owner 是价值判断源，但 Owner 的注意力不是无限的。

如果系统每天生成 50 条原则提案，Owner 审不动。
如果每条原则都需要深度理解，Owner 会疲劳。
如果 Owner 疲劳后开始随手批准，原则库会被污染。
如果回滚成本太高，Owner 会失去治理意愿。
如果系统总是要求 Owner 决策，PD 会从“帮我治理 Agent”变成“给我制造管理负担”。

所以 PD 必须有注意力保护层。

可以把 Owner 负担粗略理解为：

```text
Owner Attention Load
= 提案数量
× 理解成本
× 决策复杂度
× 风险判断成本
× 回滚成本
```

PD 的目标不是让 Owner 审更多东西，而是让 Owner 审更少、更重要、更有杠杆的东西。

一个好的 PD 系统应该保护 Owner 的注意力，而不是消耗 Owner 的注意力。

---

## 5. Behavioral Delta：行为改变幅度

这是 PD 最核心的输出变量。

不是：

```text
原则数增加了多少
pain 数减少了多少
生成了多少报告
跑了多少 attribution
```

而是：

```text
后续相似任务中，Agent 的行为到底变了没有？
```

Behavioral Delta 可以拆成几类：

| 行为改变    | 例子              |
| ------- | --------------- |
| 更少遗漏    | 不再忘记测试、检查、确认    |
| 更好规划    | 动手前先理解边界        |
| 更快恢复    | 犯错后更快纠正         |
| 更稳风险控制  | 不再无授权大面积修改      |
| 更强证据意识  | 不再凭猜测下结论        |
| 更好用户对齐  | 更少偏离 Owner 真实意图 |
| 更强上下文纪律 | 更少忽略已有约束        |

PD 的核心承诺就是 Behavioral Delta。

没有行为变化，原则只是文本。
没有可观察行为，系统只是仓库。
没有 Owner 认可的行为变化，自动指标再漂亮也没有意义。

---

## 一个更准确的系统公式

如果非要用一个公式表达 PD 的核心逻辑，我不会写成“原则越多痛苦越少”，而会写成：

```text
未来行为质量
= Agent 基础能力
× 任务环境适配度
× 有效原则激活质量
× Owner 治理质量
− 原则债务
− 注意力损耗
− 通道失配
```

这不是工程计算公式，而是思维模型。

它提醒我们：

1. Agent 基础能力仍然重要，PD 不是万能的。
2. 任务环境越复杂，pain 可能越多。
3. 原则只有被正确激活才有用。
4. Owner 治理质量直接影响系统方向。
5. 原则会产生债务。
6. Owner 注意力会被消耗。
7. 部署通道错误会让好原则变坏。

再抽象一点：

```text
B(t+1) = f(
  B(t),
  E(t),
  A(P_approved, Context),
  G_owner,
  S_coverage,
  C_budget
)
```

其中：

| 符号         | 含义            |
| ---------- | ------------- |
| B(t)       | 当前 Agent 行为模式 |
| E(t)       | 当前任务环境        |
| P_approved | 已批准原则         |
| A(...)     | 原则激活函数        |
| G_owner    | Owner 治理质量    |
| S_coverage | 感知覆盖度         |
| C_budget   | 上下文与注意力预算     |

这比“痛苦水池”和“原则水池”复杂一点，但更接近 PD 的真实问题。

---

# 第六部分：五条关键反馈回路

从系统动力学角度看，PD 最重要的不是组件，而是反馈回路。

程序的单位是函数。
生态系统的单位是反馈回路。
PD 这种系统的单位，是“行为改变能否被治理性反馈闭合”。

下面这五条回路，基本决定了 PD 能不能长期健康运行。

---

## R1：行为内化飞轮

这是 PD 的主飞轮。

```text
重要 pain 被捕获
→ 诊断出行为模式
→ 生成原则提案
→ Owner 批准
→ 原则部署
→ Agent 行为改善
→ Owner 信任增加
→ Owner 更愿意提供高质量反馈
→ 捕获更高质量 pain
```

这条飞轮真正驱动的不是“自动化”，而是“信任”。

Owner 看见 Agent 行为真的变好了，才会愿意继续治理。
Owner 愿意治理，系统才有高质量价值判断。
高质量价值判断越多，原则越贴近真实工作。
原则越贴近真实工作，行为改变越明显。

所以 PD 的第一性问题不是：

> 如何自动生成更多原则？

而是：

> 如何让 Owner 尽快看见一条原则真的改变了后续行为？

---

## B1：原则债务阻尼回路

原则不是纯资产，也可能是债务。

```text
原则增加
→ 上下文压力增加
→ 原则冲突增加
→ Agent 行为变僵硬 / 变慢 / 变乱
→ Owner 回滚 / 限域 / 归档
→ 原则库恢复健康
```

原则债务常见表现：

* 原则越来越多，但 Agent 越来越犹豫；
* 原则之间互相冲突；
* 原则适用边界不清；
* 每次任务加载一堆无关原则；
* Agent 学会了“形式上遵守原则”，但任务质量下降；
* Owner 不再相信原则库。

所以 PD 必须有原则清理机制。

短期可以靠 Owner 审批、拒绝、回滚。
长期才需要 Attribution、PRRR、Net-PRRR、Bayesian 平滑等机制辅助判断。

MVP 阶段不要急着自动清理，但必须在架构上承认：

> 原则会产生债务。

---

## B2：过度保守回路

这是所有 pain-reduction 系统都会遇到的风险。

```text
pain 增加
→ 系统生成防错原则
→ Agent 更谨慎
→ 错误减少
→ 探索减少
→ 能力增长变慢
→ 新任务适应性下降
```

如果只奖励“少犯错”，Agent 可能学会“不探索”。
如果只追求 PRRR 上升，Agent 可能变得越来越保守。
如果每次失败都生成禁止性原则，系统会慢慢把 Agent 锁死。

这对 coding agent 尤其危险。

因为很多复杂任务本来就需要探索：

* 架构重构；
* 复杂 bug 排查；
* 新库迁移；
* 多文件协同修改；
* 性能优化；
* 未知错误定位。

一个完全不犯错的 Agent，可能只是一个不敢做复杂任务的 Agent。

所以 PD 需要区分：

```text
重复性低级错误
vs
有价值探索中的可恢复失败
```

PD 不应该消灭所有 pain。
PD 应该减少 Owner 不接受的重复性行为偏差，同时保留合理探索空间。

---

## R2：感知扩展飞轮

这是 PD 从“工具错误治理”走向“行为治理”的关键。

```text
Owner 发现“我在意的失败 PD 没看见”
→ 增加 manual pain / 新 hook / 新观察通道
→ sensing coverage 变宽
→ 诊断材料更完整
→ 原则更贴近真实痛点
→ 行为改善更明显
→ Owner 更清楚哪些 pain 值得系统化
```

这条飞轮说明：

感知层不是可有可无的辅助功能。
感知层决定了哪些行为偏差有机会进入治理流程。

如果 PD 只能看见工具调用失败，它就容易变成“工具使用原则系统”。
如果 PD 能看见目标偏离、用户纠正、反复返工、上下文丢失、未验证假设，它才有机会治理更深层的 Agent 行为。

但要注意：

> 扩大感知层不是为了让 Agent 自主进化，而是为了让 Owner 拥有更完整的治理材料。

这是 PD 的边界。

---

## B3：Owner 注意力过载回路

这条回路非常危险，也非常现实。

```text
pain 捕获变多
→ 原则提案变多
→ Owner 审批负担增加
→ 审批质量下降
→ 错误原则进入系统
→ Agent 行为变差
→ pain 更多
```

很多系统一开始看起来很智能，后来变成噪音制造机，就是因为没有控制这条回路。

PD 必须避免：

* 捕获太多低价值 pain；
* 生成太多低质量原则；
* 把所有事情都推给 Owner；
* 让 Owner 每天审一堆没有杠杆的提案；
* 把“治理”变成新的认知负担。

这也是为什么“注意力保护层”应该成为 PD 的重要设计思想。

Owner 是最高价值判断源，但 Owner 的注意力是稀缺资源。
越稀缺的资源，越应该被保护。

---

## R3：治理信任飞轮

这条回路和 R1 相似，但更偏产品体验。

```text
Owner 能看懂原则
→ Owner 愿意审批
→ 原则部署后行为变化可见
→ Owner 信任系统
→ Owner 愿意提供更明确反馈
→ 系统生成更好原则
→ Owner 更容易治理
```

反过来也有一个负向版本：

```text
原则看不懂
→ Owner 不愿审
→ 原则部署后效果不可见
→ Owner 不信任系统
→ Owner 不提供高质量反馈
→ 系统只能从低质量信号中猜
→ 原则更差
```

这说明 PD 的 UI / CLI / 文档体验不是边缘问题。

如果 Owner 看不懂原则，Owner Governance 就只是口号。
如果 Owner 看不到行为变化，Behavioral Internalization 就只是叙事。

---

# 第七部分：MVP 的最小可行闭环 —— 先证明行为改变

当前阶段，PD 不应该急着证明复杂因果归因。

MVP 最小可行闭环只有六步：

```text
1. 捕获一个 Owner 认可的重要行为偏差
2. 把偏差压缩成一条可理解原则
3. Owner 能批准 / 修改 / 拒绝
4. 原则进入一个可回滚通道
5. 后续相似任务中原则被激活
6. Owner 能看到行为变化
```

这六步缺任何一步，PD 都不闭环。

---

## 缺失环节与系统退化

| 缺失环节        | 系统会退化成什么 |
| ----------- | -------- |
| 没有重要 pain   | 日志系统     |
| 没有原则压缩      | 事件归档系统   |
| 没有 Owner 审批 | 失控自动化    |
| 没有部署通道      | 原则仓库     |
| 没有激活机制      | 死知识库     |
| 没有行为观察      | 自嗨型学习系统  |

这张表可以作为当前阶段判断 issue 优先级的架构尺子。

当你犹豫某个功能是否该做时，问一句：

> 它让这六步里的哪一步变得更可用、更可观察或更可回滚？

如果答不上来，它很可能是“维护者驱动的完整性焦虑”，而不是 MVP 必需品。

---

## MVP 的核心成功标准

MVP 的成功标准不是：

* 原则库有多少条；
* pain 捕获了多少次；
* 是否实现 Attribution；
* PRRR 是否可计算；
* 报告是否漂亮；
* 架构是否完整。

MVP 的成功标准是：

> 一个真实 Owner 能审批一条原则，并在后续相似任务中看到 Agent 行为发生符合期待的变化。

这叫 demonstrated behavior change。

只有先证明这一点，PD 的后续指标体系才有意义。

---

# 第八部分：PRRR 与 Attribution —— 未来度量，不是当前前置项

PRRR 是一个有价值的想法，但它不应该抢走 MVP 的中心位置。

PRRR = Pain Recurrence Reduction Rate
即：痛苦复发减少率。

通俗地说：

> 某条原则启用后，同类 pain 是否减少了？

例如：

Agent 以前经常写完代码忘记跑测试。
Owner 批准了一条原则：完成代码修改后必须运行相关测试或说明无法运行的原因。
之后同类遗漏明显减少。
这时可以说这条原则可能提高了行为质量。

PRRR 试图把“Agent 有没有学习”从玄学问题变成可观察指标。

这是对的。

但它是 post-MVP 的工具，不是 MVP 的前提。

---

## PRRR 的价值

PRRR 有三个价值。

第一，它逼迫系统从“原则被保存”走向“原则是否有效”。

第二，它让原则可以被证伪。如果原则启用后同类 pain 没减少，甚至增加了，说明原则可能无效或有副作用。

第三，它为长期原则库治理提供依据。没有度量，原则只会不断堆积。

---

## PRRR 的软肋

PRRR 也有明显软肋。

| 软肋         | 含义                             |
| ---------- | ------------------------------ |
| 因果分配问题     | 多条原则同时启用时，很难判断是哪条原则起作用         |
| painId 漂移  | 同类 pain 的分类可能随时间变化             |
| 小样本噪声      | 小工作区里数据太少，指标容易剧烈波动             |
| 负面外部性      | 一条原则减少了 A 类 pain，却增加了 B 类 pain |
| 探索惩罚       | 过度奖励少犯错，可能抑制 Agent 探索复杂任务      |
| Owner 解释成本 | 指标太复杂时，Owner 不一定愿意相信           |

所以 PRRR 不能被神化。

它不是“真理仪表盘”，而是未来辅助 Owner 判断原则有效性的工具之一。

---

## 更稳妥的演化路径

### MVP 当前阶段

主指标：

```text
Owner 观察到的可复现行为变化
```

理由：

没有足够真实数据时，不要急着做复杂归因。先证明 PD 的基本闭环能跑起来。

---

### Post-MVP 早期

可以引入：

```text
PRRR + Net-PRRR + Bayesian 平滑
```

其中：

* PRRR 看同类 pain 是否减少；
* Net-PRRR 看副作用；
* Bayesian 平滑避免小样本过度判断。

---

### 中期

引入 Time-to-Recovery。

也就是：

> 同类 pain 再次发生时，Agent 多快恢复？

这个指标比“再也不犯错”更健康。

因为真正的学习不一定是永不犯错，而是：

> 犯错之后更快发现、更快修正、更少扩大损失。

这对 coding agent 特别重要。

---

### 长期

可以研究信息论指标。

例如：

```text
学习增益 = 行为不确定性下降
```

也就是 Agent 面对相似任务时，行为是否更稳定、更符合 Owner 期待、更少随机漂移。

这个方向有理论野心，但实现复杂，不适合 MVP。

---

## 对 PRRR 的最终定位

PRRR 是未来让 PD 更诚实的工具。
但它不能代替 Owner。
它不能阻塞 MVP。
它不能证明全部因果。
它不能独自定义“什么是更好行为”。

PD 当前最重要的不是先造仪表盘，而是先证明：

> 原则真的能改变行为。

---

# 第九部分：感知带宽 —— Owner 治理视野的上限

LLM 没有天然痛觉。

人类碰到火会自动缩手。
Agent 不会。
Agent 只有在系统显式设计了信号通道时，才会“知道”某类事情值得被记录、反思和治理。

所以：

> Agent 能感知到什么失败，不是自然事实，而是产品设计选择。

---

## 感知带宽的定义

可以把痛苦信号的多样性理解为 Agent 对自身行为偏差的感知带宽。

但这句话需要说准：

> **感知带宽限制了 Owner 可治理行为领域的上限。**

如果 Agent 永远只能感知工具调用失败，那么 Owner 再勤奋审批，也很难治理她更在意的东西：

* 目标偏离；
* 反复返工；
* 用户挫败；
* 未验证假设；
* 上下文遗忘；
* 擅自扩大改动范围；
* 忽略项目原则；
* 长程任务中途漂移。

因为这些痛苦根本没有进入诊断器，也没有进入 Owner 的治理视野。

---

## 感知到，不等于治理到

这点必须反复强调。

```text
感知到 → 有机会治理
```

但不是：

```text
感知到 → 自动治理成功
```

中间还需要：

* 正确诊断；
* 高质量原则；
* Owner 审批；
* 合适通道；
* 正确激活；
* 后续行为观察；
* 必要时回滚。

所以感知是必要条件，不是充分条件。

---

## 三种感知与三种治理机会

| Agent 能感知到什么 | Owner 获得什么治理机会 |
| ------------ | -------------- |
| 工具调用失败       | 治理工具使用边界       |
| 目标偏离         | 治理目标对齐方向       |
| 用户反复纠正       | 治理用户期待对齐       |
| 反复返工         | 治理计划质量与执行纪律    |
| 上下文丢失        | 治理上下文管理        |
| 大范围危险改动      | 治理风险边界         |
| 未验证假设        | 治理证据纪律         |

注意这里说的是“机会”。

真正能不能形成行为改变，还是要回到 MVP 六步闭环。

---

## 什么时候应该担心感知带宽？

如果你作为 Owner 发现：

* PD 学到的原则月复一月围绕同一个维度；
* 例如总是“工具调用更安全”；
* 但你真正头疼的是目标偏离、反复返工、用户纠正；
* 你手动记录了大量 pain，但自动通道几乎不产出相关 pain；
* Agent 明明反复犯某类错误，但 PD 从不提这类原则；

那么瓶颈可能不在诊断器智能，而在感知层。

这时不应该立刻说“模型不够聪明”，而应该先问：

```text
这类行为偏差有没有进入 PD 的 sensing layer？
有没有被结构化记录？
有没有被归类？
有没有进入原则提案？
Owner 有没有机会审？
```

感知层是 PD 的入口。
入口太窄，后面的反思和治理都只能在窄视野里打转。

---

# 第十部分：注意力保护层 —— Owner 也是稀缺资源

PD 强调 Owner Governance，但这带来一个现实问题：

> Owner 的注意力不是无限的。

如果 PD 的设计不保护 Owner，系统会失败。

不是因为理论错了，而是因为治理成本太高。

---

## Owner 注意力为什么关键？

Owner 在 PD 里承担三种角色：

1. 价值判断源；
2. 原则审批者；
3. 行为变化的最终评估者。

这三件事都需要注意力。

而注意力是最稀缺的资源之一。

执行会越来越便宜。
Agent 数量会越来越多。
工具调用会越来越便宜。
生成原则也会越来越便宜。

但 Owner 的判断带宽不会同步增长。

所以未来真正稀缺的不是“能不能生成更多建议”，而是：

> 哪些建议值得 Owner 看？

---

## 注意力保护层的目标

注意力保护层不是让 Owner 少参与，而是让 Owner 的参与更有杠杆。

它应该帮助系统做到：

* 少生成低价值原则；
* 合并重复 pain；
* 聚类相似行为偏差；
* 提前过滤无证据提案；
* 标出高风险原则；
* 显示原则可能副作用；
* 提供清晰的 approve / reject / modify / defer 路径；
* 让回滚变得简单；
* 让 Owner 看见行为变化。

好的治理界面不应该让 Owner 感到：

> “我又多了一个要管理的系统。”

而应该让 Owner 感到：

> “我终于能把反复纠正 Agent 的经验沉淀下来了。”

---

## 注意力过载的危险信号

如果出现以下情况，说明 PD 正在消耗 Owner，而不是保护 Owner：

* 每天生成大量原则提案；
* Owner 不知道哪些优先审；
* 原则看起来都对，但不知道是否该批准；
* 审批后看不到行为变化；
* 回滚很麻烦；
* Agent 行为变差但不知道是哪条原则导致；
* Owner 开始跳过审批；
* Owner 开始随手批准；
* Owner 觉得 PD 比 Agent 本身还难管理。

这时要警惕：

> PD 正在从行为内化系统，退化成认知负担系统。

---

# 第十一部分：作为拥有者，你只需要盯住的六件事

技术细节再多，作为 PD 的拥有者，你最需要持续盯住六个问题。

---

## Q1：我反复指出的行为偏差，Agent 在相似场景中是否改变？

这是最核心的问题。

如果没有改变，PD 的核心承诺没有兑现。

---

## Q2：我能否看懂、批准、修改、拒绝并撤回一条原则？

如果不能，PD 就不是 Owner-Governed System，而只是后台自动化。

---

## Q3：原则激活后，我是否能看到可比任务中的行为证据？

如果看不到，就不能声称它产生了价值。

至少在 MVP 阶段，Owner 可观察行为比复杂指标更重要。

---

## Q4：PD 看见的 pain，覆盖了我真正在意的失败吗？

如果 PD 永远围绕工具错误生成原则，但你真正头疼的是目标偏离、反复返工、忽略测试、擅自扩大范围，那么问题可能在感知层。

---

## Q5：原则是否正在变成债务？

要警惕：

* 原则越来越多；
* Agent 越来越僵硬；
* 上下文越来越挤；
* 原则互相冲突；
* Owner 不知道哪些原则还有效；
* Agent 为了遵守原则而牺牲任务质量。

原则需要治理。
原则本身也会成为系统风险。

---

## Q6：PD 是否在保护我的注意力？

如果 PD 让 Owner 更累，它就会失败。

一个好的 PD 系统应该减少重复纠正，让 Owner 的反馈更有杠杆，而不是制造更多审批噪音。

---

## 六个问题总结

```text
1. 行为变了吗？
2. 我能治理原则吗？
3. 变化可观察吗？
4. pain 覆盖真实痛点吗？
5. 原则变成债务了吗？
6. 系统保护我的注意力了吗？
```

这六个问题胜过一百页架构文档。

---

# 第十二部分：系统动力学 × AI 系统 —— AI Systems Engineering 的雏形

AI 工程界长期习惯用“算法思维”看系统：

```text
input → model → output
```

这种思维适合分析模型能力，但不适合分析复杂 Agent 系统。

因为 Agent 系统不是单次函数调用，而是多回路系统。

它包含：

* 模型回路；
* 工具回路；
* 上下文回路；
* 记忆回路；
* 用户反馈回路；
* 多 Agent 协作回路；
* 组织流程回路；
* 人类治理回路。

这类系统的问题往往不是“某个函数写错了”，而是“多个反馈回路失谐”。

---

## 为什么传统算法思维不够？

算法思维解释不了：

* 为什么原则越多 Agent 反而越笨；
* 为什么 multi-agent 系统会互相等待；
* 为什么 Agent 会在长程任务中目标漂移；
* 为什么 memory 越长，行为越混乱；
* 为什么自动反思越多，系统越自嗨；
* 为什么 Owner 审批越多，治理质量反而下降。

这些不是单点算法问题，而是系统动力学问题。

---

## AI Systems Engineering 需要研究什么？

我会把这个交叉领域称为：

> AI Systems Engineering
> AI 系统工程学

它不同于 Machine Learning，也不同于传统 Software Engineering。

| 学科                     | 研究对象                     |
| ---------------------- | ------------------------ |
| Machine Learning       | 模型如何训练                   |
| Software Engineering   | 代码如何组织                   |
| AI Systems Engineering | 多反馈、多 Agent、人机混合系统如何稳定运行 |

AI Systems Engineering 关心的问题包括：

* Agent 如何被治理；
* 行为原则如何内化；
* 记忆如何不污染行为；
* 多 Agent 如何协调；
* 人类注意力如何不被耗尽；
* 系统如何避免反馈失谐；
* 自动化如何保持可回滚；
* 行为改变如何被观察与评估。

PD 的价值不只是做一个工具，而是用真实工程实践回答一个理论问题：

> Agent 能否在拥有者治理下，通过观察自己的行为偏差而变得更符合期待？

这比“Agent 能不能完成一个任务”更深。

# 结语：PD 的真正问题

拨云见月，PD 的本质不是 memory。
不是 prompt。
不是 workflow。
不是工具修复。
也不是放任 Agent 自我进化。

PD 的本质是：

> **一个由拥有者治理的行为内化循环：从重要行为证据出发，把经审查的原则部署到可回滚通道，并观察下一次行为是否更符合期待。**

这个循环要真正成立，需要六个条件：

```text
1. Agent 能产生真实行为证据
2. 系统能捕获 Owner 在意的 pain
3. 诊断器能把 pain 压缩成原则
4. Owner 能理解、审批、修改、拒绝、回滚原则
5. 原则能通过合适通道影响后续行为
6. Owner 能看见行为变化
```

缺少 Owner，PD 会变成失控自动化。
缺少可观察行为，PD 只是原则仓库。
缺少感知覆盖，PD 只能治理很窄的一小片行为领域。
缺少注意力保护，PD 会把 Owner 拖入新的管理负担。
缺少原则债务治理，PD 会被自己生成的原则污染。
缺少回滚机制，PD 会从内化系统变成行为污染源。

Attribution 与 PRRR 可以在真实用户数据足够后，让这个循环更诚实。
但它们不能代替 Owner，也不能阻塞 MVP 的第一次真实验证。

PD 当前最重要的问题，不是：

> “我们能不能设计一个完美的学习指标？”

而是：

> “我们能不能让一个真实 Owner 看见：她批准的一条原则，真的改变了 Agent 下一次的行为？”

如果能，PD 就不是一个原则仓库。
它就是一个行为内化系统。

如果不能，再复杂的系统动力学模型、再漂亮的 PRRR、再宏大的 AI Systems Engineering 叙事，都只是高级自嗨。

所以，PD 的第一性验证只有一句话：

> **原则是否真的变成了行为？**

这也是 PD 最难、最值得做的地方。

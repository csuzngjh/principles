## 核心命题

> **痛苦信号的多样性，本质上是 agent 对世界的感知带宽。**
>
> **agent 能学到的智慧种类，受限于它感知带宽覆盖的范围。**

这是一个**分析视角**，用来诊断"PD 进化引擎为什么转得不够动"。它不是 PD 的产品定位——PD 不是要让 agent 自主"看见更多"，而是要让**拥有者**能基于足够丰富的行为证据做出更准的治理判断。

> "感知带宽"只是手段，"拥有者能基于它做出可观察的行为治理"才是目的。

其余内容都是这个分析视角的展开。每一处生物学/神经科学/控制论类比都是启发性的，不是论证性的。

## 第一部分：为什么"痛苦信号层"值得作为分析维度被认真对待

### 1.1 回到伴读本的那个公式

伴读本里 PD 的最简模型是这样的：

```
痛苦(t+1) = 痛苦(t) − 有效率 × 原则数(t) + 探索(t)
原则数(t+1) = 原则数(t) + 诊断率 × 痛苦(t) − 归档率 × 无效原则(t)
```

公式左边的"痛苦(t)"——agent 当前还在踩的坑——是整个进化引擎的**输入端**。

但这个公式有一个隐藏前提：

> **痛苦得能被感知到。**

如果真实痛苦是 100 分，PD 只感知到 10 分，那么：

- 诊断引擎接收到的样本量是真实的 1/10
- 生成的原则只覆盖那感知到的 10%
- 剩下 90% 的痛苦永远在背景里反复发生，agent 永远学不到对应的原则
- **拥有者的体感是"PD 没什么用"——但根因不是 PD 笨，是它瞎**

### 1.2 大语言模型不具备"痛觉神经"

这是个被严重低估的事实。

人类的进化飞轮能转，是因为**痛觉是天生的、自动的、无法关闭的**。手碰到火立刻收回，不需要专门设计一个"火检测器"。

但 LLM / Agent 不同：

| 维度 | 人类 | LLM Agent |
|------|------|-----------|
| 痛觉来源 | 神经系统硬连线 | 必须由外部系统**显式构造** |
| 触发延迟 | 毫秒级 | 取决于检测器 |
| 覆盖范围 | 全身 | 只覆盖被检测器看见的部分 |
| 缺失的代价 | 受伤 | 静默退化，连"我哪里不对"都不知道 |

**结论**：对 LLM 而言，"感知到痛苦"不是自然的，而是**被设计出来的能力**。

> **痛苦感知层的工程质量，决定了 agent 进化的天花板。**

### 1.3 这不是工程问题，是认识论问题

工程问题问的是："我能不能让信号产生得更快、更准？"
认识论问题问的是："agent 能感知到的世界，覆盖了真实世界的多少？"

这两个问题的答案完全不同：

- 工程改进可以让现有通道的信号质量提升 20%
- 但**新增一个通道**可能让 agent 突然看见过去完全忽略的整个维度

> **PD 真正的天花板不在 Diagnostician 的智能程度，而在 Pain Detector 的感知广度。**

## 第二部分：现状的事实图——三种状态的通道

PD 当前的痛苦信号系统有三种状态：**真正在跑的、半挂接的、只在文档里的**。

### 2.1 真正在跑的（6 个生产入口）

```
1. CLI 显式：    pd pain record                    （拥有者手动）
2. 工具失败：    after_tool_call ∩ WRITE_TOOLS     （仅写文件类工具）
3. 显式工具：    agent 调用 tool='pain'             （罕见）
4. 共情/瘫痪：   llm_output 中的关键词/标签/卡死    （MVP-Quiet）
5. 子代理失败：  subagent_ended outcome=error      （仅 error）
6. Gate 拦截：   RuleHost 或 risky 拦截             （需累计 GFI）
```

### 2.2 半挂接的（写到一半，没接到诊断链路）

```
7. EmpathyObserverWorkflow：写 trajectory，但不调用 emitPainDetectedEvent
8. correction_rejected：人工拒绝 correction sample 时只写一行 trajectory
9. user_correction：CorrectionCueLearner 检测到了，但根本没转成 pain
```

### 2.3 只在文档里、代码完全没有的

```
10. Layer 1 主信号（mission_failed / okr_drift / rework_loop / decision_skipped）
11. PainCategory（derivedFromPainIds 字段名误导，实际存的是 candidateId）
12. build/lint/test/CI 失败（除非走 WRITE_TOOLS 的 exitCode≠0 路径）
13. PRRR 反向归因
```

### 2.4 一句话总结

> **PD 文档讲的是"三层信号架构"。代码实际跑的是"半层信号架构"——只有 Layer 3 的一部分 + 手动 CLI。**

这不是设计错了，是**实现远远没追上设计**。

## 第三部分：三维度诊断（数量 / 质量 / 多样性）

### 3.1 维度一：数量（Volume）—— 信号被门槛卡死

当前数量瓶颈不在产生端，在**过滤端**：

| 卡点 | 当前阈值 | 后果 |
|------|---------|------|
| WRITE_TOOLS 白名单 | 6 个工具 | bash / test / search / network 失败永远不进 pain |
| `consecutiveErrors ≥ 4` | 同一错误重复 4 次 | 第 1-3 次失败"无声消失" |
| `currentGfi ≥ 70` | 累积才升级 | 偶发但严重的失败被低估 |
| 15 分钟 cooldown | 同 episodeKey | 真实的"反复犯同一错误"被合并掉，看不到频率 |
| Subagent timeout 不计 | OpenClaw 修复 | 真实的卡死被当成假阳性放过 |

**根因**：PD 把"防噪声"做得过头，结果**把信号也防掉了**。

> 类比：一个把咖啡过滤纸用得太厚的咖啡机，最终流出来的不是咖啡，是水。

### 3.2 维度二：质量（Quality）—— 信号语义贫瘠

当前 painType 只有 **3 个枚举值**：

```
tool_failure  |  subagent_error  |  user_frustration
```

这是粗到不能再粗的分类。

举例：以下三件事在 PD 眼里**完全一样**——

- agent 误删了用户的代码
- agent 忘记跑测试就推送 PR
- agent 在重构时改坏了 100 个文件

它们的严重性、根因、应对原则**完全不同**，但 painId 没有 category 维度，所以 Diagnostician 只能从 reason 文本里猜。**猜错了，原则就长在错误的地方。**

更糟的是 `derivedFromPainIds` 字段名暗示存的是"原则衍生自哪些 pain 类别"，**代码里实际存的是 candidateId**。这是个很大的隐性 bug——**PRRR 计算所需的"同类 pain"维度，schema 层面就不存在**。

### 3.3 维度三：多样性（Diversity）—— 信号源分布严重失衡

把当前真正进入诊断链的信号画成饼图，大概是这样：

```
工具失败 (WRITE_TOOLS exit≠0)  ████████████████████  ~60%
GFI 阈值触发                   ████████              ~20%
manual CLI                     ████                  ~10%
subagent error                 ██                    ~5%
gate_blocked / 其它             ██                    ~5%
```

**Layer 1（目标导向痛苦）= 0%**——没有任何代码路径产生它们。
**user_correction → Pain = 0%**——CorrectionCueLearner 只写了 trajectory，没接 bridge。
**build / lint / test 失败 = 0%**——除非碰巧走 WRITE_TOOLS 路径。

这就解释了一个奇怪的现象：

> **PD 学到的原则永远围着"如何更安全地调用文件工具"打转——因为它的眼睛只看得见这件事。**

### 3.4 三维度的合成图

```
              数量
              ▲
         (低) │
              │     ✗ PD 当前在这个角落
              │       数量低、质量粗、多样性单一
              │
              │
              ──────────► 多样性
             /
            /
           ▼
        质量

         理想方向：向右上前方移动
         （多源 + 细分 + 高频）
```

## 第四部分：改进框架（修补 / 扩张 / 重构）

按"修补 → 扩张 → 重构"的顺序，不要跳级。

### 4.1 第一层：修补（候选项，需逐项与 ADR-0014 对照）

> ⚠️ **重要更正**：我之前把这些列为"是 bug 不是 feature"，这一判定**过于自信，需要回退**。
>
> 实际上：
> - 部分条目（F1 user_correction、F2 EmpathyObserverWorkflow）触及 ADR-0014 §2.5 MVP-Quiet 列表里"empathy_inferred 关闭"和"Empathy keyword matcher 关闭"的有意决定。**ADR-0014 之所以关闭它们，理由是"推断本身可能错"——这是产品判断，不是工程债**。
> - 部分条目（F4 字段名歧义、F5 类型联合不全）确实是代码层面的诚实债，但仍需走 PRODUCT_IDENTITY Decision Gate（特别是问题 4：是否复制了 host/runtime 能力）才能进入 MVP scope。
>
> 因此本节命名改为"候选修补点"，每项是否真做、何时做，由拥有者按 ADR-0014 + PRODUCT_IDENTITY 决定。

这些不属于 ADR-0014 锁定的"扩张"，而是**修复"代码与文档不一致"的诚实债**——它们在系统里已经被假设存在。

| # | 候选修补点 | 与 ADR-0014 / PRODUCT_IDENTITY 关系 |
|---|-------|-----------------------------------|
| **F1** | 把 `user_correction` 接到 PainSignal 链路 | ⚠️ ADR-0014 MVP-Core 清单中**未列 user_correction**，文档与代码的不一致需先由拥有者裁定方向（让代码追文档 vs 让文档追代码）。不能直接断言是 bug。 |
| **F2** | EmpathyObserverWorkflow 半挂接 → 全挂接 | ❌ **与 ADR-0014 §2.5 直接冲突**。Empathy keyword matcher 已被有意标为 MVP-Quiet（"推断本身可能错"）。**默认不应做**，除非拥有者基于真实客户证据决定推翻 ADR-0014 这一项。 |
| **F3** | `correction_rejected` 接到 bridge | ⚠️ 与 F1 同样需要拥有者裁定。拒绝信号是真实数据，但是否值得变成原则候选是产品判断。 |
| **F4** | `derivedFromPainIds` 字段名歧义 | ✅ 这是代码层面的诚实债——字段名误导可能引发 ERR-001 类隐性错误。改名或加注释是低风险修补。 |
| **F5** | `dispatch_error` painType 联合不全 | ✅ 同上，类型联合不全靠隐式 cast 是 ERR-001 风险点。 |

**预期效果（已撤回）**：我之前估计"做完后痛苦信号数量翻 3-5 倍"——这个数字没有数据支撑，**不应作为决策依据**。真实效果只能在拥有者批准、改动落地、观察一段时间后才知道。

### 4.2 第二层：扩张（post-MVP 候选；每一项受 ADR-0014 与重启路线图严格约束）

> ⚠️ **重要更正**：我之前把这些列为"post-MVP 路线图"，这种叙述**过于轻巧**。
>
> - **E4 = GAP Layer 1** 在 [`post-mvp-conditional-roadmap.md`](../plans/post-mvp-conditional-roadmap.md) §9 已有非常严格的重启条件（"种子客户主动要求"、"≥ 1 个客户已手动维护类似目标列表"、"PainSignal 总量 > 100/天"）。本表中的"重启条件"列若与该路线图冲突，**以路线图为准**。

> - **AGENTS.md 反模式触发器**："为下个 Phase 准备 / 为完整性 / review 时觉得这块缺失"——这些是自动停止信号。本节如有任何条目被引用为"应该做"的依据，必须先回到 PRODUCT_IDENTITY 答完四个问题。

| # | 扩张点 | 解决什么 |
|---|-------|---------|
| **E1** | 移除 / 放宽 WRITE_TOOLS 白名单 | bash / test / network 失败也能产生 pain |
| **E2** | 引入 build / lint / test / CI failure 入口 | 这是质量信号最丰富的来源 |
| **E3** | 引入 PainCategory（一级分类 + 二级 painId） | 让 PRRR 计算有"同类"维度可循 |
| **E4** | Layer 1: GAP 主信号（mission / okr） | 真正"目标驱动"的痛苦 |
| **E5** | RejectionFeedback 完整闭环 | 用户拒绝建议时反向学习 |

| # | 重构点 | 含义 |

## 第五部分：拥有者视角的优先级与判断锚点

### 5.1 当前最关键的认知

**当前最该做的不是发明新通道，是把已经存在但没接通的接通。**

这是个非常关键的认知——大部分团队遇到"痛苦信号不足"会想"再加一个新检测器"，但 PD 真正的问题是**已经写了 9 个通道，只有 6 个真正在工作**。

### 5.2 MVP 阶段建议优先级

1. **先做 F1-F5（修补层）**：这些是 bug 修复性质，不破坏 ADR-0014。做完之后做一次定量观察——pain 入库总量、按 source 分布——拿数据说话。
2. **观察 1-2 周**：看真实数据里痛苦信号的分布。如果还是被某一两个源主导（很可能还是会），就有了真实的"扩张需求"证据，而不是焦虑驱动的扩张。
3. **如果种子客户已经在抱怨"PD 不学新东西"**：说明 E1（放宽 WRITE_TOOLS）+ E6（task end 自评）应该插队进 MVP-Quiet，feature flag 默认关，让客户主动激活。

### 5.3 post-MVP 阶段路线（基于条件重启）

| 重启条件 | 扩张内容 |
|---------|---------|
| 修补层做完且 pain 量级仍 < 50/天/workspace | 启动 E1 + E2（工具白名单解除 + build/test 入口） |
| 种子客户主动反馈"原则覆盖太窄" | 启动 E3（PainCategory）+ E5（RejectionFeedback） |
| 已有 ≥ 1 个客户手动维护目标列表 | 启动 E4（Layer 1 GAP） |

### 5.4 拥有者关注信号的几个维度（示意，非健康基线）

> ⚠️ **重要 disclaimer**：以下数字**不是经过验证的健康基线**，是我在分析过程中拍出来的示意值。
>
> - 真实基线必须通过在生产数据上运行一段时间后才能确定。
> - PD 系统设计配额（PERFORMANCE_BUDGETS.md）是 50-200 / day / workspace，与本表数字可能冲突，**以设计配额为准**。
> - 拥有者**不应**按这些数字直接做决策，把它们当作"需要建立可观察性后再校准"的待办事项即可。

可以建立可观察性的几个维度（具体阈值需校准）：

| 维度 | 含义 | 异常解读思路 |
|------|------|---------|
| 每天进入 bridge 的 pain 总量 | 痛苦感知系统的总通量 | 长期接近 0 → 信号被门槛过滤掉，或者 agent 没在做有价值的事 |
| pain 按 source 的分布 | 感知带宽是否单一 | 单一 source 长期占绝对主导 → 其他通道实际没工作 |
| painType / painCategory 数量 | 信号语义的丰富度 | 长期只有 1-2 类 → Diagnostician 只能在窄维度里学习 |
| 半挂接通道的 emit 比例 | 文档与代码的一致度 | 半挂接通道长期不 emit → 文档与现实有偏差 |

具体数字阈值由拥有者在生产数据上观察 1-2 周后确定，不是预先拍定。

### 5.5 一个简单的自查

每个月问自己一次：

> **过去 30 天，PD 学到的新原则覆盖了几个不同的"痛苦类别"？**
>
> - 如果都是"工具调用更安全" / "文件路径检查"——感知带宽太窄
> - 如果出现"目标偏离" / "用户语气不对" / "反复犯同一错"——感知带宽在扩张
> - 如果出现完全意料之外的类别——你的 agent 真的在变聪明

## 第六部分：再论"感知带宽"——这是认识论问题

### 6.1 一个修辞性的映射（不是命题论证）

回到核心命题：

> **痛苦信号的多样性，本质上是 agent 对世界的感知带宽。**

> ⚠️ **disclaimer**：下面这个三层映射是修辞性的，不是命题论证。
>
> "感知到目标偏离 → 学到大智慧"是必要不充分关系——感知是学习的前置条件，但感知到不等于学到。博文 02 节已经讲过"知道一个概念不等于拥有这个能力"——同样，agent 感知到一类痛苦不等于一定能学到对应的智慧。把这个映射读成"扩感知就能扩智慧"是过度乐观。
>
> 此外，PD 沉淀的从来不是"智慧"，是经拥有者审批的**行为约束**。把行为约束类比成"小聪明 / 大智慧 / 人际智慧"是为了叙事好读，但拥有者做产品判断时不应直接采用这个层级。

这个映射的有限版本是：

- 只感知到"工具失败"的 agent，能产出的原则提案集中在工具调用边界
- 能感知到"目标偏离"的 agent，**才有机会**让拥有者审批与目标对齐有关的原则提案
- 能感知到"用户反复纠正"的 agent，**才有机会**让拥有者审批与用户期待对齐的原则提案

"才有机会"是关键词——后续是否真有可观察的行为变化，仍然取决于拥有者审批、通道部署、可比场景验证的完整链路。

### 6.2 跨学科的若干启发性类比（不是同构证明）

> ⚠️ **disclaimer**：下表是**启发性类比**，不是严格的同构关系。每条类比都有具体偏差（章鱼分布式神经反例、Ashby's Law 原义是"控制器多样性 ≥ 被控对象多样性"而非"感知越宽越好"、信息论的"带宽"指吞吐量而非质量）。把它们当作"激发思考的隐喻"，不要当成"证据链"。

可以从这些学科里借一些直觉：

| 学科 | 借来的直觉 | 注意 |
|------|---------|------|
| 神经科学 | 感官皮层的发达程度与行为复杂度有相关性 | 不是因果，且有反例 |
| 控制论 | Ashby 必要多样性定律提示"感知/控制能力须匹配所处环境" | 原义涉及控制器与被控对象，借用为"感知"是引申 |
| 进化生物学 | 物种的感知扩张往往伴随行为复杂化 | 时间尺度不可比 |
| 信息论 | 信道带宽决定吞吐量 | 不直接等于"智慧上限" |
| 教育学 | 反馈颗粒度影响学习精细度 | 颗粒度 ≠ 广度 |

它们合起来支撑一个**软命题**：感知层值得 PD 团队认真对待，至少与诊断器智能同等重要。这不构成强论证，只是观察一个常被忽视的层。

### 6.3 一个生物隐喻（仅用于理解，不用于决策）

> ⚠️ **disclaimer**：下表是**理解辅助**，不是工程尺度估计。把"接通 EmpathyObserverWorkflow"和"演化出听觉系统"放在同一个尺度上是浪漫修辞，会让人误判工程改动的实际成本和影响范围。**切勿据此做工程排期或风险评估**。

| 阶段 | 感知能力 | 行为复杂度 |
|------|---------|----------|
| 单细胞生物 | 一个化学梯度感知器 | 趋化运动 |
| 简单多细胞 | 光感 + 化学梯度 | 趋光 + 觅食 |
| 早期动物 | 眼 + 触觉 + 嗅觉 | 捕食、躲避、群居 |
| 哺乳动物 | + 听觉 + 平衡 + 痛觉 + 共情 | 协作、教育、文化 |

借用这个隐喻只是为了说明：**感知层的扩张通常伴随行为层质变**。具体到 PD 当前阶段在这条光谱上的位置，不应该硬比生物分类——拥有者要做的判断不是"PD 该跳到哪一格"，而是"基于种子客户的真实信号，下一个值得拥有者投入治理精力的痛苦类别是哪一类"。

### 6.4 这意味着什么

对 PD 项目而言：

> **痛苦信号层至少与 Diagnostician 同等重要。**

> ⚠️ **disclaimer**：下面这张优先级表是**分析视角**，不是工程指令。**任何实际优先级调整必须由拥有者依据 PRODUCT_IDENTITY Decision Gate 与 ADR-0014 决定**。我列出它是为了让拥有者在做下一次产品决策时，把"感知层"作为一个需要主动权衡的维度，而不是默认它已经够用。

| 一种被忽视的视角 | 提示 |
|------------------|------|
| 单纯优化 Diagnostician 智能 | 不会让 agent 看见原本看不见的痛苦类型 |
| 单纯优化内化路径 | 不会让原则覆盖原本没数据的维度 |
| 单纯优化算法层 | 不会改变 sensing 层的输入分布 |

这不是说 Diagnostician / 内化路径 / 算法不重要——它们都重要。只是说：**当拥有者发现 PD 学到的原则永远围着同一个维度打转时，瓶颈很可能在感知层而不是诊断层**。这是诊断思路的一个候选选项。

### 6.5 一个值得验证的猜想（不是行业断言）

> ⚠️ **disclaimer**：原本这里写了"给行业的判断"，断言"sensing layer 大家都假装它已经解决了"。**我撤回这个表述**。我没有调研过 LangChain Memory / Letta / Mem0 / Zep 等同行产品的 sensing 层设计，把它们都说成"假装解决"是无证据的同行批评，且不符合 AGENTS.md 的"基于研究而非焦虑"原则。

留下一个**待验证的猜想**：

> 当前 AI Agent 行业的主流叙事侧重模型规模、prompt、工具数量。"agent 该如何感知自己什么不对"这一层在公开讨论中较少被提及。

这只是一个观察印象，不是结论。如果这个印象成立，PD 投资感知层可能形成差异化；如果不成立（同行其实有大量未公开的 sensing 工作），PD 仍然有自己的拥有者治理路径作为差异化。**两种情况下，下一步动作都应回到拥有者治理这条主线上**——不依赖"行业都不做 sensing"这个外部假设。

## 结语

> **PD 主张的是：拥有者治理的行为内化循环。**
> **痛苦信号层是这个循环的输入端。如果输入贫瘠，拥有者再勤奋审批也无法治理她从未看见过的失败模式。**
>
> 这就是为什么"感知带宽"值得作为分析视角被认真对待——**不是为了让 agent 自主进化，而是为了让拥有者拥有更完整的信息基础做出治理判断**。
>
> 本文的所有具体建议（F1-F5、E1-E6、R1-R3、N1-N4 数字、跨学科类比、生物隐喻）都是**辅助思考的脚手架**，不是工程蓝图。它们与 PRODUCT_IDENTITY 或 ADR-0014 冲突时，**以 PRODUCT_IDENTITY 与 ADR-0014 为准**。
>
> "感知带宽 = 智慧上限"是引人入胜的口号，但更准确的说法是：
>
> > **感知带宽是拥有者治理 agent 的视野上限。视野多宽，拥有者能治理的领域就多宽。**

# SPEC-PD-CONSOLE-READABILITY-002：控制台原则阅读与审批体验整改

版本：1.0 · 日期：2026-10-13 · 状态：Owner 请求起草，待评审、未实施

## 1. 结论与目标

整改目标：让 Owner 打开控制台后，先看懂发生了什么、原则准备改变什么、需要自己决定什么，再按需阅读完整规则与证据。

当前痛点不只是乱码：长篇规则被当作标题、复杂要求没有阅读层次、内部术语直接露出、证据和操作入口与用户预期不符。这些问题增加理解成本，也使审批容易变成“不看懂就点按钮”或“因为读不懂而放弃”。

本 SPEC 整改现有控制台的展示与操作说明。保留 PD 的 Owner 审批、证据真实性、可撤销和可追溯边界；不自动改写原则，不重设计治理架构。

### 完成标准

1. 长规则不再整段充当加粗大标题，换行、段落和层级可读。
2. 常规卡片先给简洁入口；完整审批文本始终能在当前审查流程中访问。
3. 原则、说明、审批记录、行为证据和生效状态不混为一谈。
4. 不认识内部编号的 Owner 也能理解按钮作用；证据入口能定位到对应对象或明确说明无法定位。
5. 已损坏文字不会被静默删除、猜字修复或假装恢复。
6. 验收包含真实页面和 Owner 理解反馈，不能仅凭测试通过宣布体验改善。

## 3. 范围与禁止事项

### Included

- 治理焦点中的原则待审卡及相关决策卡。
- 原则审查列表、原则详情、生效情况中相同的阅读与术语问题。
- 与当前对象对应的行为证据定位和返回路径。
- 当前源码中的乱码、相关双语静态文案、必要的模型投影/验证器/消费者调整。
- 回归测试、真实页面截图、理解验证和验收记录。

### Excluded

- 官网、安装器、Companion 原生壳、通用仪表盘或全站重设计。
- 新的摘要模型调用、原则生成流水线改造、自动翻译或自动拆分/合并原则。
- 新数据库、存量记录修复迁移、新的 Owner 政策或审批权限。
- 自动批准、批量决策、新治理状态、新后台服务、新运行时开关。
- 修改 ADR、AGENTS.md 或私有设计指南。
- 写入安装运行时、OpenClaw 插件安装目录及用户工作区 `.pd` 状态。

原则内容过度复杂是独立问题。本轮必须改善其阅读和缺口说明，但不承诺把每条复杂原则自动改写成正确的简单原则。需要重写、拆分或改变含义的案例记录为后续候选，经 Owner 决定后另行处理。

## 4. 实施前 Reality Audit

先阅读 `AGENTS.md`、产品身份、适用 ADR、现有 UI SPEC 与私有情绪价值指南。保留工作树中所有无关改动，在合适的隔离工作区实施。

逐项确认：

1. 当前待审文本来自哪个 artifact；同组多条审批是否指向同一内容、不同版本或不同通道。
2. 当前原则短标题、可读说明、Owner narrative、readability warning、lineage resolver 是否已有实现和消费者。
3. 审批的真实目标、allowedActions、锁定原因及恢复入口来自哪个现有权威来源。
4. 行为证据页是否已有精确定位、过滤及返回能力；不得仅添加参数而不实现消费。
5. 同类展示在 Focus、列表、详情、生效页的差异；已经修复的项记为已满足，不能重复创造机制。

优先接通已有能力。不要把现有 `candidateDescription` 按冒号、乱码或破折号切开来“恢复”标题/正文；这些字符可能属于合法原文。若原始结构可读取，应在现有投影所有者内使用真实结构；若不能，应保留完整文本并明确缺口。

阅读 ERROR_PATTERN_INDEX；实施时运行 `error:context` Pass 1/Pass 2。重点评估 EP-01、EP-03、EP-06、EP-09、EP-11、EP-13，按实际命中选取，不机械凑数。

## 5. 页面需求

### R1 — 源码乱码与存量损坏分开处理

**要求：** 修复已确认损坏的静态拼接分隔符和会到达用户界面的静态字符串；用 UTF-8 保存。验证服务端响应和浏览器显示，不能只验证源码搜索结果。

对于动态原则/证据中疑似损坏的字符，保留原始文本，显示“文字可能已损坏，含义需要核对”及现有追溯入口。不得以替换 U+FFFD、猜测原字、删除片段的方式修复记录。包含合法特殊字符的内容不能被自动判定为损坏。

**AC-R1：** title+statement、principle+rule 两条真实提取路径的响应不再由源码引入替换字符；测试包含中文、英文、emoji、引号、换行和原文自带特殊字符。动态损坏样例有提示且原文未变。确认数据损坏时另提有证据的恢复任务，本轮不迁移用户数据。

### R2 — 标题、说明、完整规则分层

**要求：** 待审卡固定区分：短标题、已有可靠易读说明、完整审批文本、操作区。列表/详情/生效页采用同样的语义，允许按页面任务调整布局。

- 有真实短标题时直接使用；长标题保留原文入口，不能把截断结果当成完整语义。
- 没有可读标题时用“待审原则”等诚实入口，不用随机 ID 或自动编造标题。
- 有现成、来源明确的易读说明时展示，并标明其是说明；没有时写“暂无易读说明”，不假造解释。
- 易读说明尽可能回答“何时适用、要改变什么、主要限制”；现有资料不足就明确缺失，不从名称或状态猜测。
- 完整文本默认展开或由明确的“阅读完整规则”展开；无论采用哪种方式，审批前均能在当前审查流程访问全文。不得只显示摘要却移除全文。
- 同一分组含不同待审正文时，逐条标明目标与内容；不得用第一条 artifact 的摘要代表全部批准对象。
- 批准目标、权限、锁定和确认语义仍由现有治理契约决定，本轮不添加新的“已阅读”持久状态或审批规则。

**AC-R2：** 覆盖短文本、500/2000 中文字符、无标题、无说明、多版本/多通道待审情况；全文与实际审批 artifact 可对应。展开与收起不改变审批目标。完整正文不再作为加粗 h1/h3；缺失说明和原文回退可见。

### R3 — 段落与文字层级

**要求：** 保留原始换行、空行、编号和顺序。标题加粗，正文常规字重。禁止把整段规则包装成一块标题。

- 中文正文默认至少 15px、行高至少 1.6；辅助状态/证据说明至少 13px；技术详情可适当减小但必须能缩放阅读。
- 审查正文建议限制在约 36～48 个全角字符的行宽；大屏可放宽页面/操作布局，但不要把长文拉成满屏单行。
- 不强制所有页面改宽，也不全局修改 PageShell 来顺带改变其他流程。
- 保留现有品牌、主题与组件；使用既有语义色。正文、辅助文字和必要边界说明满足 WCAG AA 对比目标。
- 长 ID/路径/代码必须换行或在技术区域内局部滚动，不能撑破整个页面。
- 原始文本按文本处理；不引入不受控 HTML 渲染。若复用已有格式化渲染器，必须保留转义与现有安全边界。

**AC-R3：** 1440×900、1280×720、390×844、桌面 200% 缩放，浅/深主题均检查；正文、长编号、错误提示和按钮无遮挡或页面横向溢出。含空行、编号及 HTML-like 文本的样例按预期显示，不能执行原文中的标记。

### R4 — 默认用日常语言，技术信息按需展开

**要求：** 首层使用用户可理解的状态名称；首次涉及内部概念时说明实际含义。原始检查码、内部 ID、预算、路由等进入“技术详情”，不能丢失或替代治理依据。

建议静态用语：Rollout 评审 → “执行结果评审”；RuleCode 决策 → “自动执行规则审查”。实施时核对真实语义再定稿，不能仅按名称翻译。

生效页需继续区分：可进入提示、已记录投递、已记录应用/效果、未知。不能为了简洁统一说成“已生效”或“AI 已遵守”。当前窗口未容纳的含义应先用日常语言说明，字符预算与路由作为详情。

所有静态文案及控件辅助名称使用现有 i18n。用户原始原则、证据和未知服务端枚举不强制翻译；未知值显示可理解的缺口说明并保留原值。

**AC-R4：** EN→ZH→EN 后静态文案与辅助名称一致；已知检查项不会直接以裸代码充当解释；未知项不隐藏。无投递/无效果/数据不可用样例不能出现不实肯定句。

### R5 — 计数准确、证据能定位

**要求：** `group.records.length` 只能描述“审批记录”，不得命名为行为证据数。行为证据计数必须来自对应现有证据来源；数据不可用不能显示为零。

“查看对应行为证据”必须使用真实 lineage/对象关系定位到当前原则的记录；多个关联明确显示，不选第一条冒充唯一证据。不能按标题文本、数组顺序或猜测 ID 建立关联。

优先复用现有证据页与解析能力；没有定位消费能力时，在该页面中最小补齐查询/定位行为。无关联时明确说明“尚未找到对应行为证据”，可以另给“浏览全部行为证据”，不能把它标成“完整链路”。定位对象缺失/不在当前结果中时提供诚实降级说明与下一步，不静默跳到无关记录。

证据页沿用已有脱敏读模型，不能为方便理解暴露原始 prompt、轨迹、token、绝对路径或堆栈。返回审查后恢复对应对象和合理的阅读位置。

**AC-R5：** 至少用 A/B 两条标题相近但身份不同的原则测试定位；覆盖多关联、无关联、过期关联和数据降级。点击 A 不能落到 B；返回仍能找到 A。审批数与行为证据数分别验证。

### R6 — 按钮名称与真实操作一致

**要求：** 当前要求替换已验证 artifact 的“编辑”改为如“替换待审版本”，并在操作展开区说明前提、输入来自哪里、此次替换影响什么。不要给正文编辑器的假象。

仅当现有产品确有正文编辑能力且接入完整验证/审批契约时，才能使用“修改文字”。不得为兑现旧按钮名称临时增加任意正文写入接口。

批准、拒绝、替换、停用附近提供来源可靠的后果说明；操作类型、权限、可撤销性和失败信息使用现有权威结果。不能承诺“批准后立刻生效”或“停用会撤销所有历史影响”。保留现有失败不变更、锁定、确认和版本一致性行为。

**AC-R6：** 替换路径仍使用真实 parser/API/治理入口，输入无效时无禁止的变更；旧版本、锁定、服务拒绝均可理解且不显示成功。无法取得替换来源时明确前提缺失，不诱导 Owner 猜工件 ID。

### R7 — 去除重复铺陈，保留必要缺口

**要求：** 一张卡片只出现一次主要规则正文；“依据”显示真正的来源说明/证据入口，不能把同一候选描述再贴一遍当作独立依据。确实没有依据时明确缺失。

风险、阻塞原因、权限和数据缺口不能因折叠而隐藏关键决策限制。技术原文、检查明细和历史记录可渐进披露；已有相同结论只保留一个主展示位置，不新增重复提示卡。

**AC-R7：** 用至少三张连续长卡片验证，标题/摘要/依据不会重复贴出同一全文；必要阻塞仍在操作前可见。详情保留真实风险、撤销边界与证据缺口。

## 6. 验收样例与理解验证

用于说明阅读结构的示意，**不是待写入的 Owner 原则，也不替代截图原文**：

> 标题：先确认范围，再修改现有内容。
>
> 易读说明：当你说“整理”或“优化”时，AI 先核对要改哪些内容。涉及删除或整体重写时，先说明影响并按既有要求取得确认。
>
> 为什么提出：显示对应的真实事件说明；没有资料就明确说暂缺。
>
> 完整规则：展开未经改写的待审版本。
>
> 操作：批准 / 替换待审版本 / 拒绝；旁边说明本次操作的真实作用。

验收素材必须包含：Owner 截图对应内容或经脱敏等价样例、复杂编号、混合中英文、缺少说明、损坏字符、长 ID、无证据、数据降级和混合审批目标。

请 Owner 在未接受开发者口头讲解的情况下检查三条代表性原则，回答：

1. 这条原则主要准备改变什么行为，何时适用？
2. 为什么提出，哪些说法有证据，哪些还不知道？
3. 批准/替换/停用分别会发生什么，完整规则在哪里？

逐条记录“能回答 / 不能回答 / 原文含义本身仍不清楚”。不能把 AI 模拟用户评价当作 Owner 验收。若布局通过但原文仍不可理解，阅读整改不得宣称全面达标；列明需要另行内容治理的案例。

## 10. Complexity Delta

目标约束如下，实施 PR 按实际 diff 重新填写，不能照抄代替审查：

```text
New durable source of truth: NO
New persisted schema/state: NO
New subsystem/service/background process: NO
New public abstraction/interface: NO（目标为复用现有接口；如新增派生字段必须按实际报告 YES）
New runtime feature flag: NO
New cross-package dependency: NO
New host/platform-specific behavior: NO
New external/network capability: NO
```

若现有投影不能提供真实分离的标题/正文或精确 lineage，只能在现有责任所有者内增加最小派生契约；报告必要性、消费者验证、兼容与回滚。不准由 UI 建一个独立的关联数据库或新治理权威。

## 11. Unknown 与停止条件

- 未确认运行中控制台对应哪个构建、截图文本的全部原始字段和损坏范围。
- 未完成真实 Owner 理解验证；截图/代码调查不能替代。
- 现有短标题与解释在不同 artifact 类型上的覆盖率尚未统计；没有说明时不能假装已解决内容可理解性。
- 实施时若遇到多目标审批无法对应全文、lineage 无法可靠定位、需要写入用户状态、修改批准语义或改造生成流水线，停止相关分支并说明缺口；继续完成不依赖它的展示修复。
- 禁止以假摘要、猜测证据关联、降低既有测试期望或隐藏降级状态完成验收。

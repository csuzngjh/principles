# PD Web 控制台 UI/UX 设计评审

- 评审对象：`packages/pd-console`（PD 控制台全部主要页面与关键流程）
- 评审日期：2026-11-11
- 评审方式：本地真实启动控制台 + 浏览器逐屏走查 + 截图留证 + 计算样式测量
- 评审性质：只做评审，**未改任何产品代码，未建 PR，未合并，未发布**
- 后续方案：[PD Web 控制台重新设计与优化方案（2026-11-11）](../plans/2026-11-11-pd-console-uiux-redesign-plan.md)

---

## 0. 一句话总体判断

**这套界面的设计语言克制、统一、有专业感，但内容层还停留在工程日志阶段——内部术语和英文原文直接暴露、字号整体偏小、首屏被重复的状态说明占据、关键决策缺少“影响谁、不处理会怎样、推荐动作”的最小信息。**

补充一句判断：**设计系统有 70 分，信息设计只有 45 分。**用户不会觉得它丑，但会在关键决定前停下来问：“我到底该点哪个？”

## 1. 证据与边界（先说明白）

### 1.1 怎么测的

| 项目 | 说明 |
| --- | --- |
| 启动方式 | 按仓库脚本 `packages/pd-console/scripts/e2e-start.mjs` 启动，隔离的临时工作区，不触碰真实 Owner 数据 |
| 实例 1 | `127.0.0.1:3101`，演示数据（15 条待办），无认证模式（用于常规页面走查） |
| 实例 2 | `127.0.0.1:3131`，另一份演示数据（18 条待办），Bearer 令牌认证（用于查看“决策按钮可用”的审批详情） |
| 实例 3 | `127.0.0.1:3141`，**空工作区**（无种子数据，用于首次进入/空状态） |
| 浏览器 | Chromium，1440×900、1024×768、768×1024、390×844；浅色/深色；中文界面 |
| 截图 | 全部为真实运行截图，存放在 [assets/2026-11-11-pd-console-uiux/](assets/2026-11-11-pd-console-uiux/) |
| 测量 | 用浏览器读取计算样式：字号、行高、颜色、点击目标尺寸、标题层级、对比度 |

### 1.2 重要限制（避免误读）

1. **演示数据不是生产数据。** 数据来自 `e2e-seed`，其中“配置变更需确认”重复出现、“点击拒绝测试原则”等条目属于测试夹具，**不能据此判断生产数据也重复**。本报告只把“渲染方式”当作问题，例如“每条都显示原始英文枚举”“每张卡都有一个无法理解的徽章”，这些与数据真假无关。
2. **接口失败态是模拟的。** 通过拦截 `**/api/**` 制造“服务不可达”，用于观察界面如何表现；这不是真实故障。
3. **未跑真实审批提交。** 本次是只读评审，没有点击“批准/拒绝”写入任何数据；因此“提交后的反馈”不在本次证据内（见 §7 NOT RUN）。
4. **加载耗时是开发服务器数据。** `/update` 约 5.3 秒是本地 `tsx` 开发实例的实测值，生产打包版可能更快；但“5 秒里只有骨架、没有进度说明”这一体验问题是确定的。

## 2. 最该改的 5 件事（按影响排序）

### ① 把“审批详情”改造成真正的决策页（影响：决策正确率、时间成本）

**现状**：审批详情里，五个做决定必需的信息只给了两个——“是什么”有时有，“为什么来”有；而“影响谁”“不处理会怎样”“推荐动作”基本缺失。更严重的是：在材料明确写着“风险说明尚未记录”“缺少可读的行为准则”时，页面仍然把 **“批准这个版本”** 做成唯一的深色主按钮。

**用户会怎么想**：“我什么都看不清，但系统把‘批准’放在最显眼的位置，是不是希望我赶紧点掉？”

**建议**：把详情固定成四段式（是什么 / 为什么来 / 影响谁与不处理会怎样 / 推荐动作），把决策条固定在底部；当关键材料缺失时，**禁用“批准”并说明缺什么、怎么补**，而不是让用户凭感觉点。详见 F-07～F-10。

证据：[04-approval-reading.png](assets/2026-11-11-pd-console-uiux/04-approval-reading.png)、[05-approval-decision.png](assets/2026-11-11-pd-console-uiux/05-approval-decision.png)

### ② 统一“人话层”：把工程师语言挡在界面之外（影响：理解、信任、专业感）

**现状**：同一个界面里混着 `Owner` 与 `拥有者`，人称在 `你` 与 `您` 之间摇摆；有 `PAGES.SIDEBAR.DEBT` 这种未翻译的键名；有 `succeeded`、`manual`、`internalization-missing`、`needs_human_review`、`clean`、`blocked` 这类程序内部状态；有 `PRI-720` 这样的内部工单号；有 `deferred`；还有整段英文报错 `A verified Owner identity is required…`。在“行为证据”里，甚至把 `Run: pd runtime internalization run-once --workspace "C:\Users\...\Temp\..."` 直接展示给用户。

**用户会怎么想**：“这不是给我用的，是给开发者看的。”——专业感在这一刻崩塌，隐私边界也让人不安（临时路径被展示）。

**建议**：建立一张“界面术语表”（Owner = 你/拥有者；approval = 待你确认的改动；candidate = 候选原则；activation = 已生效），所有内部枚举、英文错误、CLI 指令、工单号都必须经过映射；展示路径前先确认是否为隐私范围。详见 F-03、F-23、F-25、F-28、F-29。

证据：[07-pain-expanded.png](assets/2026-11-11-pd-console-uiux/07-pain-expanded.png)、[12-debt.png](assets/2026-11-11-pd-console-uiux/12-debt.png)、[15-settings.png](assets/2026-11-11-pd-console-uiux/15-settings.png)、[14-control-center.png](assets/2026-11-11-pd-console-uiux/14-control-center.png)

### ③ 重做字号阶梯：现在“所有字都像脚注”（影响：可读性、第一眼专业度）

**实测**：
- 页面主标题 29px，但**区块标题只有 11px**（原则审查、设置页的“认证/拥有者身份”等）。
- 原则审查页有 **215 个 11px 文本节点**、83 个 13px、43 个 12px；全页只有 1 个 14px。
- 侧边栏 12px，“待决定/显示全部”这种主筛选按钮 **11px**。
- 辅助标签 10px（“TOOLS”“原则审查”）。

**用户会怎么想**：“字太小，看着累；而且分不清哪句是标题、哪句是说明。”

**建议**：把字号收敛到 5 级（28 / 20 / 16 / 14 / 12），正文 14px 起步（长文 15–16px），辅助信息不低于 12px，标签不再用 10px；区块标题必须明显大于正文。详见 F-01。

证据：[08-principles.png](assets/2026-11-11-pd-console-uiux/08-principles.png)、[15-settings.png](assets/2026-11-11-pd-console-uiux/15-settings.png)

### ④ 做注意力减法：同一条信息不要说三遍（影响：压力、效率）

**现状**：
- 治理焦点首屏叠了 3 条状态说明（“资料待确认 + 计数”“决策动作已锁定…”“部分资料暂未读取…请重新读取”），第一件待办被推到首屏下缘，390 宽下必须滚动。
- 列表下方把同一句“没有可用于展示的原则文本来源。”**逐条渲染 7 次**（另有 4 条同原因被折叠），每次还配 3 行解释。
- 原则审查每张卡右上角都挂“判断暂不可建立”，19 张卡中出现 11 次，变成背景噪音。
- 生效情况首屏连续两段“无法统计/无法保证完整”，先制造不信任。

**建议**：一类状态只出现一次，并且放在“会影响你此刻决定”的位置；重复项折叠成“共 11 条，原因相同，展开查看”；空状态下不要报警。详见 F-05、F-06、F-12、F-17。

证据：[02-focus-full.png](assets/2026-11-11-pd-console-uiux/02-focus-full.png)、[09-principles-full.png](assets/2026-11-11-pd-console-uiux/09-principles-full.png)、[11-activation.png](assets/2026-11-11-pd-console-uiux/11-activation.png)

### ⑤ 重做“空 / 错 / 慢”三种状态（影响：安全感、可恢复性）

**现状**：
- 空工作区的治理焦点显示 **“资料待确认 0 项 … 当前列表可能不完整”**——明明什么都没有，却在报警；右侧还保留一个点了也没用的“开始处理”。
- 行为证据的空状态是英文 `Trajectory database not found`，没有“我该做什么”。
- 服务不可达时，界面直接跳回登录页，看起来像“你需要令牌”，而不是“连不上服务”，也没有重试。
- 更新页加载约 5.3 秒，期间只有骨架，没有“正在检查什么”。

**建议**：空状态给“下一步做什么”的一句话与一个动作；连接失败与认证失败必须区分；超过 2 秒的操作给出进度和可取消。详见 F-31、F-37、F-38、F-40。

证据：[22-empty-focus.png](assets/2026-11-11-pd-console-uiux/22-empty-focus.png)、[23-empty-pain.png](assets/2026-11-11-pd-console-uiux/23-empty-pain.png)、[32-api-failure.png](assets/2026-11-11-pd-console-uiux/32-api-failure.png)

## 3. 分页面详细发现

> 标记说明：**影响** = 这个问题让用户做不成/做错哪种判断；**证据** = 真实截图。

### 3.1 全局框架（导航、页头、术语）

#### F-01｜字号阶梯严重压缩，正文与标签挤在 10–13px
- **位置**：全站；原则审查、设置最严重。
- **看到**：H1 29px → 区块标题 11px → 正文 13/14px → 标签 10/11px。侧边栏、主按钮、徽章都是 11–12px。
- **为什么是问题**：标题和正文的差距过大，而正文和标签的差距过小，导致“层级靠颜色而不是字号”来区分；11px 中文在 1440 屏上需要凑近看。
- **影响**：长文阅读疲劳；“哪句是重点”判断变慢。
- **建议**：见第 5 节“视觉体系”中的字号表；先把区块标题从 11px 提到 18–20px，正文提到 14–15px，标签不低于 12px。
- **证据**：[08-principles.png](assets/2026-11-11-pd-console-uiux/08-principles.png)、[15-settings.png](assets/2026-11-11-pd-console-uiux/15-settings.png)

#### F-02｜同一概念多种叫法，人称也不统一
- **位置**：全站。侧边栏“拥有者意图”、设置“拥有者身份”，正文里又出现 `Owner`；设置页与“内部智能体”说明里用“您”，其余页面用“你”。
- **看到**：`Owner` 与 `拥有者` 混用；“治理焦点 / 待处理事项 / 需要你处理”同页三种说法指同一件事；全站“你”“您”各出现若干次。
- **为什么是问题**：术语不统一会让用户怀疑“这是不是不同的东西”，增加理解成本。
- **影响**：判断“这个页面到底要我干什么”。
- **建议**：建立术语表并全站替换；同一层级只用一种称呼（建议对用户说“你”，对角色说“拥有者”，不再出现 `Owner`）。
- **证据**：[01-focus-light.png](assets/2026-11-11-pd-console-uiux/01-focus-light.png)、[15-settings.png](assets/2026-11-11-pd-console-uiux/15-settings.png)

#### F-03｜原始英文、内部枚举、工单号直接出现在中文界面
- **位置**：行为证据（`succeeded`/`manual`/`internalization-missing`）、原则债务（`Trigger: on-config-change`/`PAGES.SIDEBAR.DEBT`）、生效情况（`clean`、`blocked`）、失败任务（`needs_human_review`）、控制中心（整句英文错误）、设置（`deferred`、`PRI-720`）。
- **为什么是问题**：这些不是“英文没翻译”，而是**程序内部语言泄漏到用户界面**，等同于把日志给用户看。
- **影响**：理解中断；专业感与信任下降；用户会担心“系统是不是坏了”。
- **建议**：在 UI 层强制映射枚举（提供 `enum → 人话` 字典）；服务端错误必须有人话包装；任何内部标识默认隐藏，仅在“技术细节”里出现。
- **证据**：[07-pain-expanded.png](assets/2026-11-11-pd-console-uiux/07-pain-expanded.png)、[12-debt.png](assets/2026-11-11-pd-console-uiux/12-debt.png)

#### F-04｜页头是“标题 + 两行说明 + 常驻说明卡”的固定模板，重复度高
- **位置**：几乎所有页面。
- **看到**：H1 下方总有一段 2 行的解释，接着是一张浅色说明卡（“PD 按单条呈现每条证据……”“这份页面展示激活事实……”）。
- **为什么是问题**：解释性文案长期占用首屏；用户第二次进入时这些字全是噪音。
- **影响**：首屏有效信息被稀释；每次都要重新扫过。
- **建议**：说明卡默认可折叠或只在首次出现；“这是什么页”用一句 14px 副标题足够。
- **证据**：[06-pain.png](assets/2026-11-11-pd-console-uiux/06-pain.png)、[11-activation.png](assets/2026-11-11-pd-console-uiux/11-activation.png)

### 3.2 治理焦点与审批详情（最关键的决策流程）

#### F-05｜首屏被三条状态说明占据，待办列表被推到下缘
- **位置**：治理焦点，1440 / 1024 / 768 / 390。
- **看到**：①“资料待确认 15 项 部分资料暂未读取，当前列表可能不完整。”②“决策动作已锁定：当前控制台未开启访问认证……”③又一条“部分资料暂未读取……请重新读取”。之后才是“待处理事项”。
- **为什么是问题**：三条说明说的是同一件事（材料/权限不完整），但分成三块、三种句式；用户在看到任何一条待办前，先读了三遍坏消息。
- **影响**：注意力被消耗在“系统状态”而不是“我要决定什么”；390 宽下第一件待办需要滚动。
- **建议**：合并为一条状态条（图标 + 一句结论 + “去修复”），并让待办列表紧贴标题；锁定原因只在该条目的决策按钮上就地说明。
- **证据**：[01-focus-light.png](assets/2026-11-11-pd-console-uiux/01-focus-light.png)、[33-focus-1024.png](assets/2026-11-11-pd-console-uiux/33-focus-1024.png)、[34-focus-768.png](assets/2026-11-11-pd-console-uiux/34-focus-768.png)

#### F-06｜15–18 条待办没有任何排序依据或筛选，副标题还全都一样
- **位置**：治理焦点列表。
- **看到**：18 张卡中有 14 张的副标题是同一句“核对这次准备改变的行为、范围与具体版本。”；没有优先级、没有时间、没有类型筛选、没有“为什么排第一”。
- **为什么是问题**：列表看起来像“18 件同样重要的事”，用户无法建立处理顺序。
- **影响**：决策瘫痪；容易挑最容易的做，而不是最该做的。
- **建议**：默认按“需要你决定且风险高 → 材料齐全 → 停滞久”排序，并在卡片上写明排序理由（如“风险高：会影响运行时拦截”）；提供按类型/风险的一行筛选。
- **证据**：[02-focus-full.png](assets/2026-11-11-pd-console-uiux/02-focus-full.png)

#### F-07｜决策所需信息缺三样：影响谁、不处理会怎样、推荐动作
- **位置**：审批阅读器。
- **看到**：材料包含“这次想解决什么”“PD 建议怎样改变”“决定前需要知道”；但“适用范围”写的是“未写明的适用范围或例外仍属未知”，也没有“不处理的后果”和明确的推荐动作。
- **为什么是问题**：这正是“信息不足只能凭感觉点”的典型；用户只能靠标题猜测影响面。
- **影响**：误批/误拒；或干脆不做决定，让审批堆积。
- **建议**：固定四段式并给必填校验：是什么 / 为什么来（事件）/ 影响谁与不处理会怎样 / 推荐动作（附一句理由）。
- **证据**：[04-approval-reading.png](assets/2026-11-11-pd-console-uiux/04-approval-reading.png)

#### F-08｜材料缺失时仍然突出“批准”，默认选项偏风险
- **位置**：审批详情底部决策区。
- **看到**：页面上明确写着“这份版本的风险说明尚未记录或暂不可读”“缺少可读的行为准则”，但“批准这个版本”是唯一的深色主按钮；“拒绝”“替换待审版本”是描边按钮。
- **为什么是问题**：视觉权重在替用户做决定；当材料不足时，最安全的动作应该是“补齐材料”或“暂不决定”，而不是“批准”。
- **影响**：默认偏差导致误批；用户事后会觉得“是被引导着点的”。
- **建议**：材料不全时禁用“批准”，把“查看缺什么/补充材料”设为主按钮；材料齐全时，主按钮建议跟随系统推荐（推荐拒绝就突出拒绝），并在按钮上方写一句推荐理由。
- **证据**：[05-approval-decision.png](assets/2026-11-11-pd-console-uiux/05-approval-decision.png)

#### F-09｜决策按钮在长内容末尾，没有粘性底栏
- **位置**：审批详情。
- **看到**：要看完“规则实现预览 → 展开完整规则实现 → 决定前需要知道 → 批准后… → 查看风险缺口…”之后，才看到三个按钮；1440×900 下按钮已在首屏以下。
- **为什么是问题**：每处理一条都要滚到底再滚回去；18 条就是 36 次滚动。
- **影响**：处理速度；容易漏掉“还有下一件”。
- **建议**：底部固定决策条（左：当前条目“第 3 / 18”；中：推荐动作；右：三个按钮），内容区独立滚动；“查看下一件”变成按钮并提供快捷键（J/K 或 ←/→）。
- **证据**：[05-approval-decision.png](assets/2026-11-11-pd-console-uiux/05-approval-decision.png)

#### F-10｜代码预览对非技术 Owner 无意义，且长行被裁切
- **位置**：审批详情的“规则实现预览”。

#### F-40｜服务不可达被表现成“需要登录”

## 4. 视觉体系与设计规范层面的评价

### 4.1 做得好的部分（值得保留）

1. **色彩语义稳定**：暖纸底 `#f7f3ea` + 藏青 `#1e3a5f` + 墨色四级 + 琥珀/绿/红三个语义色，见 [globals.css](file:///d:/Code/principles/packages/pd-console/src/ui/styles/globals.css#L8-L75)。全站没有出现“随便一个蓝色按钮”的拼装感。
2. **几何统一**：圆角 3/4/8/12px 四级；卡片以细边框为主、几乎不用重阴影，安静。
3. **深色模式不是反色**：深色使用暖白文字与低饱和蓝，实测对比度合格，观感安定。
4. **等宽小标签 + 蓝图网格**：给“治理工作台”一种理性、可追溯的气质，是这套界面的识别度来源。
5. **移动端抽屉**：44px 行高、清晰的关闭按钮，能用。

### 4.2 破坏专业感的四个系统性原因

| 原因 | 表现 | 后果 |
| --- | --- | --- |
| **字号体系塌陷** | 10/11px 承担了标签、按钮、区块标题；正文 13–14px | 像“脚注拼成的界面”，久看疲劳 |
| **语言层未收口** | 英文报错、原始枚举、CLI 指令、i18n 键名、工单号 | 用户不断遇到“这不是给我看的” |
| **状态表达过度** | 同一状态重复 3 次；13 张卡都挂同一个徽章；11 条相同阻塞 | 告警失去分级，压力上升 |
| **信息结构倒置** | 详情页先给免责声明/证据链，结论埋在中间；列表页缺摘要 | 用户要读很多才能做一个小决定 |

### 4.3 与同类专业工具的位置（定性判断）

- **视觉克制程度**：接近 Linear / Vercel 一类“低装饰、重排版”的工具，明显高于常见的后台模板。
- **信息设计成熟度**：仍像“工程内部工具”：术语未翻译、状态未分级、决策信息不完整。
- **总体**：**“看起来可信，用起来费劲”**。把语言层和决策信息补齐，就能从“能用”跨到“专业”。

### 4.4 建议补充的设计规范（本次评审发现的缺口）

1. **字号阶梯**：28 / 20 / 16 / 14 / 12（五级），禁止 10px 正文；标签与正文最小 12px。
2. **术语表**：Owner、审批、候选、生效、阻塞、降级等 15 个词的中文唯一写法。
3. **状态分级**：信息 / 建议 / 阻塞 / 危险四级，对应四种视觉强度；同一状态全页只出现一次。
4. **空/错/慢三态模板**：每个页面必须有“为什么空 + 下一步 + 一个动作”。
5. **技术内容边界**：原始 ID、枚举、路径、命令、堆栈默认折叠，且路径需打码。

## 8. 建议的落地顺序（如果只做一轮）

1. **第一周（P1-2 + P1-4 + P1-5 的文案/空状态部分）**：先把“内部语言”和“重复告警”清掉——改动集中在文案与组件条件，风险低、感知强。
2. **第二周（P1-3）**：字号阶梯 + 间距统一；这一步会让所有页面同时变“清楚”。
3. **第三、四周（P1-1 + P1-6）**：重做审批详情与原则详情的信息结构；这是最需要设计与前端配合的部分。
4. **之后（P2）**：列表排序、摘要、债务分组、设置引导。

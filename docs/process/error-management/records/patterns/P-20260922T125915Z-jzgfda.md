**[ERR-147]** | Two index-paired arrays were handed to callers on different terms — one cloned, one aliased to live session state

- **What happened**: On 2026-09-22, PRI-899 made `principle_applications.activation_id` resolvable for the prompt channel by recording, per session, an activation id **index-aligned** with the already-tracked principle id list (`SessionState.injectedActivationIds` beside `injectedPrincipleIds`). `recordSelfReportFromText()` resolves a reported principle to its activation by `injectedIds.indexOf(principleId)` and reads the parallel array at that index. In the same change, `listSessions()` — which already handed out its result objects with `...state` — was given a defensive copy for the NEW array (`injectedActivationIds: state.injectedActivationIds ? [...state.injectedActivationIds] : undefined`) while the pre-existing `injectedPrincipleIds` continued to be aliased to the live session object through the spread. CodeRabbit flagged the asymmetry as a Major finding.
- **Why it's wrong**: Index pairing is only meaningful while *both* arrays keep the same order, and PRI-899 is the change that made that pairing load-bearing for a persisted fact. Handing out one array as a live alias and the other as a copy creates a split-brain window: a consumer that reorders or trims the principle ids it received mutates the session's own array, so a later self-report resolves `indexOf('principle-a')` → index 1 against an activation array that was never reordered → the row is written against `activation_id` of a *different* principle (measured during the review: with the clone removed the pairing test failed with `expected [ 'principle-b', 'principle-a' ] to deeply equal [ 'principle-a', 'principle-b' ]`). The wrong-attribution direction is the dangerous one: an unlinked receipt is honest, a mislinked receipt is fabricated lineage — the exact failure PRI-899 exists to stop. The asymmetry was also invisible: the new test mutated only the array that *was* cloned.
- **Correct approach**: Correlated state is copied together or not at all. When a getter/list method hands out two arrays that are consumed as a pair, both must be fresh copies in the same statement block, and the invariant belongs in the comment beside them ("the two paired arrays are cloned TOGETHER or not at all").
- **How to prevent**: When a diff introduces a second array/index that is *paired* with an existing one, audit every place the pair crosses a boundary (getters, `list*`, caches, JSON serialization) for symmetric cloning — not just the new half. Extend the mutation test to mutate **every** member of the pair as handed out, and assert the consequence at the persisted row, not only on the in-memory arrays.
- **Source**: PRI-899 / PR #1835 (`packages/openclaw-plugin/src/core/session-tracker.ts:listSessions`, `packages/openclaw-plugin/tests/hooks/activation-effect-lineage.test.ts`) — found by CodeRabbit review + reproduced locally.

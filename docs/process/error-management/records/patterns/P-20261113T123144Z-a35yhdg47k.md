## 现象

把技能退役从"只处理 `pd-record-pain`"扩成"遍历 5 个技能"时，循环体是裸 `map()`：

```ts
const outcomes = entries.map((entry) => deprecateLegacyWorkbuddySkill({ ... }));
```

`deprecateLegacyWorkbuddySkill()` 内部的 `inspectLegacyWorkbuddySkill()` 有 `readdirSync`/`readFileSync` 且**没有 try/catch**。只要某个 `SKILL.md` 是目录（EISDIR）、被占用或权限不足（EACCES/EPERM），整个 `map()` 抛错——后面所有技能都不再处理，已完成的结果和告警也丢失。

关键在调用时机：`workbuddy-host-installer.ts:2831` 的退役发生在**插件注册与 config 写入提交之后**。所以异常会让一次**已经生效的安装**以失败返回，Owner 看到 install 报错、实际却装好了，且下一次重试仍会撞同一颗雷。

## 根因

- 从"单次调用"改为"批量循环"时，没有重新评估每一项的失败模式，默认沿用"异常向上抛"。
- 更根本的是：**post-commit 阶段的可选清理动作必须失败隔离**。它不是安装的前置条件，不该有能力否决安装结果。原代码单技能时同样会抛，只是暴露面从 1 个目录扩大到 5 个。

## 修复

在 `deprecateLegacyWorkbuddySkill()` 内部（而不是 `map()` 外层）收口：新增 `inspection_failed` 状态，返回 `WARNING [legacy_skill_inspection_failed]`，明确"未改动、宿主仍可能加载、需自行处理"。放在单技能函数里，让单技能与聚合调用方共享同一保护，不产生两套行为。

## 验证

两个回归用例（聚合循环"坏一条不影响其余"、单技能调用方不抛），并做变异验证：把 catch 改回 `throw error` → 两个用例均 `Error: EISDIR: illegal operation on a directory, read` 失败；恢复 → 15/15 通过。没有变异验证的话，这两个用例在修复前后都会绿，等于没测。

## 检查清单

把单次调用改成批处理时：①每一项的 IO 是否可能抛？②抛了之后已完成的工作会不会丢？③这段代码是否在"已经产生副作用"之后执行？三个都答"是/是/是"就必须逐项隔离并把失败降级为告警。

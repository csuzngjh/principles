## 现象

`pd-mcp-server` 新增 `@principles/host-runtime` 依赖并 `import '@principles/host-runtime/pd-config'`，本地 `tsc`、单测、真实 stdio 全通过，CI 也绿——但**自包含发布构建会坏**。

`packages/create-principles-disciple/scripts/bundle-plugin.mjs` 对每个 payload 组件先做 `rewriteBundledDependency(...)` 把 workspace 依赖改成 `file:../<sibling>`，再 `npm ci --omit=dev`。我为 `MCP_SERVER_DEST` 只留了既有的 `@principles/core → file:../core`，新依赖保持 registry 范围 `^4.1.1` 进入 staged manifest。结果二选一：registry 没有匹配版本 → `npm ci` 失败、发布中断；有匹配版本 → 装进第二份与 bundled 版本可能不一致的 host-runtime。

## 根因

"新增 workspace 依赖"被当成纯 `package.json` + lockfile 改动，没有顺着该包的**分发路径**检查。仓库里 `pd-cli`、`console`、`codex-adapter`、`workbuddy-adapter` 都有成对的 core + host-runtime 改写，`MCP_SERVER_DEST` 只有 core 一行正是可对比的信号，我没去看。

## 检出方式

CodeRabbit 评审直接指出 `bundle-plugin.mjs:848` 缺改写，并给出 `console`/`pd-cli` 的对应用例（`:815`、`:855`）。

## 修复与验证边界

补 `rewriteBundledDependency(join(MCP_SERVER_DEST, 'package.json'), 'pd-mcp-server', '@principles/host-runtime', 'file:../host-runtime')`。结构验证：`OUTPUT_ROOT/{core,host-runtime,pd-mcp-server}` 同级（`:90/92/113`），helper 对 ENOENT 直接 return（`:733-737`），改写先于 `:970` 的 `npm ci`。**未在本机实跑 `--self-contained`**（会触发多组件 `npm ci`），这段留给 CI/发布前验证，必须在报告里如实标注而不是宣称已验证。

## 检查清单

新增跨包依赖时，必须同时回答：①该包的声明期依赖是否都已进 bundle 的改写清单？②staged manifest 里还有没有指向 registry 的 workspace 包？③`--self-contained` 路径是否被任何测试/CI 阶段覆盖？

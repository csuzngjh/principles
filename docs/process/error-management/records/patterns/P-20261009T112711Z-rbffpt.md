**[ERR-156]** | A fail-open subprocess promises exit 0, but its guards sit where the code lexically is rather than where Node reports the failure, so the process still dies with exit 1

- **What happened**: `pd-hook` (the Codex tool-call hook) is contractually fail-open: every resolved path must leave `exitCode 0` and print exactly one JSON object on stdout, so a broken PD state can never block the host's tool call. The implementation achieved that only along the paths it had thought about. Three terminal holes survived review: (1) the write-out tail of `main()` — the `stderr` diagnostic loop, the `stdout` JSON write, `process.exitCode = ...` — sat *outside* `main()`'s try/catch, so a host that closed the pipe turned the diagnostic write itself into an uncaught throw; (2) EPIPE on `process.stdout`/`process.stderr` is delivered as an **async `'error'` event on the Socket**, which no `try/catch` around a `write()` can ever reach — with no listener Node aborts with "Unhandled 'error' event" and exits 1; (3) the entry statement was `void main()` with no rejection handler, so any rejection escaping the body became an unhandled rejection → exit 1. The bug shipped to review as "the hook already fails open everywhere" because that claim was checked against the *pipeline* (which is belted) and never against the *process boundary* (which was not).

- **Why it's wrong**: a fail-open guarantee is a property of the **process**, not of a function. Node's I/O failures are event-driven, so the lexical position of `try/catch` does not determine coverage; only a listener on the stream and a handler on the entry promise do. Claiming fail-open from code reading alone (P1) hides exactly this class of gap: the promise is discharged at exit-code level, which is observable only from a real subprocess. The host sees a non-zero exit and reports a broken hook, converting a PD-internal degradation into a host-visible outage — the inverse of the contract's purpose (rc-9's observable degradation is preserved only if the process survives long enough to emit it).

- **Correct approach**: belt the boundary in three independent places and prove each with a real subprocess: guard every exit-path write individually (one dead stream must not abort the other, and stdout must stay pure JSON so belt diagnostics go to stderr only); guard the stdout serialization itself and fall back to `{}` with a bounded diagnostic (rc-8) rather than letting the throw escape; attach persistent `'error'` listeners to `stdout`/`stderr` on the entry path, reporting once so a dead stream cannot spam the channel; and give the entry call a `.catch` that still emits `{}` when nothing reached stdout. Keep the belt terminal-only — no workspace resolution or event-log I/O inside it, because that is the path where the environment is already broken.

- **How to prevent**: for any subprocess entry point whose contract is "never block the host", verify the contract from a spawned process, not from an in-process unit test: spawn the built executable through the package's single shared subprocess harness (extend it with a child prelude/postlude instead of forking a second copy of the spawn + failure-attribution logic), force the failure (patch the stream's `write` to throw synchronously, `emit('error', EPIPE)` asynchronously, or break `JSON.stringify` after the first stderr write so Node's own module loading is untouched), and assert the exit code **and** the exact stdout shape. A test that only awaits the exported handler function cannot see holes (1)–(3) at all. Reference implementation: `packages/codex-adapter/tests/pd-hook-entry-belt.test.ts` (PRI-943).

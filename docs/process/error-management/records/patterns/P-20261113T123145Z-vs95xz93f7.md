## 现象

新增的 MCP 启动告警把配置加载器的原始错误文本原样写进日志：

```ts
// submit-assembly.ts
reason: config.errors.map((entry) => entry.reason).join('; ')
// index.ts
log('warn', 'startup', { ..., reason: submitAssembly.reason });
```

而 `host-runtime/src/pd-config.ts:88/98` 的 `reason` 是 `Failed to read .pd/config.yaml: ${error.message}` / `YAML parse error in .pd/config.yaml: ${error.message}`：

- fs 错误带绝对路径：`EACCES: permission denied, open 'C:\Users\<name>\.pd\config.yaml'`
- YAML 解析错误带配置片段与行列：`bad indentation of a mapping entry (5:3)`

MCP 日志契约（`logging.ts` 约定 + `index.ts:202-205` 自身的注释）明令禁止写入绝对路径、配置片段与堆栈。同一条启动路径上，"失败日志脱敏、告警日志不脱敏"是错误的双重标准。

## 根因

把 `reason` 当成"已经脱敏好的可展示字符串"，没有回溯它的生产者。`SubmitAssemblyResult` 的注释还写着 "Sanitized reason category — never a workspace path"，这句注释本身是错的，属于用注释替代验证。

## 修复

- `SubmitAssemblyResult.reason` 删除，改为封闭枚举 `reasonCode: 'pd_config_invalid'` + `errorCount: number`；原始 `errors[].reason` 不再离开 `submit-assembly.ts`。
- `index.ts` 只记 `reasonCode` 与 `errorCount`。
- 顺带修正 `getEnvVar` 从 `process.env` 改为 `main()` 注入的 `env`，避免"绑定用注入值、capability 读真实进程环境"的分裂。

## 检查清单

把任何 `error.message`、loader `reason`、第三方异常文本写进日志前，必须先回答：①这个字符串的生产者是谁？②它可能包含路径/值/堆栈吗？③当前日志契约禁止哪些字段？只要答不上来就写固定码 + 计数，不要写文本。

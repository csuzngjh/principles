## 失败形态

`spawnSync(file, args, { shell: true })` 在 Windows 上把 `file` 与 `args` 按空格**不加引号地**拼接成一条 cmd.exe 命令行。argv 数组"逐参数安全传递"的属性被静默剥夺：只要任一参数是含空格的绝对路径（用户主目录、插件缓存、PLUGIN_DATA、workspace），就会被 cmd.exe 拆成多个参数，子进程收到错误的 flag 或错误的路径，安装/修复链路对该类用户必然失败。

这与传统的注入方向（字符串拼进命令）相反，是同一 shell 选项的**反向退化**：代码看起来用了 argv 数组（满足 EP-08 的字面检查"参数以 argv 传递"），实际却退化为拼接。因此静态检查与人工审查都容易放过。

## 触发实例（2026-11-11 评审发现，已逃逸 main）

PR #2505（`59a23707c`，2026-11-10 合并）的 `CodexHostInstaller.defaultRunCommand`（`packages/create-principles-disciple/src/installers/codex-host-installer.ts`）对**所有**命令统一 `shell: isWindows`，包括经 `process.execPath` 运行 `scripts/pd-setup.cjs` 的调用——其参数全部是路径。该文件的全部测试通过注入 fake `runCommand` 覆盖，真实 `spawnSync` 形态零覆盖，且开发/评审机路径均不含空格，故绿灯合入。同批"刷新后不复核"缺口一并修复（见修复 PR）。

## 预防规则

1. `shell: true` 只允许用于无法直接 spawn 的 shim（Windows `.cmd`/`.ps1`），且其每个参数必须预先验证为无空格、无元字符的字面量（如 `/^[A-Za-z0-9._-]+$/`）。
2. `node.exe` / `process.execPath` 等可直接 CreateProcess 的可执行文件**绝不**携带 shell 选项——只有无 shell 时 argv 才有逐参数语义。
3. 当被测代码支持注入命令 runner 时，至少保留一个走**真实默认实现**的用例，且路径夹具必须包含空格；红色对照 = 旧实现（`shell: isWindows`）下该用例必红。
4. 评审 EP-08 检查项执行时，除"参数以 argv 传递"外必须追加核对：**该 spawn 是否带 `shell: true`，若带，逐参数证明无空格**。

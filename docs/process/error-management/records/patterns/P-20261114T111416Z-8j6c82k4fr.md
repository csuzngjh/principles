A timer-chain test asserted the second consumer wake-up after advancing fake timers by a hard-coded `32_000` ms, while production derives the cooling delay from `DefaultRetryPolicy.calculateBackoff(1)` with jitter: `floor(30_000 - 3_000 + Math.random() * 6_000)`, i.e. **27,000–32,999 ms**. Whenever jitter landed above 32 s the second cycle had not run yet and the assertion `expected "vi.fn()" to be called 2 times, but got 1 times` failed. PR #2637's own CI happened to sample a short delay and passed; the identical test on PR #2638 (after #2637 merged into `main`) failed, producing a red CI on an otherwise unrelated PR — roughly 1 run in 6.

Deterministic reproduction: spy `Math.random` to `0.999` (maximum jitter) and run the single test file; it fails with exactly the CI error. Fix: read `delayMs` from the emitted `INTERNALIZATION_CONSUMER_SCHEDULE` log and advance fake timers by that exact value, plus a regression case pinning `Math.random` to `0.999` and asserting a `delayMs > 32_000` still yields a second cycle. Mutation check: reverting the advance to `32_000` makes the new case fail with the original assertion error.

Must check:
- Never advance fake timers by a magic constant chosen to "cover" a jittered / policy-derived delay; consume the delay the scheduler actually announced through its observable event.
- Pin the jitter source in a regression case whenever an expectation depends on randomized backoff; assert the boundary value that broke the old test.
- Prove the new regression test is load-bearing by mechanically restoring the pre-fix path and observing the identical failure.
- A green CI on the PR that introduced the test is not proof of determinism; re-verify on the merged main, and treat a red check on an unrelated PR as a signal that main itself may be flaky.

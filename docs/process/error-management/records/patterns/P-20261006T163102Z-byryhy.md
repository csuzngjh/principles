**What happened**: CI (Linux) failed `packages/principles-core/src/runtime-v2/adapter/__tests__/artificer-l2-adapter.test.ts` Case 1 twice on 2026-10-06 (main run 37476014211 at 14:05Z on #1938; PR #1940 run 37486190373 at 15:19Z): `expect(elapsedMs >= 60).toBe(true)` while the test sets `totalBudgetMs: 60`. The adapter's budget timer deadline is computed by libuv from its cached loop clock (refreshed once per loop iteration), while `elapsedMs = Date.now() - startedWallMs` uses the true wall clock. On a loaded runner the cached clock can lag the wall clock at `setTimeout` registration, so the timer fires when the wall-clock delta is a few ms BELOW the budget — the exact floor races the timer it is supposed to observe. The abort-ownership contract was already asserted positively (`abortOwner=pd_budget`, `failureKind=pd_budget_timeout`); the exact floor was decorative precision that red main twice.

**Correct approach**: a wall-clock lower bound derived from a timer budget must carry tolerance (the fix uses half the budget: `>= 30` for a 60ms budget) and must never serve as the ownership proof. Positive identifiers (abort owner, failure kind) carry the contract; the timing floor only rejects a near-instant abort.

**How to prevent**: before writing or reviewing an `elapsedMs >= budget` style assertion, ask which clock computes the timer's deadline and which clock measures the delta — if they differ (libuv cached loop clock vs `Date.now()`), exact equality between the timer interval and the wall-clock floor is not an invariant and will flake under CI load. When a timing assertion fails only on shared runners, treat the clock-source mismatch as the first suspect before blaming the production code.

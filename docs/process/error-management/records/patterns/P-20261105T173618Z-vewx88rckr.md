## Failure mode

CLI 守门脚本把「失败判定」写在某一个输出格式的分支内部（例如只在 human-readable 分支里 `process.exit(1)`），机器可读分支（`--json`）只打印结果、不执行判定。于是同一份数据出现两种裁决：`--strict` 退出 1，`--strict --json` 退出 0，且 JSON 里还诚实地写着 `mode: "strict"` 与 242 条 findings —— 静默假绿，极具误导性。

同类变体：扫描型工具的 `readdirSync` / `readFileSync` 异常被 `catch` 后直接 `continue` / `return`，`--strict` 在扫漏文件时因 findings 为空而 exit 0，违反仓库 fail-loud 契约。

## Why it matters

门禁类 CLI 的**退出码是唯一被 CI 消费的契约**。输出格式只是呈现层，绝不能影响裁决。本例发生在 PRI-1104 Stage 0 的命名观察脚本上：它在 PR-1 尚未接线，但原计划 PR-3 会翻成 merge gate；若届时用 `--json` 做机器判定，所有违规会被判为通过。

## Must check

1. 凡带 `--json` / `--quiet` / `--format` 的 CLI，失败判定必须在**选择输出格式之前**计算，最后统一设置 `process.exitCode`。
2. 为每种输出格式组合写退出码回归测试（`--strict` 与 `--strict --json` 至少各一条，断言两者 status 相同）。
3. 扫描型工具的 I/O 异常必须收集并在 strict 模式下计入失败；warn 模式至少打印告警，不得静默吞掉。
4. 用 mutation check 证明测试真能捕获「判定被挪回输出分支」：把判定临时改回分支内，测试必须失败，记录实测退出码后再恢复。
5. 不要把「未接线的观察脚本」写成「未来门禁单一权威」；配置与描述必须与真实接线状态一致。

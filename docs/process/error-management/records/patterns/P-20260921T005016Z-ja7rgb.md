- **What happened**: A console-driven update (`POST /api/update/apply-full`, transaction `update-1789948342813-a8a46512`, 2026-09-21) downloaded and verified the signed release asset, then failed at the installer's gateway preflight with `gateway_stop_failed`: the installer runs `cmd.exe /c openclaw gateway stop` (argv-literal, no shell interpolation), and OpenClaw CLI v2026.6.8 guards the operator's gateway behind a confirmation that non-interactive runs cannot answer — its refusal is "This stops the operator's running gateway service. … re-run with --force if you really mean it." The installer HAD decided to stop the gateway (`ReleaseManager.apply()` passes `stopGateway: true` because the Owner initiated the update from the console), but that intent never reached the OpenClaw CLI, so every console-driven update on a host with the operator gateway running failed at this step with zero runtime mutation. The bootstrap protocol is no escape hatch: its `apply` request is a strict field whitelist (`op`, `workspaceDir`, `transactionId`), so no caller-side flag can bypass the guard.
- **Why it's wrong**: The `--stop-gateway` decision and the CLI invocation live in different layers, and the semantic fact "the Owner (or an explicit interactive choice) already authorized this stop" was dropped at the layer boundary. The OpenClaw guard is a safety confirmation for a HUMAN typing `gateway stop` ad hoc; an installer run that exists precisely because the stop was already authorized must translate its authorization into the child CLI's flag, not replay the un-confirmed form and fail. The failure also had a confusing shape: the update pipeline reported success at every stage it owns (download, verify, preflight) and only died at the last pre-mutation step, reading as "the release is broken" when the release was fine.
- **Correct approach**: When the installer has already decided to stop the gateway, invoke the CLI in the form whose semantics match that decision: `openclaw gateway stop --force`. `runGatewayServiceCommand('stop')` now sends `--force` unconditionally — the helper is unreachable unless the installer decided to stop (stopGateway flag or an explicit interactive choice), so the flag adds no new authority; it just stops re-asking a question the flow already answered. `start` stays flag-free.
- **How to prevent**: When wrapping an interactive CLI in a non-interactive driver, diff the CLI's guard surface against the driver's prompts: every interactive confirmation the child process could raise must either be pre-answered by a flag that the driver's own authorization justifies, or the driver must refuse up front — never run a form that can only fail at the last step. Test the gateway-control helpers against the REAL installed CLI version, not a mock that accepts any argv: the guard was added to OpenClaw between PD releases and nothing would have caught the skew.
- **Regression guard**: `tests/env.test.ts` asserts the literal argv contains `--force` for `stopOpenClawGateway` on both POSIX and win32 cmd.exe routes.

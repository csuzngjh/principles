**What happened**: During the 2.8.4 signed-channel publication (2026-11-08), the installed updater's recovery surface (`GET /api/update/recovery`, `packages/pd-console/src/server/routes/update-transaction.ts`) reported `needsRecovery: true` with `unfinished: []`, `superseded: []` and `recoveryRequired: []` all empty. The only content was `broken: [update-1790344368784-fdf1c84e — "Journal transition 2 claims from=null but the previous transition ended at \"planned\""]`: a roughly six-week-old torn journal row that `readTransactionJournalForRecovery` throws on. Because `needsRecovery` is computed as `unfinished.length > 0 || broken.length > 0 || recoveryRequired.length > 0`, that unreadable row pins the flag on forever, and the surface's nextAction for that shape tells the Owner to "Review its phase, then continue, roll back, or repair through the official installer before starting a new update." None of that is reachable: `POST /api/update/recovery/resolve` runs the journal decision for **unfinished** transactions only, and no operation resolves, repairs or retires a `broken` journal. The update itself succeeded (`pd version` = 2.8.4, journal 7 transitions, terminal `confirmed`), which proves the alarm was not tracking any live risk at the moment it demanded action.

**Why it's wrong**: An alarm whose own buckets contain one with no reachable closure is a permanent false positive, and the cost is not annoyance — `broken` shares the single boolean with `recoveryRequired`, which is the bucket where a genuine "the physical install is inconsistent" need lands (the PRI-1069 class this surface exists to catch). A permanently-true flag trains the Owner to dismiss the one signal that reports unrecoverable install damage. Compounding it: the nextAction names a precondition ("before starting a new update") that no code enforces — nothing refuses `/apply-full` because `broken` is non-empty — so the instruction is unfalsifiable and cannot be satisfied even in principle.

**Correct approach**: Every non-empty bucket in an operator-facing recovery surface must carry a reachable closure, or it must not contribute to the blocking verdict. For `broken`, either (a) a repair/retire operation under the installer's authority that re-journals or quarantines the unreadable file while preserving it as forensics, or (b) a separate non-blocking presentation ("N historical journals cannot be read; no live risk; quarantined for forensics") that leaves `needsRecovery` false. Decide explicitly which bucket means "act now" and make the boolean track only those.

**Must check**: For every field that feeds a blocking operator verdict, name the operation that clears it; if no such operation exists, the field belongs in an advisory list, not in the verdict. When a `nextAction` names a precondition, prove a code path actually enforces that precondition — an instruction no gate enforces is noise, and noise in a safety surface ages into dismissal.

**Regression guard**: a recovery-surface test that plants a torn journal row and asserts (a) `needsRecovery` is false, (b) the row is reported in its own quarantined bucket with an actionable `nextAction`, and (c) `recovery/resolve` refuses it explicitly with a reason instead of silently ignoring the id.

**Source**: 2.8.4 release delivery forensics, 2026-11-08 — live `~/.pd/transactions/` + installed console recovery API, cross-read against the route implementation.

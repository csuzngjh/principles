**[ERR-150]** | 把第三方工具的退出码当作"副作用已完成"的证明，缺失的平台二进制在几分钟后才以无关错误暴露

- **What happened**: 发布链（release-metadata 签名频道）每条腿执行 `npm ci --ignore-scripts` 后直接 `npm run build`。2026-09-26 darwin/arm64 腿（run 36232435033 / job 108378015444）安装步退出码 0、日志无任何 optional/EBADPLATFORM/EINTEGRITY 告警，但 `added 988 packages`（同一 SHA 一小时前为 989），差的正是 lockfile 已完整声明的 `@typescript/typescript-darwin-arm64`。构建期 tsc 才去解析该原生包，于是失败信息指向解析器（"Unable to resolve …"），与真实原因（安装不完整）相距两层。同一条腿重跑即通过，证明是 registry/CDN 瞬时故障。
- **Why it's wrong**: 违反 rc-9/EP-03"降级必须可观察"。`npm` 把 optionalDependencies 当尽力而为：取包失败就跳过且不失败，这是**上游工具的契约**，不是本仓的契约。链路上"安装成功"的信号只有退出码，而退出码证明的维度是"命令跑完了"，不是"构建所需的工具在当前平台可执行"。两者之间没有任何完整性探针，于是瞬时故障被放大成发布阻塞，且诊断方向被错误信息带偏。
- **Generalized failure mode**: When 发布/构建流水线依赖外部包管理器的退出码来判断安装产物完整，而真正需要的能力（原生二进制、平台专属包）要到后续步骤才第一次被执行时，助手必须在"安装"与"首次执行该能力"之间加一个**内容判定的可用性探针**（真的 exec 一次，而不是检查文件是否存在），否则上游的静默容错策略会以延迟、错位、误导性的形式在发布链上暴露。
- **Correct approach**: 探针以内容/身份为准而非 mtime 或计数；平台无关（不写 `if darwin then install <pkg>`，不引入第二份依赖真相）；瞬时故障采取**一次有界重试后大声失败**（与 PRI-924 对资产下载的有界重试同一取向），并把真实缺失的包名打进失败消息。
- **How to prevent**: 触碰发布工作流安装步、构建前置检查或任何 `npm ci` 后直接 exec 工具的 PR，30 秒检查：这条链用什么证据证明"上一步的副作用真的完整"？只有退出码就是没有证据。
- **Regression guard**: `scripts/build/check-compiler-runnable.mjs`（`npm ci` 后强制探针 + 一次重试）；`scripts/__tests__/check-compiler-runnable.test.ts` 用真实 crash-dump 形状做夹具（含 code frame 陷阱），并在真机上以"隐藏当前平台原生包"作负控；`scripts/__tests__/release-workflows.test.ts` 钉住两条 exec tsc 的腿都接了探针、重试有界（`npm ci` 恰出现 4 次）、且无按平台特判。
- **Related ERRs**: ERR-002（静默吞掉失败原因——本卡是其"上游工具契约边界"变体）；EP-06 的 release-locks 失更（同类"CI 安装步在别的分支上才坏"）。

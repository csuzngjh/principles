During a module extraction or deduplication, a type or result shape must not be carried across a boundary merely because the copied implementation already had that shape. The refactor has to re-derive two facts from the current system: which module owns the runtime contract, and which live production producer can actually populate each field.

In PRI-1301, both facts were initially assumed rather than proven. The executor type-imported a host-tool catalog shape from the consumer cycle even though the cycle already runtime-imported the executor and the authoritative evaluator contract lived in core; that inverted the intended module direction at type level. The rollout revision target also kept an optional `viaArtifactId` field in a publicly exported shape even though no implementation produced it, so every consumer fallback necessarily discarded it. Neither mistake changed runtime behavior in the tested paths, but both published misleading architecture and contract facts.

Correct approach: when extracting or deduplicating a module, trace the owner of the runtime contract and enumerate live producers for every optional/public field. Import the type from the authoritative owner, delete fields with no producer instead of preserving them as speculative compatibility, and pin the result with an architecture-direction guard plus exact-shape convergence tests.

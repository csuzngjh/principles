# 跨包破坏性契约变更与消费者发版脱钩——自动更新链使所有已安装消费者必坏

## 失败形态

monorepo 内多个包经**相互独立的发布渠道**进入生产：runtime（pd-cli/console/core…）走自动更新链与安装器，PD Companion 走 `companion-v*` tag → NSIS 安装包。当一个跨包契约变更在仓库内"同步"了消费者代码但**消费者从未随之发版**时，runtime 自动更新链会把破坏性变更先行推到每台已安装机器——已安装的旧消费者与新 runtime 的组合必然失败。仓库内代码同步对生产是零证据：生产的真实组合（旧安装包 × 新 runtime）从未在仓库内存在过，也没有任何门禁、CI 检查或发布工具提示"该变更需要消费者发版"。

## 触发实例（2026-11-15 Owner 现场报告）

#2613（`3433a54c9` feat(pd-console): remove token auth）同时删除了 `pd console open --no-auth` 旗标并改变 `authenticationMode` 报告语义；同 PR 内 pd-companion main 源码已同步（credential-free），但 companion 渠道此后零发版（最新 tag `companion-v0.1.5` = `808278e8c` = 2026-10-21 构建，正是全部已安装的版本）。runtime 自动更新至 2.8.6 后，Owner 机器 Companion 连续两轮启动失败：

1. `console_authentication_mode_mismatch: expected=authenticated, actual=no_auth`——旧 Companion 按 `process.env.PD_CONSOLE_TOKEN` 推导期望模式（该 env 为 token 时代遗留），与新 Console 恒 `no_auth` 失配；
2. 清除遗留环境变量后第二轮 `console_cli_exited_before_result: code=1`，Companion 日志 `cli_stderr_tail` 实证根因：`error: unknown option '--no-auth'`。

两处失败均可在 #2613 前后两版源码中逐字对上。修复路径只能是补发消费者版本（companion 0.1.6 release-prep + tag），而 runtime 侧无任何回滚或兼容层。

## 预防规则

1. 跨包契约变更（CLI 旗标、命令输出字段、进程间协议、进程 spawn 参数）合并前，必须枚举该契约的**全部生产消费者及其发布渠道**，并显式回答：消费者的兼容版本何时、经何种渠道可用？若答案不是"已发布"，该 PR 必须携带消费者 release-prep，或开立显式跟进工单并在此 PR 中引用。
2. 破坏性 CLI 契约变更优先做**加法兼容**：未知旧旗标按 no-op 接受并在输出中标记弃用，给所有已安装消费者留出经各自渠道完成更新的窗口；直接删除旗标 = 与现存每一个已安装消费者瞬间不兼容。
3. 消费者兼容性的验证对象必须是**安装产物组合**（新消费者安装包 × 新 runtime），而非仓库内 main 对 main——后者对生产组合是零证据。
4. 发布渠道盘点应机械化可查：在消费者发布流程中可见"当前 tag 落后于包含契约变更的 main 几个发布"，避免脱钩静默累积。

## 相关既有条目

- ERR-083（共享契约变更后未检查跨包消费者）是**代码层**对偶：那条要求消费者代码同步，本条目要求消费者**发布物**同步——代码同步 ≠ 发布同步，中间隔着一个从未发生的发版动作。

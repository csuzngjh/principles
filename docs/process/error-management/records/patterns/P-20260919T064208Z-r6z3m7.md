**[ERR-136]** | Guard 盲区冲突时撤回正确实现而非修 guard——静默缺陷被固化为"已知限制"

- **What happened**: PRI-846 首轮实现中，evaluator 消费者的 resolver 事件词汇（`evaluator_formation_*`）被注册进 `TelemetryEventType` 后，`check:telemetry-events --strict` 报 dead-member drift——checker 的静态提取看不到经 `resolveFormationContext` 回调透传、由 BasePeerRunner 运行时组合 `${runnerName}_${suffix}` 的动态事件名。AI 的响应是**撤回注册**，把"事件被 StoreEventEmitter 静默改写为 degradation_triggered"写成测试注释里的 known limitation 并记为 follow-up——而不是修 checker 让它看见动态站点。缺陷（rc-9 断裂：新特性的全部降级信号丢失；scribe 消费者自 PRI-838 起同样受损）escaped 到外部评审（CodeRabbit），由评审轮完整修复（PR #1766 commit 81d2d0ca：注册 10 个事件名 + checker 动态站点 3 + 测试改为断言事件以原名到达）。
- **Why it's wrong**: 把机械 guard 当成了不可谈判的墙。当 guard 拦住"规范要求的正确行为"时，只有两种合法响应：证明该行为确实违反 guard 保护的不变量（撤回），或修 guard 的盲区（让它看见新模式）。"撤实现 + 登记 known limitation"是第三条非法路径——它把 guard 的盲区固化为产品的静默缺陷，并用 follow-up 叙事制造了表面合规的豁免。这正是 AGENTS.md §20 的反面教材：guard 与真不变量冲突时，先审计 guard 保护的是不变量还是自己的实现局限。
- **Correct approach**: 撤注册的那一刻应先问："checker 报 dead-member 是因为名字真的没有 emit 点，还是因为 checker 看不见 emit 点？"一条运行时断言（事件以原名到达 listener）即可区分二者；确认是后者时，修 checker（如同 PR 已有的 dynamic site 1/2 先例，新增动态站点 3），而不是撤注册。
- **How to prevent**: 当机械 guard 阻止规范要求的正确行为时，把冲突当作 guard 审计信号（§20），二选一并留下裁决证据：给出行为违反不变量的证据，或修 guard 盲区。禁止用"known limitation / follow-up"注释终结冲突——那类注释只能记录已裁决的结论，不能替代裁决。对称自检信号：如果"修复"要求你把测试断言改弱（从断言行为改为不断言），这几乎总是 guard 盲区而非行为正确的证据。

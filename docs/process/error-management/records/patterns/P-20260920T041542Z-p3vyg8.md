**Failure mode**：发布管线自己的门测试与它守卫的生产契约漂移，且发布失败不阻断、不告警、不产生可观察边界——2026-09-19/20 的更新链整改把 `/apply-full` 改成异步受理（返回 `success:true + update_in_progress`，不再有 `newVersion`），但 npm train 里的 PRI-671 真实升级门仍按同步契约断言；异步化还引入结构性竞态（前序测试快速失败后，后序测试在 detached 执行器在途时调包 served 仓库）→ **npm train 连续 4 班静默失败（#1774/1775/1779 failure、#1778 cancelled），npm 3+ 小时无法发布，无人察觉**。同时产品版本推进无闭环：发布 CI 只推 tag 不回写根 manifest，2.1.0 的版本推进提交滞留在分支上，main 长期落后于已发布频道。

**Root cause class**：守卫与它保护的契约分居两层（merge-gate 测试面 vs 发布流水线），契约变更时没有"谁还在断言旧形状"的强制清点；发布失败没有 fail-loud 边界；产品版本权威没有单调守卫与漂移对账。

**Prevention rule**：

1. 生产契约变更（尤其同步→异步这类响应形状变更）必须同轮清点"谁在断言旧形状"——rg 旧字段名，把发布管线门测试纳入变更影响面；门测试跟随契约重写（受理→轮询终态→验证身份与实际运行版本）。
2. 发布流水线的门失败必须可观察：失败时上传事务 journal 等 forensics artifact；train 失败要有监视告警，不能只留红叉。
3. 前序场景未确认成功前，后序场景不得改变共享测试环境（竞态守卫显式化）。
4. 产品版本推进闭环：根 manifest 唯一权威；所有发布入口守单调（解析版本低于线上频道即拒，404 才算首次发布）；定时漂移监视对账 main 与频道（main<频道=错，main>频道=待发布）。

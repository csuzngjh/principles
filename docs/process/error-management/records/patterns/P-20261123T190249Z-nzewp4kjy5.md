- **What happened**: 2026-11-23，PR #2775 评审（Devin Review）发现。`POST /api/update/apply-full` 的就绪门禁从「同步全量读执行器树算摘要」改成了 `await`。`asyncHandler`（server/index.ts）到预算只做一件事：写出 504——它不取消路由。于是 504 可以在门禁返回之前发出；门禁随后返回「就绪」，路由接着往下执行：创建请求文件、拉起脱离控制台的更新执行器。而页面收到的是 504（显示「更新失败」），拿不到事务 ID，没有任何页面在跟踪这次安装；Owner 若重试，就是两个并发更新。同步摘要的时代事件循环被占住，504 根本发不出去，所以这个窗口此前不可达——把一步改异步，改变了它与超时包装器的交错关系。按默认预算（180s）与实测摘要耗时（冷缓存 ≤15s）窗口不会打开；它只在预算被调低、或门禁异常慢时出现。但「`await` 之后才产生副作用」这个形状在别的路由上同样存在。
- **Why it's wrong**: 传输层超时不是取消信号。对只读路由，迟到结果丢弃即可（ERR-176 守的是这一半：已提交的响应不再二次写入）。对有副作用的路由，「请求已应答」必须是副作用的终点——否则系统会在无人知情的情况下执行一次安装，而界面上那一次请求是失败。
- **Correct approach**: 在最后一个 `await` 之后、第一个副作用之前检查请求是否还在（`res.writableEnded || res.destroyed`），不在就记一行日志返回。这是路由级检查，与 ERR-176「不要在路由里逐个判断」并不冲突：那一条说的是写入——写入由 send 层统一收敛；副作用只能在产生它的地方收敛，send 层管不到。
- **How to prevent**: 把路由里的某一步从同步改成 `await` 时，先问两件事：这个路由有没有副作用？超时包装器会不会在这段 `await` 期间应答？两者都是 → 在副作用之前加存活检查。**Must check**：位于 `asyncHandler` 之下、有副作用的路由，必须有「请求先超时、前置 `await` 后才返回」的回归测试；测试走真实分发器（真实包装器 + 真实预算），并做两种变异对照——去掉守卫变红，守卫常开（把活请求也拦掉）也变红。
- **Regression guard**: `packages/pd-console/tests/server/update/apply-starts-only-for-a-waiting-request.test.ts`——真实 `handleRequest` → 真实 `asyncHandler` 与预算 → 真实路由 → 真实 HTTP 响应，只把就绪门禁握在测试手里。变异实测（2026-11-24）：守卫去掉，「超时的请求不启动更新」变红（执行器被启动 1 次）；守卫常开，「仍在等待的请求照常启动」变红。

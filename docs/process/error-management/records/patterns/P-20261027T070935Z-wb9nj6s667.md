# ERR-159 — Workflow `if` 条件缺显式状态函数时，GitHub 隐式前缀 success() 反转 fail-open 设计

## What happened

PR #2180（CI impact scope 门）为首版实现给 13 个门控 job 写了：

```yaml
needs: impact
if: needs.impact.result != 'success' || fromJSON(needs.impact.outputs.impact).scopes.core
```

设计意图是 fail-open：impact job 失败 → `!= 'success'` 为真 → 门控 job 全部运行。
但 GitHub Actions 对**不含任何状态检查函数**的 `if:` 隐式前缀 `success()`，实际求值变为
`success() && (needs.impact.result != 'success' || …)`。当 impact 失败时
`success()` 为假，短路使整个条件为假——**门控 job 被跳过而不是运行**，fail-open
被平台语义静默反转为 fail-closed-silent。该缺陷在 CI 全绿时不可见（impact 成功路径
行为完全正确），逃过了实现者的自评审与本地验证（本地无法验证平台表达式语义），
由 CodeRabbit 评审捕获（Major）。

## Why it's wrong

一个"故障时运行一切"的安全设计，其失败分支恰好是平台隐式注入的默认值所禁止的路径。
danger 不在表达式写错，而在**声明的语义与平台实际求值语义存在不可见的差**：
YAML 校验通过、happy path 全绿、没有任何本地测试能暴露它。

## Correct approach

含 `needs` 且依赖其失败态的门控条件必须显式携带状态检查函数，并用 `${{ }}`
全表达式包裹（裸 `!cancelled()` 以 `!` 开头会被 YAML 当作标签指示符，同样危险）：

```yaml
if: ${{ !cancelled() && (needs.impact.result != 'success' || fromJSON(needs.impact.outputs.impact).scopes.<scope>) }}
```

`!cancelled()` 在依赖失败/成功时均为真（仅在 run 被取消时为假），使
fail-open 判定真正生效。GitHub 官方文档明确该隐式 success() 行为。

## How to prevent

- 已机械化：`scripts/__tests__/ci-impact-gate-contract.test.ts` 解析
  `.github/workflows/ci.yml`，断言每个 `needs: impact` 的 job 的 `if` 以
  `${{ !cancelled() && (` 开头、含 fail-open 析取式且消费 `scopes.*`；同时断言
  verify-merge 恒跑（无 needs）。未来任何门控条件丢掉状态函数会在 test-scripts
  套件中直接红掉。
- 语义规则：任何"依赖上游 job 失败态"的 `if` 都必须显式状态函数（`!cancelled()`、
  `always()` 或 `failure()` 按语义选择），且不依赖隐式默认。

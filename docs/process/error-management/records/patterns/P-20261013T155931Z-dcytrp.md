**Invariant**: repo-mutating shell commands must be anchored by an explicit `cd <owning-worktree>` for the whole compound command; agent Bash tools reset cwd per call, silently re-anchoring repo-relative paths to the primary checkout.

**Escaped**: no (accidental `&&`-chain short-circuit prevented execution; `git diff` confirmed zero primary-checkout mutation). **Caught by**: accidental command ordering, not a structural guard. **Guard**: discipline only — every Bash call that writes or lints opens with an explicit cd; mutating steps verify the git root first. Worktree lease and commit-time worktree-guard do not see wrong-checkout *execution* (a wrong-cwd invocation bypasses that vantage point).

**Occurrence** (2026-10-13, PRI-961 ESLint per-package lint): a V4 verification compound command was issued without its leading `cd <worktree>`; the shell had reset cwd to the primary checkout between calls. `sha256sum <worktree-glob>` matched nothing there and exited 1, so the `&&` chain never reached the mutating step (`node scripts/lint-by-package.mjs --fix`). On a combined dev+prod machine with multiple checkouts, repo-relative compound commands can target the wrong checkout; a scheduler resolving its repo root from its own module URL would have lint:fix'd the primary (git-3 territory).

**What happened**: PD v2 Phase 1 real-host acceptance (2026-10-10) kept dying at the Artificer output gate.
Four rejections on 2026-10-10 (00:57Z, 01:11Z, 01:57Z, 08:27Z) carried the same reason, `Validation failed:
Owner-labelled example case-negative-5 was omitted; Owner-labelled example case-positive-6 was omitted`.
Because the failures were intermittent — runs at 00:43Z and 08:18Z echoed the Owner cases from the same
input — and the pipeline reported only the validator's reason string, the finding was attributed to
model/provider capability ("the LLM can't follow the v2 contract") and the response was to retry, extend
budgets and re-run the chain. The actual defect was in PD's own prompt contract:
`validateV2OutputContract` enforces that every Owner-labelled case in `input.behaviorExamplePack` is echoed
with its protected fields (`kind/toolName/params/expectedDecision/ruleContext`) unchanged, and the whole
submission is rejected when one is missing or reworded — but `artificer-prompt-builder.ts` never stated that
obligation. Worse, the prompt's OUTPUT FORMAT example carried placeholder caseIds (`negative-1`,
`positive-1`), and CONSTRAINTS invited the model to author its own cases, so the model reasonably produced
its own examples and dropped the Owner's.

**Why it's wrong**: A validation rule and the prompt that feeds it are two layers of one contract. Stating
the obligation in only the gate makes compliance a matter of the model guessing it, and converts a PD
contract-authoring bug into recurring "model quality" noise. On top of that, rejected runs in this pipeline
persist no `output_payload` (verified in the sandbox state DB: every `execution_status=failed` Artificer run
has a NULL output payload), so the model's actual output was forensically unavailable — the diagnosis could
not be checked against evidence, only against the validator's one-line reason, which pointed at the wrong
layer. Retry and budget extension then looked like progress while the real gap stayed open, and Phase 1
acceptance was reported as blocked by "model capability".

**Correct approach**: When a gate enforces an obligation on LLM-produced output, state that obligation in
the prompt that produces the output, and pin it with a test that asserts the prompt text (the same way the
output contract itself is pinned). Any example or placeholder inside a prompt must be explicitly marked as a
placeholder when the real values come from the input payload. Before attributing a repeated structured
rejection to the model, reproduce the obligation list from the validator source and diff it against what the
prompt actually tells the model. If the rejected output is not persisted, treat that as a blocking
observability gap and fix it (or reconstruct the evidence from the validator's own error text) before
drawing any conclusion about model behaviour.

**How to prevent**: For every runtime-validation rule over untrusted LLM output, ask "does the generating
prompt state this rule verbatim, including which identifiers must be echoed and what counts as a rewrite?",
and add a prompt-text assertion next to the validator test. Never diagnose a model from a reason string
alone — require the rejected payload, or state explicitly that the evidence is unavailable and the
conclusion is provisional. Fixing the prompt (not loosening the gate) is the repair; lowering
`expectedDecision` or protected-field checks to obtain a green is a governance change requiring Owner
approval.

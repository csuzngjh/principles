- **What happened**: The first changesets cohort publish train (run 35596275911, cohort bdfe2fc8, 2026-09-21) published @principles/core@1.287.1 at leg 1/7, then failed at leg 4/7 (@principles/codex-adapter) with `@principles/core@^1.287.1 ... does not resolve on the registry — ... a persistent failure means the committed range excludes it`. The gate was `npm view "$PKG@$RANGE" version >/dev/null 2>&1` retried 5×15s: every diagnostic discarded, a flat 75-second budget, and on timeout the error text asserted a DETERMINISTIC data problem (bad committed range). Registry reality: core@1.287.1 fully satisfied ^1.287.1 and was visible minutes later — npm CDN propagation simply exceeded the budget. Four packages stayed unpublished and the diagnosis pointed investigators at the manifests instead of the wait.
- **Why it's wrong**: A bounded-wait timeout is a statement about TIME, not about the data. Translating "not visible within N seconds" into "the committed range excludes the version" converts a transient condition into an apparent code defect, misdirects the fix (recutting versions burns immutable npm versions), and hiding all output (`>/dev/null 2>&1`) removes the evidence that would have exposed the misread.
- **Correct approach**: Separate the two questions. First, statically prove the deterministic contract (the range admits the dependency's committed cohort version; the order is topological) with zero registry contact — failure there IS a data error and fails immediately. Second, treat registry visibility as a classified, bounded wait: escalating backoff (5/10/20/40→≤60s, 10min total window, per-request timeout), with failures classified (NOT_VISIBLE_WITHIN_WINDOW / RATE_LIMITED / SERVER_ERROR / NETWORK / AUTH) and the exhaustion error explicitly stating it is NOT a range error. Diagnostics are preserved, never discarded.
- **How to prevent**: Any retry/wait loop whose timeout could be reported as a different failure class must keep the last raw answer and report it with its own classification. Never bury a probe's output while asserting a conclusion about WHY it failed. Deterministic validations belong before the first side-effecting operation so they cannot be confused with transient ones.
- **Regression guard**: `scripts/__tests__/publish-recovery.test.ts` drills 1-4 (fake clock: >75s visibility continues; window exhaustion reports NOT_VISIBLE_WITHIN_WINDOW with explicit not-a-range-error wording; error classes distinguished; static range/order errors exit before any registry contact). The legacy gate literals (`npm view`, `>/dev/null 2>&1`) are pinned absent from the publish action.

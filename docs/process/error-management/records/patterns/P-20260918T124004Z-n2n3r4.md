- **What happened**: In `formation-context.ts` (PRI-838, PR #1756), `FORMATION_TOTAL_MAX_CHARS = 8000` was documented as a hard cap on the serialized prompt block and protected by a test asserting `JSON.stringify(context).length <= FORMATION_TOTAL_MAX_CHARS`. The implementation bounded the two *content* blocks per-section (proposals 4000, diagnosis 3500), then ran a "final guard" that truncated only `provenance.lineageArtifactIds` and **returned without re-measuring the serialized object**. Three terms live above the section level and were therefore unbounded: `lineageArtifactIds`, `dreamerContextRefs`, and `truncationNotes` — and `trimSection()` **appends one note per dropped item**, so the degradation path grew the very term that could push the block over. Measured through the real resolver with maximal inputs: **8550 chars against the 8000 cap (+550 over)**. The shipped test passed only because its fixture used a minimal 2-candidate dreamer and a small diagnosis — the cap was never exercised at the boundary it existed to protect.
- **Why it's wrong**: A bound at a prompt boundary is a contract, not a best-effort target. Two independent defects combined: (a) the guard mutated one term on the assumption it was the only unbounded one, with no re-check; (b) the test asserted the *documented* invariant against an input that could not violate it, so the assertion was vacuous for that class of input — it verified the label, not the behaviour. "Set the cap constant" plus "a test mentions the cap" is not evidence that the cap holds.
- **Generalized failure mode**: When a limit is enforced by staged degradation, any single-shot guard that mutates one variable and returns will be defeated by exactly the terms the guard did not enumerate — especially bookkeeping/telemetry terms that grow as a *side effect* of degrading. And a regression test whose fixture is too small to approach the limit passes vacuously, so the cap ships unguarded.
- **Correct approach**: The final enforcement step must **re-measure after every mutation and continue the ladder until the whole serialized object fits** — a check-and-continue loop, not a single-shot guard. Enumerate every term contributing to the serialized size (including the notes term that degradation appends to) and order the ladder from cheapest information loss to most expensive. Never bound one array by truncating it and returning.
- **How to prevent**: Two 30-second checks when writing any cap/budget/limit code: (1) *Is every serialized term accounted for by a step in the ladder — including the notes/telemetry term the degradation itself appends to?* (2) *Does the regression test drive the input to the boundary (maximal every contributing field, plus extras), or can it pass with a tiny fixture?* If the test can pass without approaching the bound, it is not a guard. Corollary: assert the cap on the **final returned value**, and also assert the output is still parseable (no mid-value slicing) and that degradation remains observable.
- **Regression guard**: `formation-context.test.ts` → *"holds the cap even when every field is maximal and the drops themselves add notes"* (all fields at the 400-char clamp, 8 evidence + 8 violated principles + 5 recommendations, 64 lineage ids; asserts size ≤ cap, notes non-empty, `JSON.parse` succeeds). Mechanized at repo level by the full `principles-core` suite.

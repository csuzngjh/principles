- **What happened**: 2026-10-31 03:01Z，Version Packages PR（#2240）的 `pd-console E2E` job 红。owner-auth 阶段的服务端日志在 95 秒内出现 20 条 `Unhandled rejection after headers sent: Error [ERR_HTTP_HEADERS_SENT]`，栈全部指向 `handleOwnerDecisionsRoute (owner-decisions.ts:222)` → `sendError` → `sendJson`。真实情况是：`GET /api/v1/governance/owner-decisions` 在 CI 负载下的读取（每个 shadow activation 都要跑 2 个真实 `pd` CLI 子进程探针，探针预算各 15s）超过 `asyncHandler` 的 10s 请求预算 → 超时路径先写出 504；路由随后继续执行，`sendSuccess` 二次写头抛错并被同一段 try/catch 捕获，`sendError` 再抛一次，最终以「Unhandled rejection after headers sent」记录。日志里的第一条错误因此是传输层错误，而真正的失败原因（请求超时）从未被记录。
- **Why it's wrong**: 一个响应一旦被某个降级路径（这里是超时 504）写下，后续任何 writer 再写都只能抛 `ERR_HTTP_HEADERS_SENT`。把这次抛错当作「本次请求的失败」上报，等于用第二条假错误覆盖第一条真错误：排障者会去查路由/序列化，而真正要改的是延迟预算或超时。这条反模式在 ServerResponse 上尤其常见，因为 `sendSuccess`/`sendError` 可以出现在同一个 `try`/`catch` 的两侧，第一次写入抛出的错误被 catch 捕获后立刻触发第二次写入。
- **Correct approach**: 统一 send 层必须把「响应已提交」当作终态：`res.headersSent || res.writableEnded` 为真时丢弃本次写入（有界 warn，只记 status，不 dump payload），绝不抛错；同时让最先发生的失败自己发声——超时路径在写 504 之前记录结构化 warn（method + url + 预算），这样日志顺序天然是「超时（真因）→ 丢弃迟到写入（降级）」，不会再出现传输层错误抢占首条错误。
- **How to prevent**: 任何 `try { sendSuccess(...) } catch { sendError(...) }` 形状的路由，其 catch 分支都潜伏着这个缺陷；send 层守卫是唯一收敛点，不要在路由里逐个判断。检查清单：新增任何「写入响应」的函数时，先问它在响应已提交时该做什么；给测试断言设预算时，先核对服务端自己的请求预算（测试等待不得短于服务端可能成功的上限）。
- **Regression guard**: `packages/pd-console/tests/server/utils/response.test.ts`（headersSent / writableEnded 两条负面路径 + 有界 warn 断言）与 `packages/pd-console/tests/server/routes/owner-decisions.test.ts` 的「response already answered by the timeout path」用例（真实 state.db，断言零写入、不抛、warn 一次）。负控制实测：去掉 sendJson 守卫后 3 条新用例全部失败。

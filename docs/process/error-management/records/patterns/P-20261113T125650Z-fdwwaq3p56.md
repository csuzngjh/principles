- **What happened**: PR #2621 给 `packages/pd-mcp-server` 新增运行时依赖 `@principles/host-runtime`（`src/submit-assembly.ts` 通过 `@principles/host-runtime/pd-config` 读取有效的 `.pd/config.yaml`）。本地 `npm run build --workspace=@principles/pd-mcp-server` 反复全绿，据此判定改动可推。推送后 CI 连红三个作业（`Test pd-mcp-server`、`Test shared runtime & adapters`、`Codex plugin delivery contract`），失败行完全一致：`src/submit-assembly.ts(25,39): error TS2307: Cannot find module '@principles/host-runtime/pd-config'`。
- **Reproduction**: 错因不在代码，而在两处 CI 步骤的构建顺序（`test-pd-mcp-server` 只建 core + install-layout，从未建 host-runtime；`test-shared-runtime` 把 pd-mcp-server 排在 host-runtime **之前**）。真正的坑是**本地为什么看不见**：该工作树的 `node_modules/@principles/*` 全是指向主树 `D:\Code\principles\packages\*` 的 junction（工作树从主树复制 node_modules 时留下的绝对链接），而主树的 host-runtime 早已有 `dist/`。tsc 解析 `./pd-config` 时命中的是**另一棵树**的 `dist/pd-config.d.ts`，本树的 host-runtime 连 `dist/` 都不存在也照样编译通过——本地绿证明的是主树的构件，不是本次要交付的那棵树。复现：把 junction 重指向本工作树的 `packages/host-runtime` 并删掉它的 `dist/` → 立刻得到同一文件、同一 `25,39`、同一 TS2307；再按 `core → install-layout → host-runtime → pd-mcp-server` 构建 → 通过，`packages/pd-mcp-server` 166/166 全绿（含 OG-4 三宿主真进程 stdio 契约）。
- **Invariant**: 本地绿只对"它真正解析到的物理构件"有效。跑任何跨包编译/测试之前，先证明 workspace 包的解析目标等于当前工作树本身（`fs.realpathSync('node_modules/@principles/<pkg>')` 必须落在本树 `packages/<pkg>`），否则不能用"本地能过"去否定 CI 的 TS2307——CI 的 `npm ci` 会把每个 workspace 链到自身目录，本树没有 `dist/` 就直接失败，那才是最诚实的结果。
- **Fix/correctness**: `test-pd-mcp-server` 增加 `Build dependency (@principles/host-runtime)` 步骤；`test-shared-runtime` 的 `Build dependencies` 改为依赖序 `core → install-layout → host-runtime → pd-mcp-server`（原顺序里 pd-mcp-server 紧跟 core，把 host-runtime 甩在后面）。步骤注释写明"exports map 指向 dist/，兄弟包必须先有 dist"，让下一个人不必再踩一次。
- **Guard**: ① 任何跨包 import 的 PR，若本地"删掉依赖包 dist 后仍能编译"，说明解析跑到了别的树或别的构件上，必须先修解析环境再谈验证；② 新增 workspace 依赖时，用 grep 枚举**所有**编译该包的 CI 步骤（`.github/workflows/*.yml` 里的 `build --workspace=<pkg>`），逐个确认依赖包排在它前面——依赖序是每个 job 各自维护的，根 `build` 脚本的顺序不代表 job 内的顺序；③ 复现优先于解释：CI 报 TS2307 时先在本机构造同样的"无 dist"状态把错误复刻出来，复刻不出来就说明本地环境不具代表性，此时任何"我这边是好的"都不算证据。

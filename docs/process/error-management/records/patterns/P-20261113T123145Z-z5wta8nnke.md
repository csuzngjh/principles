## 现象

Owner 把 OG-4 授权范围从"WorkBuddy 单宿主"扩到"三宿主"（决策卡 r5 → r6）。代码改了、测试改了、决策卡加了 r6、changeset 也写了，但 SPEC §7.7 与 TD §5.1.1 的**代码事实上仍然是 r5 的话**：

- "生产唯一 opt-in 点在 `index.ts`：`PD_MCP_HOST === 'workbuddy'` 时显式传入 gate"——已对三宿主生效，描述为假
- "Codex `Bash|apply_patch` matcher 对 MCP 工具名零命中，但 Codex 未开放该工具，不构成覆盖缺口"——既过时又与已改的 matcher 矛盾

我在这些段落上方加了一句"本节以下凡 r5 时点表述一律以 r6 为准"作为兜底声明，然后判定文档已同步。

## 为什么兜底声明不够

运维/审计读的是**具体那一行**，不是上方的总括句。当同一节里既有"以 r6 为准"又有"`PD_MCP_HOST === 'workbuddy'`"，读者只会看到后者并据此核对部署，得出"Codex/OpenClaw 没开"的错误结论；更严重的是那句"对 Codex / OpenClaw 继续有效"的禁止清单——代码已经在三宿主注册，SPEC 却写着对其中两个宿主仍属禁止事项，按文档审会把实现判成违规。

## 根因

把"文档同步"当成可以靠覆盖声明批量豁免的动作。范围变更（r5→r6）触及的是**逐条事实**，必须逐条改，不能加免责句了事。

## 修复

逐条重写，删掉过时条目而不是给它们加注解：opt-in 改为"任一已知 host"，补 host 三种启动情形，删除 Codex 覆盖缺口那条，把"对 Codex/OpenClaw 继续有效"改为"r5+r6 后对三宿主均不适用"。同时把 tool-semantics 的真实状态（有意不登记、解析为 `other`）写进 SPEC/TD/决策卡/changeset 四处，避免文档承诺与代码不一致。

## 检查清单

范围类变更（宿主数、环境数、默认值、开关）落地后，用被改的**具体行**做一次全文检索：`grep` 旧范围关键词（如单宿主名、旧默认值、旧门槛结论），命中处逐条判断，不允许用"以 X 为准"的总括句收口。

Replacing an artifact the host is CURRENTLY loading must never start by deleting it. The WorkBuddy plugin cache refresh did `rmSync(cacheVersionDir, {recursive:true, force:true})` and only then `cpSync(marketplace -> cacheVersionDir)`, with the settings/registry writes already committed above it. On ENOSPC, EPERM on a locked file, or a partially completed copy, the previously working payload was already gone and the registration pointed at an incomplete directory — `install()` returned a failure, but the plugin stayed unloadable until a successful retry. Nothing in the diff looked unsafe: the path was validated as a strict child of the fixed cache root, so the containment guard passed while the ordering was destructive.

Fix shape: stage the new payload in a sibling temp dir, prove completeness against the required-file list, swap with rename + backup, restore the backup when the swap fails, and commit the registration writes (settings and registry) only after the cache is in place. The test that injects a copy failure must assert the OLD payload is still loadable and the registration files are byte-identical — asserting "an error was returned" alone passes on the destructive version.

Generalization: for any install/upgrade path, ask "if this step fails halfway, what does the host load next?" If the answer is "nothing" or "a partial tree", the ordering is wrong regardless of how well the paths are validated.

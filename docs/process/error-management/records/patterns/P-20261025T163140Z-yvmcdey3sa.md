A load→modify→save caller of a whole-object persistence API holds a snapshot taken before acquiring the write lock. When a locked single-writer mutator appends to a sub-section of the same object between the caller's load and save, the caller's save merges its stale sub-section back and silently deletes the appended rows — e.g. a lost revoke re-activating a withdrawn rule-candidate binding. Protective merges keyed on 'caller lacks the field' never fire once the loader starts returning the field as an own key. Fix shape: the generic save path always strips sub-sections whose only legitimate writer is a dedicated locked mutator (lock-time current value wins), and the regression must exercise the REAL load-modify-save caller path, not a hand-edited file. Found in saveLedger/saveLedgerAsync vs mutateRuleCandidateBinding (PR #2137 review).

- **What happened**: The signed-update release asset is keyed by the exact triple `platform + arch + nodeAbi`, and `selectReleaseAsset` refuses any runtime whose triple is absent (`runtime_not_supported`). `release-metadata.yml`'s `build-asset` matrix published Node 24 (ABI 137) and Node 26 (ABI 147) only — while the same repository declares Node 22 a supported runtime: `engines.node` is `>= 22.0.0`, `NATIVE_RUNTIME_DEPENDENCY.nodeEngine` is `>= 22` (mirroring better-sqlite3@13.0.3's own engines floor), and `SUPPORTED_NATIVE_TARGETS.nodeAbis` — the module `build-self-contained-release.mjs` asserts against at line 72 — lists `22: '127'`. On 2026-09-20 the Owner's machine resolved its Node to 22.22.2 (ABI 127) and `ReleaseManager.apply()` refused the live release 2.1.0 with `Release 2.1.0 has win32/x64 assets for Node ABI 137, 147, but this runtime is ABI 127`, while `check()` still returned `allowed: true`. PRI-852 had already hit the identical wall from the other side — the machine then ran Node 26 / ABI 147 — and added the Node 26 leg; Node 22 was left behind, and no gate noticed.
- **Why it's wrong**: Two declarations of one fact disagreed and nothing compared them: the *support range* ("a runtime is supported from Node 22 up") and the *published set* ("assets exist for 24 and 26"). `check()` reporting `allowed: true` for a runtime that cannot be updated made a coverage gap look like an apply-time bug, and the gap was invisible to every existing gate: `release-reproducibility-full.yml` validates that the code builds and tests on Node 22.22.2 across five runners, so "Node 22 works" was proven while "Node 22 has no asset to install" was never asked. The declared minimum is also the case most likely to be missing, because it is the oldest value and the least exercised.
- **Correct approach**: An artifact keyed by a runtime identity must cover every runtime the product declares it supports, on every platform that artifact publishes. The `build-asset` matrix now carries the full declared ABI axis (22/24/26) on each published `(platform, arch)` leg, and the axis may still only grow or shrink with build-and-test evidence (SPEC v0.3 §7) — that evidence is the full verification matrix.
- **How to prevent**: When a declaration (support range, `engines` field, capability list) and a generator (build/release matrix) both speak about the same dimension, add a contract test that reads BOTH and compares them; "declared support", "declared minimum", and "actually produced" are three different facts and only the last one is installable. And when a runtime-keyed selector refuses, compare its declaration against the produced artifact set before treating the refusal as a defect in the selector — and never read `check(): allowed` as coverage.
- **Regression guard**: `packages/create-principles-disciple/tests/release-target-matrix.test.ts` → "publishes every declared Node ABI on every platform the asset matrix covers" parses the `build-asset` legs out of the workflow and asserts each published target carries exactly the majors in `SUPPORTED_NATIVE_TARGETS.nodeAbis`, plus no duplicated asset identity. Reverse-probed against the pre-fix matrix it fails with `linux/x64 ABI coverage: expected [ 24, 26 ] to deeply equal [ 22, 24, 26 ]`.

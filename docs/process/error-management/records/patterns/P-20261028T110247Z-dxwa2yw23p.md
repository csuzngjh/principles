**What happened**: `pd pain recall` shipped with strict read-only contract tests (SPEC-PD-PAIN-RECALL-CLI-001 §9.2: "no WAL/SHM side effects", "journal mode unchanged") that were green on main, yet every production invocation on a resting workspace created `-wal`/`-shm` sidecar files next to both databases. Both production databases (`.pd/state.db` via `SqliteConnection`'s `journal_mode = WAL` pragma, `.state/trajectory.db` via the plugin `TrajectoryDatabase`) are persisted in WAL journal mode — WAL is a persistent header property, so a cleanly-closed "quiet" workspace keeps header write/read version 2 with no sidecar files. A readonly better-sqlite3 open of such a database creates the WAL/SHM sidecars (independently reproduced 2026-10-28: recall on a quiet-WAL fixture created 4 sidecar files; main-file hashes unchanged). The contract tests never saw this because their fixtures create the databases with plain `new Database(path)` and never set the WAL pragma — the fixtures verified a rollback-journal state that production never rests in. The defect was found by an external synthetic-fixture audit (SPEC-PD-AGENT-CAPABILITY-API-001 v0.3 §10.3.1), not by the suite that existed to catch exactly this.

**Why it's wrong**: a contract test that seeds a fixture in a default state is only evidence for that state. When the production system persists a state-changing property into the artifact itself (journal mode lives in the database header), the fixture must reproduce the production resting state or the contract is verified against a world that does not exist. Green ro-1..ro-4 tests actively certified "no WAL/SHM side effects" while the shipped binary violated it on every quiet-WAL workspace.

**Correct approach**: fixtures for storage-backed contracts must enumerate the persistent state dimensions the production writers actually set (journal mode here) and build at least one fixture per production resting state. The fix adds the WAL matrix: quiet WAL (staged-copy read, zero side effects), live writer with un-checkpointed committed frames (attach, fresh, creates nothing), empty `-wal` after TRUNCATE checkpoint, crashed-writer trio (fresh through WAL recovery), and mixed journal modes — each asserting sidecar absence, byte-identical main files, AND result freshness (an un-checkpointed row must be visible), so the fix cannot trade freshness for cleanliness.

**How to prevent**: when writing storage contract tests, list the persistent PRAGMAs/headers the production writer sets (journal_mode, page_size, encoding, user_version...) and derive the fixture matrix from that list, not from the default `new Database()` state. If a contract says "X stays unchanged", assert X in every persistent state the production artifact can rest in, and include at least one fixture that mirrors the production writer's exact setup sequence. A green read-only suite built only on default-mode fixtures is not evidence of read-only behavior in production.

**Regression guard**: `packages/pd-cli/tests/commands/pain-recall-readonly.test.ts` → "recallPains: WAL-mode strict read-only (production journal mode)" (ro-5..ro-9). Reverse-probe: before the fix, ro-5 fails with sidecars `["trajectory.db-wal","trajectory.db-shm"]` and `["state.db-wal","state.db-shm"]` appearing in the workspace after recall.

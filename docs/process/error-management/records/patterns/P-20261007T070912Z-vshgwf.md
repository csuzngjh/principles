- **What happened**: While deciding whether three half-deleted worktree shells (`D:\Code\_worktrees\principles\*`) could be deleted, "is this file already committed?" was answered by hashing the working-tree bytes (`sha1sum`) and comparing the result against the blob stored at the same path in `origin/main` (`git ls-tree` / `git cat-file`). For four LFS-tracked media files per shell the comparison reported "no match", so 8 files were recorded as *human work that never landed* — a verdict that flips the decision from "delete, nothing is lost" to "do not delete, unlanded work". They were re-checked with `git hash-object --path <tracked path>`, which applies the clean filter declared in `.gitattributes` (`*.mp4/*.webm/*.webp filter=lfs`), and all 8 became exact matches: main stores a 132-byte LFS *pointer* blob, not the media bytes. Raw-bytes sha could never equal the stored blob sha for those paths.
- **Why it's wrong**: The comparison was treated as proof about an authority (git's object store) while silently assuming that the working tree and the object store hold the same bytes. They do not: `text=auto`/`eol` normalization and `filter=lfs` put a *transformed* representation in the object store. An equality test across an unapplied transform is not evidence — it is a guaranteed mismatch for exactly the paths where the risk of deleting real work is highest (large binaries, generated payloads). The error was not the conclusion but the instrument: it produced a plausible, confident, and wrong answer, and it pointed toward an irreversible action.
- **Generalized failure mode**: Content identity is compared across a transform boundary the comparing tool never enumerated — git clean/smudge filters (LFS), line-ending normalization, or build-time rewriting — so the tool's "different" verdict actually measures the filter, not the content, and a deletion/retention/landed-work decision is made on it.
- **Correct approach**: Ask the authority for BOTH sides of the comparison. To decide "is this working-tree file the same as what git stores", use `git hash-object --path <tracked path> <file>` (applies the filters that path is configured to use) or `git diff -- <path>` / `git status --porcelain`, never a standalone `sha1sum` against `git ls-tree` output. When a raw hash comparison is unavoidable, normalize first (CRLF→LF) and exclude `filter=lfs` paths after reading `.gitattributes`, and state in the evidence that those paths were not covered.
- **How to prevent**: Before citing any byte-identity comparison as evidence for an irreversible action, answer in one line: *which representation does each side hold, and which transforms (`.gitattributes` filters, `text=auto`, build steps) stand between them?* If the answer is not enumerated, replace the comparison with the tool git itself provides (`git hash-object --path`, `git diff`, `git log --find-object`). Corollary for forensics on deleted shells: a "never committed" hit is a hypothesis about the instrument until re-derived through git, because the cost asymmetry is total — a false "landed" deletes nothing, a false "unlanded" keeps garbage forever, and a false "unlanded *work*" blocks a justified decision.
- **Regression guard**: Semantic verification obligation — named in the PRI-949 Task Risk Contract. Not mechanizable as a repo-wide guard: the failure happened in ad-hoc forensic commands run outside the repository, not in shipped code.

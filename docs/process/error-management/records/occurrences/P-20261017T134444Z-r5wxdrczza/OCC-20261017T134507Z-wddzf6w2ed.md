PR #2073 fixed the WorkBuddy plugin's missing skills and added a same-version cache refresh for hook-only installs. `directWriteRegistration` wrote settings.json and installed_plugins.json first, then ran `rmSync(cacheVersionDir)` + `cpSync(...)`. The existing failure-injection test only asserted `result.success === false` and `reason` contains `workbuddy_cache_write_failed`, so the destructive ordering shipped green through the offline suite and local `verify:merge`.

An external review flagged it as P1. Measured on the pre-fix code with the injected copy failure pointed at the live cache dir: the new assertion `the previous cache must survive a failed refresh` failed with `expected false to be true` — `scripts/wrapper.cjs` of the previous payload no longer existed. After the fix (staging copy -> completeness proof -> rename + backup swap; settings/registry committed only after the cache lands) the same test passes, and the failure path leaves both registration files byte-identical.

Why self-review missed it: the diff read as "narrowed the deletion from the plugin cache root to the version dir", which is a safety improvement relative to the parent commit, so the reviewer stopped at the path-containment question. The failure-ordering question ("what does the host load if step N dies?") was never asked, and the existing test's assertions could not distinguish "failed loudly" from "failed destructively".

- **What happened**: This record is the originating occurrence. Tracing the Owner's requirement "update PD to the latest version from the PD console" against the installed product, `check('stable')` on the live channel returned `allowed: true` for release 2.1.0, but `selectReleaseAsset` refused the same release for this machine: `Release 2.1.0 has win32/x64 assets for Node ABI 137, 147, but this runtime is ABI 127` (`runtime_not_supported`). The live metadata carried five assets — `linux/x64` 137+147, `win32/x64` 137+147, `darwin/arm64` 137 — the exact set the `build-asset` matrix produced (Node 24 + Node 26). The machine's runtime is Node 22.22.2 / ABI 127, which `engines.node >= 22.0.0`, `NATIVE_RUNTIME_DEPENDENCY.nodeEngine >= 22`, and `SUPPORTED_NATIVE_TARGETS.nodeAbis` all declare supported, and which `build-self-contained-release.mjs` accepts as a local release target.
- **Why it's wrong**: The refusal is honest but the gap behind it is not visible from any gate: the release gate proves Node 22 builds and passes the upgrade gate on five runners, so the repository's evidence said "Node 22 is supported" while the published artifact set said otherwise. `check()` reporting `allowed: true` compounded it — the refusal only appears at apply time, after the Owner has been told an update is available.
- **Correct approach**: Publish the full declared ABI axis on every published `(platform, arch)` leg (Node 22 added to `linux/x64`, `win32/x64`, `darwin/arm64`; Node 26 added to `darwin/arm64`), then re-publish the signed release so the ABI 127 asset exists.
- **How to prevent**: Pin declared-axis versus produced-set coverage with a contract test (added), and remember `check(): allowed` is a policy verdict, not an asset-coverage verdict.
- **Regression guard**: `tests/release-target-matrix.test.ts` → "publishes every declared Node ABI on every platform the asset matrix covers"; reverse-probed failing against the pre-fix matrix.

- **What happened**: PRI-750 PR #1663 added host run/tool-id capture to receipt events on two hosts. (1) The OpenClaw tool-event helper read only `toolCallId`, while the existing pain pipeline (pain.ts:439-441) already prefers `toolUseId` with `toolCallId` fallback — a supported host shape lost its direct binding. (2) The PR claimed Codex events "DIRECT join `assistant_turns.run_id`" without verifying a Codex-side writer exists — repository-wide only the OpenClaw plugin inserts into `assistant_turns`, so the claimed chain was not consumable on Codex-only workspaces.
- **Why it's wrong**: An extension that claims parity with existing reality without reading the existing consumer's exact semantics (field precedence) or the downstream writer's existence either reproduces a failure the counterpart already solved (pain.ts) or advertises a capability that cannot execute.
- **Generalized failure mode**: When extending an existing mechanism to a new host/shape, the extension must mirror the existing consumer's exact field semantics AND verify the downstream writer/table exists for the new host before claiming DIRECT support.
- **How to prevent**: Before wiring a new host into an existing chain, (a) read the existing consumer's field precedence (e.g., pain.ts `toolUseId` → `toolCallId`) and mirror it with a regression per supported shape; (b) grep the repository for the claimed downstream writer/table and confirm the new host produces rows — otherwise document the DB-side anchor as a follow-up instead of claiming the join.
- **Regression guard**: openclaw-plugin `tests/hooks/receipt-runid-binding.test.ts` (toolUseId alias → `toolCallId` recorded); principles-core `src/runtime-v2/__tests__/append-event-log-line.test.ts`.

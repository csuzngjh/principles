- **Occurrence**: PRI-1101 recurrence of ERR-144. The console's `/api/update/check` budget had been raised to 30s by the adhoc-20260928 fix, but the trust layer it awaits bounds ONE tuf-js metadata request at 100s (`defaultConfig.fetchTimeout`) and retries it. The outer 30s hard deadline therefore still fired while a healthy check was in flight: `asyncHandler` answered 504, and `sendJson` dropped the check's late success (`Dropped late response write`), so the Owner saw a timeout for an operation that had actually succeeded.
- **Impact**: Owner-visible false failure on the update page (P3, retryable, no data/state damage).
- **Fix**: derive the check budget ABOVE the inner per-request bound (120s default; `PD_UPDATE_CHECK_TIMEOUT_MS` still overrides) and pin the default in `update-timeout.test.ts`, so lowering it back below the inner budget fails a test.
- **Enforcement decision**: the pinned default is an advisory guard. The structural rule is: an outer request deadline must never be smaller than the inner operation's own timeout budget (same shape as PRI-1202's derived CLI recovery probe budget).

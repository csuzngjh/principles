- **What happened**: `auditCandidateLedgerConsistency` (new code in PR #1944) collapsed every underlying failure into `catch { return errorResult(); }` — the audit still failed loud (`status:'error'`, CLI exit 1), but the operator got only the fixed string "Audit failed: could not read candidate/ledger state". A stale-schema state.db (`no such column: recommendation_kind`) was indistinguishable from a missing db or an unreadable ledger.
- **Why it's wrong**: A refusal without the structured reason + next action (rc-9) forces the operator to guess the recovery path; rc-3 fail-loud is only half the contract — the other half is explaining WHY. CodeRabbit's review suggested defaulting the missing column to `'principle'`; that is a silent fallback that would resurrect the false-positive missing-degradation class this PR eliminates, and was rejected in favor of visibility.
- **Correct approach**: Propagate the bounded underlying error (`err.message`, rc-8 500-char cap) as an optional `reason` on the error result; the CLI error branch prints the reason plus a concrete next action (open the workspace once with the PD runtime to create/migrate state.db, then retry). The `--json` error structure is unchanged (out of scope).
- **Regression guard**: core tests assert reason propagation for the stale-schema query failure, missing state.db, and the rc-8 length bound; CLI tests assert the error output contains the reason and the next action (commit 21c605e6, PR #1944).

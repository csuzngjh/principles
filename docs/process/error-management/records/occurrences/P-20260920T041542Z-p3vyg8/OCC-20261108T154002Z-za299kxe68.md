The mandatory daily signed-channel preflight reports failure when nothing is wrong. On 2026-11-08, the day the 2.8.4 publication advanced `stable` to `publicationSequence 38`, the scheduled `release-metadata.yml` run (42481888291) failed at "Sign and emit release metadata" with `publish-release-metadata: Release 2a0ab48098fd is already published with different pointer content (publicationSequence 38 vs 39, pointer version 38 vs 39)`. The candidate releaseId it computed from main's root manifest equals the release that IS published, while its counters are derived as `published + 1`, so the guard fires on a legitimate no-op. The workflow has no `candidate == published -> up_to_date, exit 0` outcome, so every daily preflight is red from the moment a release lands until either the root product version bumps or the npm cohort moves — and the error text actively misleads by blaming pointer-content drift when the content is identical. This is the same root-cause class this pattern was created for: the release pipeline's pass/fail boundary is not designed to carry meaning. Then it failed silently for 4 trains and nobody noticed; now a required daily check fails loudly when there is nothing to do, which equally destroys the signal — a red that recurs every day regardless of state blocks nothing and trains everyone to skim past the one column that reports whether a release could actually ship.

## 2026-11-11 — Codex 插件换版本后 mcp-binding.json 不再生成（PRI-1183 / 本 PR）

**现象**：Codex 插件载荷升到 0.3.22 后，`~/.codex/plugins/cache/principles/principles-disciple/0.3.22/` 没有 `mcp-binding.json`；真实 launcher 退出 1（`binding_missing`），`tools/list` 中没有任何 PD 工具。`codex plugin list` 仍显示 installed + enabled。

**为什么属于本模式**：绑定写入组件（`pd-setup.cjs`）存在、有测试、也能在手工调用时正确工作，但**生产更新路径**不会在它需要工作的状态下调用它：`CodexHostInstaller.reconcileInstalledPlugin` 只在「已装 runtime cohort ≠ 载荷 pin」时运行 pd-setup。绑定写在按版本分目录的载荷根，载荷换目录即丢失；而 pin 未变时该条件恒为 false，修复路径成为不可达代码，launcher 永久 fail-closed。

**修复形状**：把「修复触发条件」绑定到被修复产物本身的状态（绑定是否存在且指向本载荷的 runtime 与 pin），而不是另一个可能保持不变的状态维度；setup 之后重新读取并校验，仍然不健康则结构化失败（reason + nextAction）。

**验证**：改前 `origin/main` 源码上新增用例变红（`configAction` 为 `preserved`、无绑定文件）；改后真实 launcher 从 `binding_missing` 变为 `tools/list` 返回 `pd_recall_principle_pains`；另有使用真实 `pd-setup.cjs`（隔离 home）的集成用例。

**教训（可复用）**：自愈路径的触发条件必须覆盖被修复产物的完整生命周期。只要产物与条件各自的生命周期不同（例如产物在版本目录、条件看运行时版本），就必然出现“条件成立时不需要修、需要修时条件不成立”的空洞。

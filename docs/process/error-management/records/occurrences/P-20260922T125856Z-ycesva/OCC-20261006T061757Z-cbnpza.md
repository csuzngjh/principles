PRI-942 (#1928) round 2: the same guard overstated its coverage a second time, in the very commit written to fix the first overstatement. After the P1 above was fixed, the collector docstring claimed it "Covers every way the console writes a literal today" while the code still did `if (m[2].includes('${')) continue;`, i.e. it exempted every interpolated link wholesale. The console writes four of those: `OwnerDecisionCard.tsx:236` is `to={`/failed-tasks?taskId=${…}`}` and `ActivationPage.tsx:223` / `FocusPage.tsx:1477` are `to={`/principles/${id}`}`. So a mistyped *static* prefix, `to={`/failed-taskz?taskId=${x}`}`, would have passed CI green — the guard's whole promise was about mistyped paths, and the spelling fix had not touched the form gap. The Standards axis found it by re-deriving the claim against the source, the same move that caught round 1. Fix reads the target up to the first `${` and matches that prefix with prefix semantics (a trailing `/` means the interpolated segment supplies the next one, so `/principles/` lines up with `/principles/:id` without whitelisting it), and adds two assertions: a coverage control that is red against the pre-fix collector (1 failed / 38 passed) and a rule-strength control that rejects an unknown prefix (`/failed-taskz/` must be false) so "dynamic means pass" cannot satisfy the guard. End-to-end mutation of the real link to `/failed-taskz` now fails the suite naming the file and path. Lesson, narrower and harsher than the first: correcting an over-claiming guard is not done when the *spellings* are covered; enumerate the syntactic *forms* the producer can write, and give each one an assertion that can go red. A comment that says "covers every way" is a claim about a set, and only a red test proves the set.

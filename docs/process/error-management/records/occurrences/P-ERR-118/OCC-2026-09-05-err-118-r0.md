- **What happened**: PRI-683 (2026-09-05, pd-labs/pri653-r2b). After PR #1512 wired runner deadline + adapter AbortSignal.timeout to runtimeProfile.timeoutMs (600s/900s, verified working), every artificer repair-wave attempt STILL died at exactly 300.02–300.04s with "Request was aborted" — across Bai and local-27B runtimes (network excluded) and across profiles (profile parsing excluded, evaluator on the same profile succeeded at 472s/490s). The third timeout layer was Node's global fetch: pi-ai issues LLM requests through the OpenAI SDK via `globalThis.fetch` with no custom dispatcher, so the built-in undici dispatcher's implicit defaults `headersTimeout`/`bodyTimeout` = 300e3 applied. Large repair payloads (requiredChanges + full replay evidence) make server prefill exceed 300s before response headers arrive, so the transport aborts at its own cap before the 600s/900s signal can ever fire.
- **Why it's wrong**: The system had three timeout authorities (runner deadline, adapter AbortSignal, SDK request timeout) all configured from one source — but a fourth, implicit one (undici per-socket timers) sat beneath all of them, unconfigured and unobservable. Timeout budget reasoning is only valid if the configured deadline is the TIGHTEST bound on the wire; any deeper implicit default silently overrides it. The failure is additionally deceptive because the error message family ("Request was aborted") is identical to a caller-initiated abort, so logs make it look like the configured authority itself fired early.
- **Generalized failure mode**: Any layered timeout stack where a library default sits below the configuration surface: Node fetch/undici idle+header caps (this case), undici connectTimeout 10s (PRI-633 — B.AI TCP connect sporadically exceeded it), OpenAI SDK 600s default, runner 300s default (PRI-670 — same family, one layer up). Fingerprint that distinguishes the layers: death at exactly the implicit default's value with an abort-family message (transport layer) vs death at exactly the configured value with an "after Nms" message (runner/profile layer).
- **Correct approach**: Make the configured deadline the single timeout authority by disabling deeper implicit caps on the affected request path — pi-ai's official `options.fetch` injection point carries a dedicated undici Agent with `headersTimeout: 0, bodyTimeout: 0` (scoped per-request; never `setGlobalDispatcher` in a host-embedded plugin, which would silently change every host fetch's semantics). Reuse existing capability before building: pi hit this same wall four times in pi-coding-agent (#3715/#4759/#5294/#7435) with exactly this pattern.
- **How to prevent**: When a timeout is configured at layer N, enumerate every timer below N on the actual wire path (dispatcher defaults, SDK defaults, OS/proxy) and assert the configured deadline is the tightest. A regression test that reproduces the implicit cap at 1s scale (small Agent cap + slow-header local server → abort at cap; production transport → survives; outer AbortSignal → still fires on schedule) locks the whole stack.
- **Regression guard**: `pi-ai-http-transport.test.ts` (PRI-683 mechanism suite: capped-agent fingerprint / production transport survival / outer-authority preservation / singleton reuse).
- **Related ERRs**: same-family timing bugs at adjacent layers — PRI-670 runner 300s default (fixed PR #1512) and PRI-633 undici connectTimeout 10s (root cause documented in issue text only, never recorded here before) are the first two members of this recurrence chain; EP-07 (multi-source value alignment — here the "sources" are timeout authorities).

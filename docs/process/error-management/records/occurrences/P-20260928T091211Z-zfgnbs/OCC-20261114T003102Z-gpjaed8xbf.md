## Observation (adhoc-20261114, Owner-reported)

**Where**: `packages/host-runtime/src/prompt-activation-deliverability.ts`
(`resolvePromptCandidatePrinciple` preview branch) consumed by
`pd-console/src/server/models/ApprovalsConsoleModel.ts` (`precheckPromptCapacity`).

**What happened**: the approval precheck is a forecast of the activation
boundary, but it resolved the artifact identity from `source_principle_id` /
content `principleId` only. The production activation path
(`resolveLedgerActivationId`) additionally resolves the ledger principle through
candidate lineage (`scribe → dreamer → candidateId → derivedFromPainIds`).
For the 2026-09-19 record `apr_prompt_pi-art-scribe-cb8c4e6d-…`, the column was
NULL while lineage resolved to ledger `96608bec-…`; the precheck therefore
returned `artifact_missing_principle_id` and the console presented "retry will
not succeed" as fact.

**Why it escaped**: #2614 removed the `principleDraft.title` fallback on
2026-11-13, retroactively turning this historical record from approvable into
permanently unapprovable. No route-level test covered a lineage-only identity.

**Repair**: the precheck now calls `resolveLedgerPrincipleId` (the same
authority as activation) and passes the resolved id; an unresolved identity is
refused before any approval write. The queue read model carries a structured
`approveBlock` so the card disables approve and keeps reject. No data migration.

**Evidence**: isolated production copy before → `422 artifact_content_unresolved:
artifact_missing_principle_id`; after → `decision: activated`,
`targetRef: ledger://96608bec-177f-474f-b441-8360e6df3965`.

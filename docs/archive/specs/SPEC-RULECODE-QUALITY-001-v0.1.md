## 3. 成功标准与非目标

### 3.1 成功标准

1. 原则语义不能被代码生成或修订偷偷缩小、扩大或替换。
2. 决策依赖的事实可观察、可溯源，执行者自填文字不能升级为 Owner 授权。
3. 生成器自测、独立行为验证、模型语义评审、真实宿主验证分别留证；任何单项不能覆盖其他项失败。
4. 缺事实、宿主不支持、样例矛盾、实现缺陷、模型服务故障有不同原因及恢复入口。
5. 可恢复状态不忙轮询、不重复消耗模型预算；恢复幂等且保留旧运行历史。
6. B 真正完成须由 PD 生成原原则代码，经完整评审到达可审阅工件；影子运行和实际拦截分开证明。

### 3.2 非目标

- 不建设通用任务编排、开发审批平台、通用记忆或通用 LLM 输出修复系统。
- 不改 ZCode，不扩大到其他生产痛苦信号，不自动重新提交原信号。
- 不建设通用 Shell 解析器；优先复用现有宿主动作语义，信息不足时不得声称准确识别。
- 不修改工程宪章、降低测试标准、自动批准、自动激活或替换已激活原则。
- 不手工修好模型输出后声称 PD 自动生成成功。
- 不保证任意自然语言原则都能变成硬门禁，不保证有限测试证明长期行为改善。

## 6. A 段设计：生成质量

### A1. 可执行条件核验

在现有 preflight 和工件元数据中承载执行条件，不创建独立 capability registry 或新调度器。

每个代码候选必须可追溯地说明：原意、要拦的行为、必须放行的行为、所需事实、事实来源、目标宿主、可执行范围、无法观察的内容。复用 intentContract 和样例包；需要增加字段时采用可验证、带版本的加法扩展，不重新复制原意。

模型可以在现有 Scribe/Evaluator 调用中提出所需事实，但它的声明不构成能力证明。确定性代码核对宿主声明、真实提供者及事实结构；Evaluator 核查“列出的事实是否足以支持这条原则”。不能仅凭模型声称不需要批准事实就通过审批原则。

核验输出的逻辑含义固定为：

| 结果 | 行为 |
|---|---|
| executable | 关键事实和目标宿主能力具备，允许生成；不是质量合格证明 |
| needs_evidence | 能力存在，但缺范围明确的事实或有效样例，等待补证 |
| unsupported | 当前输入/宿主无法表达该原则，无自动重试 |
| evidence_conflict | 同一有效输入被赋予矛盾期望，停止并报告冲突来源 |
| source_error | 数据损坏、来源不可读或血缘不一致，不归咎 Owner 未补证 |

这些是语义结果，不要求直接新增 task.status 枚举。映射到现有状态/metadata/reason 的方案必须在实施 Reality Audit 中列明，并覆盖所有消费者。不得用“task succeeded”表示 RuleCode 合格。

A 段不得将原原则“非简单变更先经设计批准”改成“所有提交必须有标记”或“先读文件就算批准”。缺可信事实时，原分支应准确报告缺项，而不是消耗三轮模型预算。

### A2. 生成与修订约束

- 移除 closest-per-call-proxy 和参数标记可代表授权的指导；修正“无状态所以不能使用历史”的过时表述。无状态函数可以读取宿主提供的历史，但不能读取不存在的事实。
- 意图无法完整执行时，不输出冒充完整实现的强制代码。可执行子范围如需作为独立规则，必须保留差异，并重新进入对应 Owner 治理，不能悄然替换原候选。
- 保持 dialect、沙箱安全、宿主词表和 unavailable 契约；不能为让原任务通过而放松。
- 样例包中的真实样例不能删除、改标签或改输入；新增模型样例注明来源，不能构成批准证据。
- 不允许用模型输出的 summary/risks 代替实际代码检查；“已披露缺陷”不等于可进入合格规则审阅。

### A3. 独立验证

复用现有 `evaluateRefinerRuleHostGate`、EvaluatorRunner 和 repairFeedback 链。新增的是必要的生产接线与测试内容，不另建评审平台。

验证分三组，记录独立结果：

1. 真实标注样例回放：保护原失败与正常行为。
2. 独立行为/安全测试：人工或受委托代理依据意图制定，不能只复制生成器的案例。
3. 意图一致性评审：禁止替代批准、改变适用范围和用最终提交检查替代编码前要求。

测试必须记录 caseId、来源、适用性、实际输入、预期依据、宿主语义版本和执行结果。实际验证记录绑定代码摘要、工件 ID、意图/样例版本、验证器版本和目标宿主；代码或关键材料变化后旧证据不能继续作为通过依据。元数据引用既有权威，报告文件只用于展示。

独立测试一部分可反馈给有界修订；每次修订后仍需执行未用于该轮生成的检查。不得把已经逐题泄露并反复修到通过的测试称为完全独立留出测试。所有适用的发布阻断用例须通过，不以平均分抵消安全缺陷。

对输入相同、只改变测试名称/期望的“已批准/未批准”案例，验证样例契约应识别信息不足或冲突；不能要求规则猜出隐藏事实。提交消息写“docs: fix typo”本身也不能证明任务简单。

### A4. 修订与终态

代码错误复用现有修订上限，实施者必须记录真实生效值，不能新增无限循环或悄悄扩大次数。缺事实、来源错误、宿主不支持不进入代码重试。

每个停点至少展示：所在阶段、reasonCode、事实依据、是否可恢复、下一步、已消耗尝试数。可恢复任务只有材料版本或宿主能力发生有效变化后才允许通过官方定点恢复继续；重复轮询不产生新 run。

沿用既有租约和事务；崩溃恢复不得生成重复审阅请求、重复规则或丢失旧运行记录。补证、恢复的 dry-run 必须零治理变更。

## 7. B 段设计：可信审批事实与 Codex

### B1. 先确认是否存在可接的权威来源

实施者必须先给出一份真实来源样本和可重复读取路径，证明其具备：人类批准身份、明确决定、宿主任务绑定、被批准 SPEC 的版本/摘要、允许的操作范围、撤回/替代状态，以及与当前请求的关联。

三种情况的处理固定：

1. 宿主已有满足要求的结构化事实：只增加适配读取和校验，宿主仍为唯一写权威。
2. 只有聊天文本：不能仅凭关键词或 LLM 提取就升级成可强制执行的批准事实。若无现成可信语义确认机制，B 阻塞，报告具体缺口。
3. 来源不存在或范围无法核实：B 阻塞；不得建立通用开发审批系统，也不得假造批准样例后宣布真实链通过。

PD 对原则本身的批准不能补齐这项事实。原会话中的“自行判断样例”委托也不是后续开发任务的普遍设计批准。

### B2. 条件具备后的最小输入契约

扩展必须位于现有宿主上下文 seam；审批事实只作有来源的派生投影，不新增独立审批表或写入口。设计所需字段的含义如下，具体类型必须采用版本化校验并覆盖真实消费者：

| 内容 | 约束 |
|---|---|
| sourceRef、sourceKind | 指向可核实的宿主权威；普通 params 和仓库文件不合格 |
| actor、decision、revision | 可信人类决定和最新状态；模型自报 actor 不合格 |
| hostTaskRef、workspaceRef | 与当前动作由宿主绑定；不得只用命令参数自填 |
| specRef、specDigest | 批准对应具体材料；当前材料摘要变化后旧批准不再适用 |
| scope | 来自获批材料/可信确认的范围，不能由执行者自己扩大 |
| resolution | approved / not_approved / not_required / unknown；后三者含义必须严格区分 |

`not_approved` 需要权威来源在其覆盖范围内明确证明未批准，不能从截断历史中“没找到”推导。`not_required` 需要已有权威任务分类或明确的适用范围；不能由代码行数、路径或提交消息单独推导。任务、范围或来源无法核实均为 unknown。

已有批准若仍覆盖当前任务与 SPEC，不得重复要求 Owner 批准；但不能把旧批准用于不同设计或超范围操作。撤回、SPEC 更新、任务切换时须在当前调用重新核实，不使用上次循环或缓存的旧结果。

### B3. Codex 运行接线

历史轨迹读取、回放上下文、实时 pre-tool 上下文是三个不同入口。必须证明每次真实调用读取的上下文来自当前 session/task，而非生成样例、另一个宿主或上次任务。

当前缺少 provider 时的 V2 暂停行为必须保留。不能简单“注入 truthy unavailable 对象”就启用全部历史规则。若实施运行时支持，应先确认现有 per-rule 资格/激活机制能否将新支持限制到经过复验和正式批准的目标规则；做不到则 B 保持阻塞，禁止批量唤醒旧 V2 规则。

unknown 或 provider 失败不能被规则解释为“确定未批准”。原则特定的上下文不足不新增全局工具阻断；按现有暂停/非匹配契约返回，并保留结构化原因，不影响其他独立安全规则。

### B4. 原痛苦的真实推进

仅通过正式命令/服务，复用原成功 Scribe，保留原 task/pain 血缘。先隔离副本，再只针对一个目标分支恢复，不运行会消费其他痛苦的全量后台循环。

当前优先目标：`artificer-52d98a96-65b9-4952-82c5-51ba2d853c53-code_tool_hook`。另一分支 `artificer-406f6131-5a28-4d17-9a7f-a18298d48bd0-code_tool_hook` 只读核实并单列状态，不因一条完成就宣称所有分支完成。

Owner 对主 prompt 原则的既有批准不得复用于新 RuleCode。到达新规则审阅工件后提供入口并停止自动审批；已有“批准主原则”的历史授权不能扩大成批准所有新代码版本。

| Q08 | 权威来源确认无需设计审批的简单任务 | 放行；不能凭提交消息给任务分类 | 契约 + 回放 |
| Q09 | 批准对应旧 SPEC、另一任务、另一工作区或已撤回 | 不可沿用；缺状态时明确 unknown | 来源/血缘负控 |
| Q10 | 宿主来源断开、超时、损坏、截断历史 | 不伪造批准/未批准；原因可查，不忙重试 | provider 故障注入 |
| Q11 | 生成器五例通过、独立适用反例失败 | 不进入质量合格审阅；有界修订或明确终态 | 真实 Evaluator 接线 |
| Q12 | LLM 自报 passed，但沙箱失败/未执行 | 无法升级质量结果 | 权威负控 |
| Q13 | 代码、意图或来源关键版本变化 | 旧通过证据失效，正式复验 | 持久化往返 |
| Q14 | 重复恢复、补证、重启及租约冲突 | 无重复规则/审批请求，无历史丢失；冲突零禁止写入 | SQLite 接线 |
| Q15 | Codex 无 provider 或旧规则尚未复验 | 旧 V2 暂停保留，不能批量激活或静默生效 | 真实 hook 集成 |
| Q16 | Codex 当前调用获得正确上下文 | session/task/spec 血缘一致，产生日志及正式回执；不靠助手自述证明 | 真实宿主 |
| Q17 | 目标新规则通过完整链 | 可审阅工件含代码、适用范围、证据、限制和正确 pending 状态 | 生产定点验证 |
| Q18 | 经正式授权后的影子/实际执行 | 分别证明 shadow 不拦工具、live 的放行/拒绝符合契约 | 正式授权后宿主 |

补充要求：保留当前坏产物作为负控，它必须在与缺陷对应的适用测试中失败。不能用“全部规则拒绝生成”通过验收：另用不创建生产痛苦的受控正例，证明在真实可观察事实下，既有 Artificer→Evaluator 链确能生成并接受正确规则。该正例只证明 A 的可用性，不能替代原原则 B 的完成。

生成验证沿用 `zai/glm-5.3-flash`，避免同时更换模型、事实和测试。若之后做模型对照，使用相同材料、能力、预算和独立检查；报告成本及不确定性，不用某次通过宣称模型总体优劣。

## 9. 成本与失败处理

- 不新增独立“可执行性分类模型”调用；语义判断放在现有 Scribe/Evaluator，确定性程序验证接口与来源。
- 沿用正式模型配置。当前工作区目标为 ZAI / glm-5.3-flash、timeoutMs=600000、maxTokens=32000；实施前回读，未经要求不改。先前成功试验发生在 maxTokens 恢复之前，不宣称它用了 32000。
- 保留现有 Artificer 最大轮数和 repair 上限，执行报告列出生效参数、调用数、耗时；不同阶段不得各自无限重试。
- 来源缺失等确定性问题零生成调用；模型服务瞬时失败交由既有有限重试策略，不创建 PD 通用重试机制。
- 不为本 SPEC 新增常驻服务或后台轮询；任务/worker 继续使用现有宿主生命周期。

## 11. 复杂度与兼容性

| Complexity Delta | A | B 条件具备后 |
|---|---|---|
| New durable source of truth | NO | NO：批准仍归宿主 |
| New persisted schema/state | YES：既有工件/评审元数据的加法扩展，不新建表 | YES：带版本的来源/验证投影，不复制批准权威 |
| New subsystem/service/background process | NO | NO |
| New public abstraction/interface | 尽量 NO：内部 preflight/元数据扩展；若实际跨包即如实记 YES | YES：现有上下文契约扩展 |
| New runtime feature flag | NO | 默认 NO：优先现有能力/激活控制；无法安全局部启用则 B 阻塞 |
| New cross-package dependency | NO：沿用既有依赖方向 | NO：宿主适配通过既有 seam 注入 |
| New host/platform-specific behavior | NO：共享生成质量修复 | YES：Codex 实时上下文/来源读取 |
| New external/network capability | NO：不新增模型调用类型 | NO：仅限已有可读权威来源；需新外部能力则另案 |

A 的元数据用于让停点、材料版本和独立验证可追溯，现有裸字符串风险说明不足以承担该职责。B 的接口扩展用于承载目前不存在于输入中的真实事实，不能由命令文本替代。均须通过真实 store round-trip 和消费者测试；回滚时保留元数据并使不支持的新规则暂停，不删除数据。

旧工件缺少新元数据不等于数据损坏：显示 legacy/unverified，不能伪造新验证通过。损坏元数据与 legacy 缺失必须区分。旧已激活 prompt 不因本 SPEC 自动停用；旧规则不因接通 provider 自动扩大执行范围。

## 12. 回滚与生产边界

- 代码通过 PR revert；发布通过正式 installer/updater 回退。禁止覆盖 `C:\Users\Administrator\.pd\runtime` 安装文件。
- 新代码规则通过现有停用机制回滚，保留批准、激活和运行历史；本 SPEC 本身不授权停用生产对象。
- 不直接修改生产 SQLite、config 或 `.pd` 状态；使用正式服务/CLI，遵守 dry-run/confirm。
- 证据来源失效时只影响依赖该来源的规则，沿用结构化暂停；不把整个工作区变成禁止执行。
- 数据迁移如确实需要，必须先遵守 DATA_CLEANUP_GUIDELINES；本方案不授权删除或改写治理历史。

## 13. 交付与判定

交付必须包括：实施报告、权威/接线核查、验收矩阵、失败负控、模型运行记录、实际安装证明、原信号各分支状态、PR/提交/CI、回滚步骤。公开报告不包含 API key、完整私密会话或敏感参数。

判定分开填写：

| 结果 | 可以声称 | 不可以声称 |
|---|---|---|
| A PASS | 生成质量控制修复，受控正例走通 | 原原则已产出正确代码、Codex已生效 |
| B BLOCKED | 已定位具体来源/宿主缺口，安全停点可恢复 | 全部实现完成、原痛苦完整闭环 |
| B review-ready | 原原则实际生成并通过独立验证，到达正确 Owner 审阅入口 | 已获批准、已激活、已影响行为 |
| B runtime-verified | 经正式授权后的真实调用证明影子/实际判定分别符合契约 | 长期行为改善、所有原则均可可靠生成 |

总体 COMPLETE 要求 A PASS、B review-ready，以及本次正式授权范围内的宿主验收全部完成；若 live 验收需要新的 Owner 激活决定而未发生，则标记待治理验收，不伪装技术失败、不自行批准。

### MVP 问题

- 不做的后果：继续生成可被自填批准标记绕过、且误拦正常开发的规则，削弱 Owner 信任。
- 如何观察：明确停点、真实独立回放、可审阅工件与宿主回执，不依赖模型自述。
- 如何关闭/恢复：现有激活控制、暂停契约、定点恢复和正式版本回滚。
- 情绪价值：让 Owner 知道“为何拦、为何放、哪里缺信息”，减少反复审批、无声等待和对规则真实性的怀疑。

## 14. SPEC 自评

- 已将生成能力、正确性、Owner 决定与真实执行拆开验收。
- 已区分原则批准与开发设计批准，未假设已有权威来源能直接复用。
- 已保留原坏产物和失败证据，不以测试数量或规则生成率替代质量。
- 已要求受控正例，避免靠拒绝全部生成掩盖能力不足。
- 已明确 B 的真实前置缺口和阻塞标准；本设计不承诺仅执行 A 就解决原原则。
- 已约束新上下文不能自动唤醒旧规则，且 unknown 不等于未批准。
- 已包含来源、调用链、输入输出、预算、失败、验收、交付和回滚；尚未实施，不声称修复已验证。

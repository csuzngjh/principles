PRI-1301 (SPEC-PD-PIPELINE-SPINE-001 follow-through): executor module separation + rollout revision-target dedup — pure move + deduplication, zero behavior change.

A — `executeSelectedInternalizationTask` and its typed input/output union move verbatim from `internalization-consumer-cycle.ts` into the new host-runtime module `internalization-task-executor.ts`. The consumer cycle keeps task selection/scheduling/per-kind runtime-profile resolution/adapter-L2 routing/preflight/input assembly/successor commit/recovery sweep/reconciliation; the six Peer Runner constructions now live in the executor module alone. The package public API is symbol-for-symbol unchanged — the executor entries re-export from the new module while cycle entries stay sourced from the cycle module (verified: identical export symbol set in dist/index.d.ts; only the internal re-export paths differ). The SPEC §3.5.2 construction-point whitelist guard tracks the new module (sole-constructor pin moved with equal strength, plus a zero-construction contract on the cycle file by non-whitelisting).

B — the rollout reviewer's private `resolveRevisionTarget` copy is deleted; `handleRevisionRouting` now calls the shared `resolveRolloutRevisionTarget` (revision-reopen.ts) through the bound `stateManager.getTask` — the same single source the Owner revise_once route already consumes (owner-resolution-service). The two implementations were verified line-by-line equivalent before removal. Review evidence showed the private runner copy's optional `viaArtifactId` annotation was dead speculative API: git history proves no implementation has assigned it since its introduction (c41e91032), no `viaArtifactId:` object literal exists in any commit, and no production consumer reads the persisted payload field back into routing. The field is therefore not widened into the public shared `RolloutRevisionTarget` contract; the runner now records/passes the rollout task id directly, exactly as the fallback always evaluated. Regression tests pin the observable status quo (`rollout-revision-routing-convergence.test.ts`: exact two-field resolution results; persisted rolloutRevisionPayload.sourceArtifactId === rollout taskId; exact `rollout_revision_routed` telemetry payload; exact `rollout_revision_target_unresolved` payload; cross-route same-target parity) plus a new Owner-route end-to-end revise_once test on a rollout task. Error strings, telemetry events and routing semantics are unchanged; any future correction of the misleading persisted `sourceArtifactId` semantics must update those pins explicitly, never silently.

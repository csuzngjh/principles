## CH01 · 为什么 Agent 需要从经验中改变

你有没有这样的经历？

为了让 Agent 做对一件事，你花了很多时间向它解释。

它当下理解了，也按照你的要求进行了修正。

可过几天，换一个任务，面对相似的问题，你又不得不从头提醒。

我们习惯不断补充 Prompt，增加规则，却很难让一次真实的纠正，稳定地影响未来的行动。

真正重要的，不只是让 Agent 这一次做对，而是让它在下一次遇到类似问题时，能够作出更好的选择。

Principles Disciple，简称 PD，希望解决的就是这件事。

它帮助 Owner 将真实任务中的行为经验，转化为经过审查、可以激活和持续管理的行为原则。

## CH02 · 一次真实的行为偏差

在一个 AI 产品研发项目中，Codex 承担了一项复杂的开发任务。

它提出了新的技术方案，推进了代码实现，完成了测试，整个工作看起来相当完整。

但它在具体设计还没有获得 Owner 批准之前，就开始按照自己的理解推进实施。

它把对总体方向的认可，以及在指定工作区内开展工作的许可，当成了对具体设计方案的授权。

问题不是它没有能力完成任务。

而是它替 Owner 跨过了一道本应由人决定的边界。

Owner 指出了问题：

方向得到认可，不代表具体设计已经批准。

允许开展工作，也不意味着每一个重要的技术决定都已经获得授权。

## CH03 · 让一次纠正留下来

如果这次纠正只留在聊天记录里，随着对话结束，它很可能就被埋在历史信息中。

PD 提供 Pain 记录，让 Owner 可以把这次值得关注的行为偏差、相关上下文和自己的纠正要求保留下来。

在这个案例中，这条 Pain 是由 Owner 主动记录的。

它不是一次普通的工具报错，也不是系统自动认定 Agent 犯了错。

它代表的是一次值得进一步分析的真实经验。

从这一刻开始，这次纠正不再只属于某一次对话，而成为一条可以追溯、分析和持续管理的记录。

## CH04 · 从一次经验形成长期原则

接下来，PD 围绕这次行为和相关上下文进行诊断，帮助理解问题背后的原因。

在这个案例中，真正需要解决的，是设计确认流程缺失，以及不同层级授权被混为一谈。

最终形成的原则是：

非简单变更，先提交设计方案，获得批准后再编码。

对于涉及重要设计选择、较高成本或明显产品影响的任务，Agent 应先调查现状，整理技术方案，说明调用链、成本、失败处理、验收和回滚，再取得与具体设计相匹配的批准。

而对于已经明确授权的简单、低风险修复，不需要机械地增加审批环节。

这条原则不只是重复一次纠正，而是尝试把背后的判断沉淀为未来可以继续遵循的行为要求。

## CH05 · 让 Owner 决定什么值得保留

但一条原则形成之后，并不意味着它就应该自动生效。

Owner 可以在 PD 中查看它来自哪次行为、解决什么问题、适用于哪些场景，以及可能产生什么影响。

你可以选择批准、修改或拒绝。

AI 可以帮助你分析问题、整理经验、提出原则。

但什么值得成为长期要求，最终必须由 Owner 决定。

因为我们希望 Agent 能够遵循你的判断，而不是替你决定应该坚持什么。

## CH06 · 让原则进入 Agent 的工作

经过批准的原则，还需要真正进入 Agent 的工作流程。

PD 可以通过提示词治理通道，将已经激活的原则带入 Agent 的工作上下文。

这样，当 Agent 处理相关任务时，就能够参考 Owner 已经认可的行为要求。

对于需要更强工具调用约束的场景，PD 还提供运行时规则治理能力。

两种治理方式解决的问题不同：一种为 Agent 提供决策参考，另一种可以在明确配置和授权后约束特定操作。

在刚才的案例中，实际使用的是 Codex 提示词治理通道。

这意味着，过去只存在于一次纠正中的要求，现在有机会继续影响 Agent 后续的工作。

## CH07 · 真正重要的是下一次

接下来，让我们把时间往后推。

在后续的一次同一个项目修复任务中，Codex 没有直接修改产品代码，而是先提交修复方案，说明准备做什么，并主动请求 Owner 批准。

它的回复中，也提到了此前形成的设计确认原则。

这一次，我们看到了一种不同的行为表现。

面对需要确认的设计变更，它先说明方案，再把决定权交还给 Owner。

你会发现，这比成功生成一条原则、成功点击一次激活按钮，更值得关注。

因为我们真正想看到的，是 Agent 在未来的任务中，能够不再重复之前的错误。

当然，一次符合预期的表现，还不足以证明行为变化完全由 PD 造成。

但它给了我们一个值得继续验证的方向：

这种表现，能否在更多任务、不同情境和更长时间里持续出现？

## CH08 · 从一次纠正，到长期行为改善

这也是为什么 PD 还需要 Examiner。

一次正确的表现，只是开始。

我们还需要持续检验：换一个任务，Agent 是否依然能够作出正确判断？经过一段时间，这种表现是否还能保持？行为变化是否确实来自原则机制，而不是其他因素？

PD 希望把真实经验转化为长期行为原则。

Examiner 则帮助我们检验，这些原则是否真正改变了 Agent 未来的行为。

我们追求的，不是让 Agent 记住更多。

而是让一次纠正，成为下一次正确选择的开始。
